# ① Next.jsとは何か — Reactとの違いとレンダリングの前提知識

[← 総合インデックスに戻る](README.md) ｜ 次の章 → [② 環境構築とプロジェクト構造](02-setup-and-structure.md)

この章では**コードを書く前に知っておくと後がラクになる前提知識**を扱います。「Next.jsが何を代わりにやってくれているのか」がわかると、以降の章の規約が丸暗記ではなく理屈で理解できます。

---

## 1. まずReactとは何だったのか

React は **「画面（UI）を部品に分けて組み立てるためのライブラリ」** です。それ以上でも以下でもありません。

```jsx
// これがReactの本質。「データ」を渡すと「画面」が返る関数
function UserCard({ name }) {
  return <div className="card">こんにちは、{name}さん</div>
}
```

React が保証してくれるのは「**データが変わったら画面も自動で追従する**」ことだけです。裏を返すと、Webサービスに必要な次のものは**一切入っていません**。

| 必要なもの | Reactに入っているか | なければどうなるか |
| --- | --- | --- |
| URLとページの対応（ルーティング） | ❌ | `/about` を開いても何も起きない |
| サーバー側の処理 | ❌ | DBに繋げない。APIサーバーを別途用意する必要 |
| データ取得の作法 | ❌ | 各自バラバラの実装になる |
| SEO（検索エンジン対応） | ❌ | 中身が空のHTMLしか返らず検索に載りにくい |
| 画像・フォント・JSの最適化 | ❌ | 表示が遅い |
| 本番ビルドの仕組み | ❌ | 自分でビルド設定を書く |

**この「足りない部分」を全部埋めたのが Next.js** です。

```
React      = エンジン
Next.js    = エンジンを積んだ「完成車」（ハンドル・車体・保安部品つき）
```

---

## 2. Next.jsが引き受けてくれること

| 機能 | Next.jsでのやり方 | 自前でやるなら |
| --- | --- | --- |
| ルーティング | `app/about/page.tsx` を置くだけで `/about` になる | React Router の設定を書く |
| サーバー処理 | コンポーネントが既定でサーバー実行。DBに直接アクセス可 | Express等のAPIサーバーを別に立てる |
| データ取得 | `async` コンポーネントで `await` するだけ | fetchライブラリ＋状態管理を組む |
| SEO | サーバーでHTMLを生成して返す＋`metadata` API | SSR基盤を自作する |
| 画像最適化 | `next/image` が自動でリサイズ・WebP変換・遅延読み込み | 画像変換パイプラインを構築 |
| ビルド | `next build` 一発（Turbopack） | webpack/vite の設定を書く |
| 更新処理 | Server Actions（関数を呼ぶだけ） | REST APIを設計・実装 |

> **ポイント**：Next.js は「フロントエンドのフレームワーク」と説明されがちですが、実態は **フロントエンドとバックエンドを1つのプロジェクトで書けるフルスタックフレームワーク** です。

## 3. レンダリング方式 — この章の山場

Next.js を理解する上で避けて通れないのが「**HTMLをいつ・どこで作るか**」の分類です。ここを押さえると、以降の章の「なぜこう書くのか」が全部つながります。

### たとえ話：レストランの料理提供方式

| 方式 | たとえ | いつHTMLを作る |
| --- | --- | --- |
| **CSR** | 材料だけ渡されて客が自分で調理 | ブラウザ側で作る |
| **SSR** | 注文を受けてから作る（できたて） | リクエストのたびにサーバーで作る |
| **SSG** | 作り置きの弁当を並べておく | ビルド時に一括で作る |
| **ISR** | 作り置きだが、一定時間ごとに作り直す | ビルド時＋定期的に再生成 |

### ① CSR（Client Side Rendering / クライアントサイドレンダリング）

素のReactアプリの方式。サーバーは**空のHTML**とJavaScriptを返し、ブラウザがJSを実行して画面を描きます。

```html
<!-- サーバーが返すHTML -->
<body>
  <div id="root"></div>   <!-- 中身が空！ -->
  <script src="/app.js"></script>
</body>
```

- ✅ 画面遷移が速い、サーバー負荷が低い
- ❌ 初回表示が遅い（JSのダウンロード＋実行を待つ）
- ❌ SEOに弱い（クローラーに中身が見えないことがある）
- 向いている用途：管理画面・ログイン後のダッシュボードなど、SEO不要な画面

### ② SSR（Server Side Rendering / サーバーサイドレンダリング）

リクエストが来るたびに**サーバーで完成したHTMLを作って返す**方式。

- ✅ 初回表示が速く、SEOに強い
- ✅ 常に最新のデータを出せる
- ❌ アクセスのたびにサーバーが働く（負荷・コスト）
- 向いている用途：ログイン後のマイページ、在庫・価格などリアルタイム性が要るページ

### ③ SSG（Static Site Generation / 静的サイト生成）

**ビルド時にHTMLを作り切ってしまう**方式。あとはCDNからファイルを配るだけ。

- ✅ 圧倒的に速い・安い（ただのファイル配信）
- ✅ SEOに強い、サーバーが落ちにくい
- ❌ 内容の更新にはビルドし直しが必要
- 向いている用途：ブログ・LP・ドキュメント・企業サイト

### ④ ISR（Incremental Static Regeneration / 増分静的再生成）

SSGの弱点（更新に再ビルドが必要）を埋めた方式。**静的HTMLを配りつつ、指定時間が過ぎたらバックグラウンドで作り直す**。

```
0秒       静的HTMLを配信（速い）
...
3600秒後  次のアクセスをきっかけに裏で再生成 → 以降は新しいHTMLを配信
```

- ✅ SSGの速さと、SSRの新しさの「いいとこ取り」
- 向いている用途：ニュース・ECの商品一覧など「そこそこ更新されるが毎回最新でなくてよい」ページ

### ⑤ PPR（Partial Prerendering / 部分プリレンダリング）

Next.js が到達した**現代の答え**。1つのページの中で、**静的な部分と動的な部分を混ぜます**。

```
┌─────────────────────────────┐
│ ヘッダー・商品説明・フッター  │ ← 静的（即座に配信）
│ ┌─────────────────────────┐ │
│ │ ログインユーザー名        │ │ ← 動的（遅れてストリーミング）
│ │ 在庫数・カート            │ │
│ └─────────────────────────┘ │
└─────────────────────────────┘
```

「ページ単位でSSRかSSGか選ぶ」時代が終わり、**コンポーネント単位で選べる**ようになりました。これを実現するのが Next.js 16 の **Cache Components**（→ [⑤データ取得とキャッシュ](05-data-fetching-caching.md)）です。

### 一覧で比較

| | CSR | SSR | SSG | ISR | PPR |
| --- | --- | --- | --- | --- | --- |
| HTML生成 | ブラウザ | リクエスト毎 | ビルド時 | ビルド時＋定期 | 混在 |
| 初回表示 | 遅い | 速い | 最速 | 最速 | 最速 |
| データの新しさ | 最新 | 最新 | ビルド時点 | やや古い | 部分ごとに選べる |
| サーバー負荷 | 低 | 高 | ほぼ無 | 低 | 低〜中 |
| SEO | 弱い | 強い | 強い | 強い | 強い |

## 4. Next.jsの歴史（なぜ今の形になったか）

丸暗記は不要ですが、**ネットの情報が「いつの話か」を見分けるために**役立ちます。

| 時期 | バージョン | 何が起きたか |
| --- | --- | --- |
| 2016 | v1 | SSR対応のReactフレームワークとして登場 |
| 2020 | v9.3 | SSG / ISR が整備され「静的も動的も」使えるように |
| 2022 | **v13** | **App Router** 登場。React Server Components を採用（大転換点） |
| 2023 | v13.4 | App Router が安定版に。`app/` が推奨される流れへ |
| 2024 | v15 | React 19対応。`params`/`searchParams` が非同期に。キャッシュ既定がOFF方向へ |
| 2025〜 | **v16** | **Cache Components（`use cache`）** 導入。Turbopack既定。`middleware.ts`→`proxy.ts` |

> ⚠️ **ネットの記事を読むときの注意**：`pages/` ディレクトリ、`getServerSideProps`、`getStaticProps` が出てくる記事は **Pages Router（v12以前の作法）** です。現在の主流である App Router とは書き方がまったく違います。**2023年より前の記事は基本的に読み替えが必要**だと思ってください。

---

## 5. Pages Router と App Router

Next.js には歴史的経緯から**2つのルーティング方式**があります。

| | Pages Router（旧） | App Router（現行・推奨） |
| --- | --- | --- |
| ディレクトリ | `pages/` | `app/` |
| データ取得 | `getServerSideProps` / `getStaticProps` | コンポーネント内で直接 `await` |
| コンポーネント | 全てクライアント側 | **既定でサーバー** |
| レイアウト共通化 | `_app.tsx` で工夫が必要 | `layout.tsx` でネスト可能 |
| 現在の位置づけ | 保守はされるが新規採用は非推奨 | **新規はこちら一択** |

**このシリーズは App Router を前提に解説します。** Pages Router は既存プロジェクトの保守で出会ったときのために、[②](02-setup-and-structure.md) で対応表だけ載せます。

## 6. 他フレームワークとの比較 — Next.jsを選ぶべきか

Next.js は万能ではありません。**選ばない方がいい場面**も知っておくと判断を誤りません。

| フレームワーク | ベース | 特徴 | Next.jsと比べて |
| --- | --- | --- | --- |
| **Next.js** | React | フルスタック・エコシステム最大 | 基準 |
| **Remix / React Router v7** | React | Web標準（fetch/FormData）志向・シンプル | 学習しやすいがエコシステムは小さめ |
| **Astro** | 非依存 | コンテンツ特化。既定でJSゼロ | ブログ・LPならこちらが軽くて速い |
| **Nuxt** | Vue | Next.jsのVue版 | Vueが好き/社内標準ならこちら |
| **SvelteKit** | Svelte | 記述量が少なく高速 | 学習は快適だが求人・情報量は少ない |
| **Vite + React SPA** | React | 素のSPA。最小構成 | SEO不要な管理画面ならこれで十分 |

### 判断フロー

```
ブログ・LP・ドキュメントが主体で、動きは少ない
    → Astro（Next.jsだと過剰）

社内管理画面・SEO不要・ログイン必須
    → Vite + React SPA（Next.jsの利点をほぼ使わない）

SEOが要る × ログイン後の機能もある × DBを使う
    → Next.js ◎（最も得意な領域）

すでにVue/Svelteが社内標準
    → Nuxt / SvelteKit

モバイルアプリと共通のAPIサーバーが主目的
    → NestJS等の専用バックエンド＋フロントは別途
```

> **正直な注意点**：Next.js は高機能な分、**概念が多く学習コストが高い**です。「ReactをやりたいだけならNext.jsから始めるべき」と言われることが多いですが、Server/Client Components の境界（→ [④](04-server-client-components.md)）でつまずく人は非常に多いです。この教材はそこを重点的に説明します。

---

## 7. この章のまとめ

- **React はUIライブラリ、Next.js はそれを本番運用可能にするフルスタックフレームワーク**
- レンダリング方式は **CSR / SSR / SSG / ISR / PPR** の5つ。現代のNext.jsは **PPRでこれらを混ぜられる**
- **App Router（`app/`）が現行**。`pages/`・`getServerSideProps` が出てくる情報は古い作法
- Next.js が輝くのは「**SEOが要る × DBを使う × ログイン機能もある**」Webサービス
- コンテンツ主体なら Astro、SEO不要な管理画面なら Vite+React でも十分
