# ⑥ 目論見書の電子交付・書類送付 — 同意管理・版数管理・郵送運用

[← ⑤ 分配金の再投資](05-distribution-reinvestment.md) ｜ [総合インデックス](README.md) ｜ 次 → [⑦ 委託会社との調整](07-management-company.md)

目論見書の交付は **「買付注文を受ける前に必ず終わっていなければならない」** 手続です。つまり注文フローの一部であり、ここが詰まると**そもそも商品が売れません**。同時に、版数管理を誤ると「古い目論見書で販売した」という重大な法令違反につながります。

---

## 0. この章のゴール

1. 交付すべき書類の種類と、それぞれの交付義務・タイミングを説明できる
2. **電子交付の同意管理**（取得・撤回・記録）を設計できる
3. **版数管理と訂正目論見書**という、最も事故が起きやすい領域を押さえる
4. 郵送運用のコストと、電子交付への誘導戦略を判断できる

---

## 1. 交付すべき書類の全体像

| 書類 | 交付義務 | タイミング | 電子交付 | 作成者 |
| --- | --- | --- | --- | --- |
| **交付目論見書**（投資信託説明書） | **あり**（法定） | **買付注文を受ける前まで** | 可（要承諾） | 委託会社 |
| **請求目論見書** | 請求があったとき | 請求後速やかに | 可（要承諾） | 委託会社 |
| **契約締結前の情報提供**（重要事項） | あり（法定） | 契約締結前 | 可 | 自社（交付目論見書で代替する運用が一般的） |
| **重要情報シート** | 実務上（FD原則） | 販売時 | 可 | 自社 |
| **交付運用報告書** | あり（法定） | 決算期後（日々決算型は特例あり） | 可（要承諾） | 委託会社 |
| 運用報告書（全体版） | 提供義務 | 同上 | 委託会社サイト掲載が原則 | 委託会社 |
| **信託約款** | 請求があったとき | 請求後 | 可 | 委託会社 |
| 月次レポート | 任意 | 月次 | サイト掲載 | 委託会社 |

> 🔍 **確認事項（法務・コンプライアンスへ）**
> 金融商品取引法は近年、**書面交付義務を「情報提供義務」に改め、電磁的方法での提供を原則とする方向で改正**されています。施行状況と、本件に適用される具体的な要件（何を・いつまでに・どの方法で提供すべきか）を、**最新の法令ベースで必ず確認してください。** 本ガイドの記載は論点の所在を示すものであり、条文の引用ではありません。

## 2. 交付目論見書 — 注文フローへの組込み

### 2-1. 原則

**「交付目論見書を交付した後でなければ、買付注文を受け付けてはならない」**

これが設計の大原則です。したがって注文画面の前に、必ず交付のステップが入ります。

```
 ファンド詳細画面
      ↓
 【交付目論見書の表示】 ← ここを飛ばして注文画面に行けてはいけない
      ↓
 「内容を確認しました」のチェック
      ↓
 適合性確認（投資経験・リスク許容度）
      ↓
 注文入力画面
      ↓
 注文確認画面 → 確定
```

### 2-2. 2回目以降の買付での省略

毎回フルで読ませるのは現実的でないため、法令には**一定の条件下で交付を省略できる規定**があります。

| 省略の考え方 | 論点 |
| --- | --- |
| すでに同一内容の目論見書を交付済みの顧客 | **「同一内容」であることの判定 ＝ 版数管理**（[3節](#3-最重要版数管理と訂正目論見書)） |
| 顧客が交付を希望しない旨を申し出た場合 | 申出の記録・管理が必要 |

> ⚠️ **省略規定を使う場合、「その顧客に、どの版を、いつ交付したか」の記録が必須**になります。これが[3節](#3-最重要版数管理と訂正目論見書)の版数管理そのものです。

> 🔍 **確認事項**：省略規定の適用要件と、自社での運用方針（毎回交付するか、省略規定を使うか）をコンプライアンスと決定してください。**「毎回必ず表示する」は法令上は安全ですが、UXが悪化し、顧客が読み飛ばす副作用があります。**

## 3. 【最重要】版数管理と訂正目論見書

### 3-1. 目論見書は更新される

| 更新の契機 | 頻度 | 対応 |
| --- | --- | --- |
| **有価証券届出書の年次更新** | 年1回 | 新しい版に差し替え |
| **決算後の改訂** | 決算期ごと | 運用実績データの更新 |
| **訂正届出書の提出** | 随時 | ★**訂正目論見書**。緊急対応が必要 |
| 約款変更 | 随時 | 変更内容の反映 |
| 委託会社の商号変更等 | 随時 | — |

### 3-2. 事故のシナリオ

```
【よくある事故】
  4/1   委託会社が新しい目論見書（第2版）を作成し、自社へ送付
  4/1   担当者がメールを見落とす
  4/2〜 自社サイトでは第1版が表示され続ける
  4/2〜 顧客は「古い目論見書」で買付をしている
  5/10  発覚 → 該当期間の全顧客に再交付、当局報告、経緯説明
```

**これは実際に起こりうる事故です。** 版数管理は「システムで自動化する」か、「絶対に漏れない業務フロー」を作るかの二択です。

### 3-3. 設計要件

| # | 要件 | 内容 |
| --- | --- | --- |
| **1** | **版数の管理** | 目論見書PDFに版数・適用開始日・適用終了日を持たせる |
| **2** | **有効版の自動判定** | 表示時点で有効な版を自動的に選択する |
| **3** | **切替の予約** | 「4/1から第2版に切り替える」を事前に登録できる |
| **4** | **交付記録との紐付け** | 「顧客Aに、第1版を、4/1に交付した」を記録する |
| **5** | **版が変わったときの再交付** | 既交付顧客に新版を交付するか、次回買付時に再表示するか |
| **6** | **訂正目論見書への緊急対応** | 即時差替え。切替の予約を待たない経路が必要 |
| **7** | **受領から公開までのSLA** | 委託会社から受領して何時間以内に公開するか |
| **8** | **受領の確認プロセス** | 委託会社から届いたことを確実に検知する仕組み |
| **9** | **公開前のチェック** | 担当者以外によるダブルチェック |
| **10** | **旧版の保存** | 「当時どの版を交付したか」を後から証明できる |

> 🔍 **委託会社への確認事項（[⑦](07-management-company.md)と連動）**
> 1. 目論見書の改訂スケジュール（年次更新の時期、決算後の改訂時期）
> 2. 改訂版の**提供方法と提供タイミング**（何日前に届くか）
> 3. **訂正目論見書が発生した場合の緊急連絡ルート**と、差替え期限
> 4. ファイル形式（PDF）、ファイル名の命名規則、版数の識別方法
> 5. 提供経路（メール／FTP／専用サイト）と、受領確認の方法

> 💡 **推奨**：「メールで送られてくるPDFを手作業でアップロード」は事故の温床です。**可能な限り、受領〜公開を自動化するか、少なくとも受領の検知をシステム化**してください。自動化できない場合は、**チェックリストによる日次確認**を業務フローに組み込みます。

## 4. 電子交付の同意管理

### 4-1. 同意のライフサイクル

```
  未同意 ──(同意取得)──→ 同意済 ──(撤回)──→ 撤回済（＝郵送に戻る）
    │                       │
    │                       └──(メール不達が継続)──→ 要確認状態
    │
    └──(買付しようとする)──→ 同意取得フローへ誘導
```

### 4-2. 設計で決めること

| # | 論点 | 選択肢・注意 |
| --- | --- | --- |
| **1** | **同意の取得方法** | Web上での同意（チェックボックス＋確定操作）／書面 |
| **2** | **同意の粒度** | 全帳票一括／帳票種類別／商品別。**一括が運用は楽**だが顧客の選択肢は狭い |
| **3** | **同意の記録項目** | 同意日時、同意対象、IPアドレス、同意時の画面の版 |
| **4** | **同意の管理主体** | ★**フロント（自社）かソナーか。責任分界点の要確認項目**（[⑩](10-sonar-integration.md)） |
| **5** | **撤回の方法** | Web上で撤回可能にするか、電話・書面のみか |
| **6** | **撤回後の扱い** | 郵送に切り替わる。**切替のタイミング**（次回帳票から／即時） |
| **7** | **メールアドレスの管理** | 登録・変更・検証（確認メール）の仕組み |
| **8** | **メール不達時** | 何回不達で郵送に切り替えるか。顧客への確認方法 |
| **9** | **閲覧確認の記録** | いつ閲覧したかを記録するか。**法令上の要否をコンプラに確認** |
| **10** | **未閲覧の督促** | 一定期間閲覧がない場合の対応 |
| **11** | **ダウンロード・保存** | 顧客がファイルに保存できる形式で提供されているか（法令要件） |
| **12** | **閲覧可能期間** | 何年間サイトで閲覧できるようにするか |

> 🔍 **確認事項（2件）**
> - **コンプライアンスへ**：電磁的方法による提供の法令要件（事前の承諾、ファイルへの記録・出力可能性、承諾の記録保存など）の具体的内容
> - **大和総研へ**：電子交付の同意情報をソナー側で保持するか、フロント側で保持してソナーへ連携する方式か。**既存の他商品での実装方式に合わせるのが安全です**

### 4-3. 「同意の正」をどこに置くか

これは地味ですが、事故が起きる論点です。

| 方式 | メリット | デメリット |
| --- | --- | --- |
| **フロント（自社Web）を正とする** | Web上の同意取得と一体で管理できる | ソナーが帳票を出すとき、毎回フロントに問い合わせる必要がある |
| **ソナーを正とする** | 帳票出力時の判定が完結する | Web上で同意を取ったら、ソナーへ連携するIFが必要。**連携失敗時に不整合** |
| 両方で保持 | ✕ **非推奨** | **必ずズレる**。ズレたときに郵送すべき顧客に電子交付してしまう |

> ⚠️ **「両方で保持」は避けてください。** 同意状態がズレると、法令上必要な書面が届かない事態になります。**正を1つに決め、もう一方は参照のみ**にしてください。

## 5. 未同意者の扱い（買付制御）

電子交付に同意していない顧客をどうするか。**これは経営判断が必要な論点**です。

| 方針 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| **A. 郵送で対応** | 未同意者には書類を郵送する | 顧客を制限しない | ★**郵送コストが代行手数料収入を上回る可能性** |
| **B. 電子交付を必須にする** | 同意しないと買付できない | コストが読める。運用が単純 | 一部顧客を排除する。**苦情・お客様本位の観点で要検討** |
| **C. 郵送に手数料を設定** | 郵送希望者から実費を徴収 | コストを転嫁できる | 手数料設定の妥当性の説明が必要 |
| **D. 一定残高以上は郵送、少額は電子必須** | ハイブリッド | コストと顧客利便の折衷 | ロジックが複雑 |

> 💡 **判断材料としてコスト試算をしてください**
>
> ```
>  郵送1通あたりのコスト
>    ＝ 印刷費 ＋ 封入封緘費 ＋ 郵便料金 ＋ （返戻処理コスト）
>
>  年間の郵送コスト
>    ＝ 上記 × 未同意顧客数 × 年間の帳票発生回数
>
>  1顧客あたりの年間代行手数料収入
>    ＝ 平均保有残高 × 代行手数料率
>
>  ★ MMFはノーロードかつ低料率、少額取引が中心になりやすいため、
>    「郵送コスト > 手数料収入」が現実に起こります。
>    この数字を出さずに方針を決めないでください。
> ```

> ⚠️ **方針Bを採る場合、「顧客本位の業務運営」の観点からの説明が必要**です。デジタルに不慣れな顧客を排除することになるため、**コンプライアンスと経営の承認を取ってください。** 高齢顧客への配慮も論点になります。

## 6. 書類送付（郵送）の運用設計

電子交付を進めても、郵送はゼロにはなりません。

### 6-1. 業務フロー

```
  帳票データ生成（ソナー／自社）
        ↓
  郵送対象の抽出（電子交付未同意者・郵送希望者）
        ↓
  印刷発送会社へデータ連携
        ↓
  【同封物の最適化】← 複数帳票を1通にまとめて郵便料金を削減
        ↓
  印刷・封入封緘
        ↓
  発送
        ↓
  【返戻処理】← 宛先不明で戻ってきた分
        ↓
  住所確認・取引制限の要否判断
```

### 6-2. 決めること

| 項目 | 論点 |
| --- | --- |
| **印刷発送会社** | 既存の委託先に相乗りするか、新規に選定するか。**リードタイムに注意** |
| **データ連携の形式・タイミング** | ファイル形式、連携頻度、締め時刻 |
| **同封物の最適化ルール** | どの帳票とどの帳票を同封できるか。**法定交付期限が異なる帳票を同封すると期限違反のリスク** |
| **発送のSLA** | データ連携から何営業日で発送するか |
| **宛名の基準日** | いつ時点の住所を使うか。基準日以降の住所変更の扱い |
| **返戻の処理** | 保管期間、再送の要否、取引制限との連動 |
| **発送記録** | 誰に何をいつ発送したかの記録・保存 |
| **大量発送のピーク** | 年間取引報告書の時期（1月）がピーク。**印刷会社のキャパシティを確認** |

> ⚠️ **同封物の最適化には落とし穴があります。** 「交付期限が異なる帳票を同封すると、早い方の期限に遅れる」ことがあります。同封ルールは**期限が最も厳しい帳票に合わせる**か、期限グループごとに封を分けてください。

## 7. 交付記録の保存

法令対応・当局検査・紛争対応のために、**「誰に・何を・いつ・どの方法で交付したか」の記録**が必要です。

| 記録項目 | 内容 |
| --- | --- |
| 顧客識別 | 顧客コード・口座番号 |
| 交付書類 | 書類種別、**版数**（★目論見書は必須） |
| 交付日時 | 電子交付の場合は「閲覧可能な状態に置いた日時」 |
| 交付方法 | 電子交付／郵送 |
| 電子交付の場合 | 通知メールの送信日時、閲覧日時（記録する場合） |
| 郵送の場合 | 発送日、返戻の有無 |
| 同意の状態 | 交付時点での同意状態 |

| 観点 | 決めること |
| --- | --- |
| **保存年限** | [②](02-customer-documents.md)・[③](03-internal-documents.md)の保存年限と揃える |
| 検索性 | 顧客・日付・書類種別で検索できるか |
| **当時の書類の再現** | ★交付した版のPDF自体を保存しておく。**委託会社のサイトから消えていても再現できるように** |
| 保存場所 | ソナー／自社／外部ストレージ |

> ⚠️ **「委託会社のサイトにリンクを張っているだけ」は危険です。** 数年後にリンク切れになり、「当時どの内容を交付したか」を証明できなくなります。**交付した版のPDF実体を自社で保存**してください。

## 9. 見落としやすい論点

| 論点 | 内容 |
| --- | --- |
| **設定日前の目論見書** | 新規設定ファンドは、設定日前に目論見書が確定している必要がある。**リリース日の前に入手できるか**を委託会社に確認 |
| **サイト掲載のタイミング** | 販売開始日の何日前から目論見書を掲載するか |
| 交付運用報告書の初回 | 日々決算型の特例により、初回交付がいつになるか（[②](02-customer-documents.md)） |
| **アクセシビリティ** | PDFのテキスト抽出可否。スクリーンリーダー対応。委託会社作成のPDFの品質に依存する |
| ファイルサイズ | スマートフォンでの閲覧に耐えるか |
| **スマホでの閲覧性** | 目論見書PDFはA4前提で作られており、スマホでは読みにくい。HTML版の提供を委託会社に相談する価値がある |
| 同意の一括移行 | 既存顧客の電子交付同意を、新商品にも適用できるか。**同意の範囲**をコンプラに確認 |
| 外国籍顧客 | 日本語のみでよいか |
| 法人顧客 | 同意者は誰か（代表者／担当者）。担当者変更時の扱い |
