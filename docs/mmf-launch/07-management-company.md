# ⑦ 委託会社との調整 — 契約・商品性・データ授受・障害時対応

[← ⑥ 目論見書の電子交付](06-prospectus-delivery.md) ｜ [総合インデックス](README.md) ｜ 次 → [⑧ 情報ベンダーへのデータ連携](08-info-vendor.md)

**このプロジェクトで唯一、自社の努力だけでは短縮できないのが委託会社との調整です。** 相手のスケジュール、相手の意思決定プロセス、相手のシステム制約に律速されます。したがって **最も早く着手すべき領域** でもあります。

---

## 0. この章のゴール

1. 委託会社と締結・取り交わすべき文書を漏れなく列挙できる
2. **合意すべき商品性パラメータの一覧**を、そのまま打合せ資料として使える
3. データ授受・決済・障害時対応の取り決め項目を設計できる
4. 打合せのアジェンダと進め方が分かる

---

## 1. なぜ委託会社との調整が最優先なのか

```
 【依存関係】

  委託会社との商品性の合意
        ↓
  ├→ ソナーの銘柄マスタ登録項目が決まる        → [⑩]
  ├→ 注文の締め時刻・受渡サイクルが決まる      → [④]
  ├→ 分配金の計算方法・端数処理が決まる        → [⑤]
  ├→ 信託財産留保額のロット管理方式が決まる    → [④]
  ├→ 目論見書の提供スケジュールが決まる        → [⑥]
  ├→ 代行手数料率と請求方法が決まる            → [③]
  └→ 決済スキームが決まる                      → [⑨]

  ★つまり、ここが決まらないと他章の設計が始められない
```

> 💡 **実務のコツ**：委託会社との第1回打合せを、**プロジェクト開始から2週間以内**に設定してください。「要件を固めてから相談する」のではなく、**「相談しながら要件を固める」**のが正しい順序です。

## 4. 商品審査とデューデリジェンス

委託会社との調整と並行して、**社内の商品審査**を通す必要があります。

| プロセス | 内容 | リードタイム |
| --- | --- | --- |
| 委託会社へのデューデリジェンス | 運用体制、リスク管理体制、コンプライアンス体制の確認 | 既存取引先なら簡略化可 |
| **商品審査**（社内） | 商品性・リスク・顧客適合性の審査 | ★**審査会の開催頻度に律速される**（月1回等） |
| 取扱開始の決裁 | 経営会議等 | 審査会の後 |

> ⚠️ **商品審査会の開催スケジュールを、プロジェクト開始時に確認してください。** 「月1回開催、資料は2週間前提出」なら、実質的に1.5か月前には商品性が固まっている必要があります。**ここがクリティカルパスになるケースが多い**です。詳細は[⑬ コンプライアンス](13-compliance-ops.md)。

## 5. データ授受の取り決め

### 5-1. 授受するデータの一覧

| データ | 方向 | 頻度 | タイミング | 論点 |
| --- | --- | --- | --- | --- |
| **注文（設定・解約）** | 自社 → 委託会社 | 日次 | 締め後 | 経路（ほふり／直接） |
| 注文の受領確認・リジェクト | 委託会社 → 自社 | 日次 | 伝送後 | ★リジェクト時の連絡方法 |
| **基準価額** | 委託会社 → 自社 | 日次 | 公表時刻 | ★未着時の対応 |
| **1万口あたり分配金額** | 委託会社 → 自社 | 日次 | 基準価額と同時？ | ★MMF固有 |
| 約定結果 | 委託会社 → 自社 | 日次 | — | — |
| **残高照合データ** | 双方向 | 日次／月次 | 夜間 | [⑨](09-trustee-settlement.md) |
| 代行手数料の明細 | 委託会社 → 自社 | 月次等 | — | [③](03-internal-documents.md) |
| 販売会社別残高報告 | 自社 → 委託会社 | 月次等 | — | [③](03-internal-documents.md) |
| 目論見書PDF | 委託会社 → 自社 | 改訂時 | ★SLA要 | [⑥](06-prospectus-delivery.md) |
| 運用報告書 | 委託会社 → 自社 | 決算期後 | — | [②](02-customer-documents.md) |
| 月次レポート | 委託会社 → 自社 | 月次 | — | [⑧](08-info-vendor.md) |

### 5-2. データ1本ごとに決めること

| 観点 | 内容 |
| --- | --- |
| **形式** | ファイル形式（固定長／CSV／XML）、文字コード、改行コード |
| **項目定義** | 項目名、桁数、型、必須／任意、コード体系 |
| **経路** | ほふりの投信決済システム／FTP／専用線／メール／Webポータル |
| **タイミング** | 送信時刻、受信可能時刻、締め時刻 |
| **件数** | 想定件数、最大件数 |
| **暗号化・認証** | 暗号化方式、認証方式 |
| **再送** | 失敗時の再送手順、再送可能時刻 |
| **受領確認** | 受け取ったことをどう確認するか |
| **★未着時の対応** | 何時までに届かなければエスカレーションするか |
| **テスト** | 接続テストの実施時期、テストデータの提供 |

> 💡 **投資信託業界には、投資信託協会が定める標準的なデータフォーマットがあります。** 独自形式で作る前に、標準フォーマットが使えないか委託会社に確認してください。**標準に乗れば、ソナー側も標準機能で対応できる可能性が高くなります**（＝アドオン回避）。

## 6. 決済スキームの取り決め

詳細は[⑨ 受託会社・決済インフラ連携](09-trustee-settlement.md)で扱いますが、委託会社と合意すべき点を挙げます。

| 項目 | 論点 |
| --- | --- |
| **決済方式** | ほふりの投信決済システムを使うか、相対（直接振込）か |

| 資金の受領口座 | 解約代金の入金先 |

| ネッティング | 買付と解約を相殺するか |
| 資金不足時の扱い | 未達時の対応、遅延損害 |
| 照合方法 | 約定照合・資金照合の手順 |

## 7. 障害時・異常時の取り決め

**「起きない前提」で契約せず、起きたときの手順を先に決めてください。**

| 事象 | 決めること |
| --- | --- |
| **基準価額の算出遅延** | 何時までに届かなければ連絡するか。連絡先。当日の約定をどうするか |
| **★基準価額の誤り・訂正** | 訂正の連絡ルート、訂正データの提供方法、**遡及訂正の手順と費用負担** |
| **分配金額の誤り** | 同上 |
| **委託会社のシステム障害** | 代替手段（FAX・メール・電話）、締め時刻の延長可否 |
| **自社のシステム障害** | 注文伝送ができない場合の代替手段、伝送期限の延長依頼先 |
| **ほふりの障害** | 相対決済への切替手順 |
| **大量解約の発生** | 解約制限の発動条件、事前連絡 |
| **繰上償還の決定** | 通知のタイミング、販売停止の手順、顧客への告知 |
| **元本割れの発生** | ★連絡ルート、顧客への説明方針、[⑬](13-compliance-ops.md)と連動 |
| 災害・BCP | 双方のBCP発動時の連絡方法 |

### エスカレーション体制表（ひな形）

| レベル | 自社 | 委託会社 | 連絡手段 | 対応時間 |
| --- | --- | --- | --- | --- |
| 通常 | 業務部 担当者 | 営業部 担当者 | メール | 営業時間内 |
| 準異常 | 業務部 役席 | 営業部 役席 | 電話＋メール | 営業時間内 |
| 異常 | 業務部長 | 部長 | 電話 | 24時間 |
| 重大 | 役員 | 役員 | 電話 | 24時間 |

> 🔍 **確認事項**：**時間外・休日の緊急連絡先**を必ず取り決めてください。障害は営業時間内に起きるとは限りません。

## 8. 販促資料・広告審査

| 項目 | 論点 |
| --- | --- |
| **資料の作成主体** | 委託会社が作るか、自社が作るか |
| **委託会社の承認** | 自社作成資料に委託会社の承認が必要か |
| **社内の広告審査** | 自社のコンプライアンス審査（[⑬](13-compliance-ops.md)） |
| **協会の規則** | 広告等の表示に関する自主規制ルールへの適合 |
| **★リードタイム** | 審査に何営業日かかるか。**リリース直前に慌てる典型例** |
| サイト掲載内容 | ファンド紹介文、リスク説明、実績表示 |
| 表示の更新 | 実績値の更新頻度と、その都度の審査要否 |

> ⚠️ **広告審査のリードタイムは、工程表に明示的に積んでください。** 「サイトの文言ができてから審査に出す」と、審査で修正が入り、修正版で再審査となり、簡単に2〜3週間が溶けます。

## 9. 苦情・問合せの連携

| 項目 | 論点 |
| --- | --- |
| 一次受付 | 自社（販売会社）が受ける |
| 委託会社へのエスカレーション基準 | 運用内容に関する質問、運用会社の判断が必要な事項 |
| 連絡ルート | 誰に、どう連絡するか |
| 回答のSLA | 何営業日以内に回答するか |
| **元本割れ・繰上償還時** | 想定問答（Q&A）を事前に共同作成しておく |
| 苦情の情報共有 | 定期的な共有の要否 |

> 💡 **想定問答（Q&A）を委託会社と共同で作っておくと、リリース後のコールセンター負荷が大きく下がります。** 特にMMFは「元本保証だと思っていた」という誤解が生じやすい商品です。[⑬](13-compliance-ops.md)と併せて準備してください。

## 10. 打合せの進め方

### 10-1. 打合せの構成（推奨）

| 回 | 時期 | 議題 | 出席者 |
| --- | --- | --- | --- |
| **第1回** | PJ開始〜2週間 | 全体スケジュール、商品性の骨子、[3節の★★項目](#3-核心-合意すべき商品性パラメータ一覧) | 企画・業務・システム |
| **第2回** | 第1回＋2週 | 商品性パラメータの詳細詰め（3節の表を全部埋める） | 同上 |
| **第3回** | 第2回＋2週 | データ授受仕様、決済スキーム | システム・業務 |
| **第4回** | — | 事務手続書のレビュー、障害時対応 | 業務 |
| **第5回** | 開発完了前 | 接続テストの計画 | システム |
| **第6回** | リリース前 | リハーサル、当日体制、Q&A | 全員 |
| 定例 | 隔週 | 課題管理、進捗共有 | PM |

### 10-2. 第1回打合せのアジェンダ（ひな形）

```
 1. 自己紹介・体制の確認（双方の窓口を明確に）
 2. プロジェクトの目的とスコープの共有
 3. マスタースケジュールのすり合わせ
    ・設定日／販売開始日（★最重要）
    ・商品審査会のスケジュール
    ・目論見書の提供時期
 4. 商品性パラメータのうち、システム設計に直結する項目の確認
    ・分配金の計算式と端数処理           （3節 #31・#32）
    ・月中解約時の経過分配金の取扱い     （3節 #36）
    ・再投資口の信託財産留保額の扱い     （3節 #26・#27）
    ・締め時刻と受渡サイクル             （3節 #12〜#15）
 5. データ授受の方式（標準フォーマットの利用可否）
 6. 決済スキーム（ほふり利用の有無）
 7. 次回までの宿題と、課題管理表の運用方法
 8. 連絡体制の確認
```

> 💡 **第1回で「4」を議題に載せるのがポイントです。** 通常、初回は挨拶と全体像で終わりがちですが、**★★項目を初回に出しておくと、相手側で検討が始まります**。回答に時間がかかる項目ほど、早く投げてください。

## 11. 課題管理の進め方

対外調整は「決まっていないこと」が多数並走します。**課題管理表を双方で共有**してください。

| 列 | 内容 |
| --- | --- |
| 課題番号 | 一意の番号 |
| 課題内容 | 何が決まっていないか |
| **影響範囲** | 決まらないと何ができないか（★これを書くと優先度が伝わる） |
| **回答期限** | いつまでに決まらないと工程に影響するか |
| ボール保持者 | 自社／委託会社／大和総研 |
| ステータス | 未着手／検討中／回答済／クローズ |
| 決定内容 | 決まった内容と決定日 |

> 💡 **「影響範囲」と「回答期限」を必ず書いてください。** 「いつでもいい質問」と「これが決まらないと開発が止まる質問」が同列に並ぶと、相手は優先順位を付けられません。詳細は[用語集の未決事項管理表](glossary.md)。
