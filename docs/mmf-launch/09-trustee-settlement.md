# ⑨ 受託会社へのデータ連携・決済インフラ — 振替制度・約定照合・残高照合

[← ⑧ 情報ベンダーへのデータ連携](08-info-vendor.md) ｜ [総合インデックス](README.md) ｜ 次 → [⑩ ソナー連携・責任分界点](10-sonar-integration.md)

「受託会社へのデータ連携」を要件として立てるとき、**最初に認識を合わせるべきことがあります。販売会社と受託会社は、通常、直接データをやり取りしません。** この構造を理解しないまま「受託会社連携」の設計に入ると、存在しない連携を設計することになります。

---

## 0. この章のゴール

1. 受託会社の役割と、販売会社との実際の距離感を正しく理解する
2. **投資信託振替制度**における自社（口座管理機関）の立場を説明できる
3. 決済スキームの選択肢と、それぞれで必要なデータ連携を設計できる
4. **残高照合（リコンサイル）** の設計と、差異発生時の調査フローを作れる

---

## 1. 【前提の整理】受託会社と販売会社の関係

### 1-1. 正規のルート

```
  ┌──────────────┐  販売会社契約   ┌──────────────┐  信託契約  ┌──────────────┐
  │ 販売会社(自社) │ ←────────────→ │  委託会社     │ ←────────→ │  受託会社     │
  │              │                 │（運用会社）   │            │（信託銀行）   │
  └──────────────┘                 └──────────────┘            └──────────────┘
         │                                 │                           │
    顧客との関係                      運用指図・基準価額算出        信託財産の保管・管理
    注文の集約                        ファンドの設定                 基準価額の照合
    口座管理                                                        分別管理

  ★契約関係は「販売会社 ⇄ 委託会社」と「委託会社 ⇄ 受託会社」の2本。
    販売会社と受託会社の間に、直接の契約関係は通常ありません。
```

> ⚠️ **したがって、「受託会社へのデータ連携」という独立した業務は、通常は存在しません。**
> 実際に設計すべきなのは、次の3つです。
>
> | 実際に設計するもの | 相手 | 節 |
> | --- | --- | --- |
> | **① 受益権の振替（振替制度）** | ほふり（証券保管振替機構） | [2節](#2-投資信託振替制度と自社の立場) |
> | **② 資金決済**（買付代金・解約代金） | 委託会社（信託口が受託会社にある） | [4節](#4-資金決済) |
> | **③ 残高照合（リコンサイル）** | ほふり／委託会社 | [5節](#5-残高照合リコンサイル) |
>
> 要件定義書では、「受託会社連携」ではなく **「決済・照合インフラ連携」** という章立てにすることを推奨します。関係者の認識がそろいます。

### 1-2. 受託会社が間接的に関わる場面

直接やり取りはしなくても、受託会社の存在を意識する必要がある場面があります。

| 場面 | 内容 |
| --- | --- |
| **買付代金の払込先** | 信託財産は受託会社（信託銀行）に開設された**信託口**で管理される。振込先口座の名義に受託会社名が入る |
| **基準価額の照合** | 委託会社の算出値を受託会社が照合する。**ここで不一致があると基準価額の確定が遅れる**（[⑬](13-compliance-ops.md)の障害対応） |
| 分別管理の確認 | 信託財産が受託会社の固有財産と分別管理されていること |
| 受託会社の変更 | 信託契約の変更。約款変更として顧客への通知が必要になる |

> 🔍 **確認事項**：委託会社に対し、①買付代金の振込先口座情報、②受託会社名、③基準価額の照合プロセスと確定時刻を確認してください（[⑦](07-management-company.md)の合意事項に含める）。

## 2. 投資信託振替制度と自社の立場

### 2-1. 制度の構造

投資信託の受益権は、**振替口座簿への電子的な記録**によって管理されます（ペーパーレス）。

```
  ┌────────────────────────────────────────┐
  │  振替機関：証券保管振替機構（ほふり）    │
  └───────────────┬────────────────────────┘
                  │
      ┌───────────┴───────────┐
      │                       │
  ┌───▼────────────┐    ┌────▼───────────┐
  │ 口座管理機関    │    │ 口座管理機関    │
  │ ＝販売会社(自社)│    │ ＝他の販売会社  │
  └───┬────────────┘    └────────────────┘
      │
  ┌───▼──────────┐
  │ 顧客の振替口座 │  ← ここに受益権の数量が記録される
  └──────────────┘

  発行者 ＝ 委託会社
```

**自社の立場は「口座管理機関」** です。顧客の振替口座を管理し、受益権の増減を記録する責任を負います。

### 2-2. 要件定義上の含意

| 論点 | 内容 |
| --- | --- |
| **新銘柄の取扱開始手続** | ほふりに対する銘柄の取扱開始の手続が必要か。**要確認** |
| **振替口座簿の記録** | 買付・解約・再投資による数量の増減を記録する。ソナーが担う |
| **顧客口座の開設** | 既存の振替口座に相乗りできるか（他の投信を保有していれば既存口座がある） |
| **★再投資による数量増加** | 月末再投資で受益権が増える。**これも振替の対象**。記録漏れがないか |
| 他社への移管 | 他の証券会社への移管（振替）への対応 |
| 相続・贈与 | 振替による名義変更 |

> 🔍 **確認事項（2件）**
> - **ほふり／委託会社へ**：新規設定ファンドの取扱いを開始するにあたり、口座管理機関として必要な手続と、そのリードタイム
> - **大和総研へ**：振替制度に係る記録・報告がソナーの標準機能でカバーされるか。**月末再投資による数量増加の記録**が正しく処理されるか

## 3. 決済スキームの選択

### 3-1. 2つの選択肢

| 方式 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| **A. 標準の決済インフラを利用** | ほふりが提供する投信の決済・照合の仕組みを使う | 標準化されており、**ソナーの標準機能が対応している可能性が高い** | 利用要件・費用の確認が必要 |
| **B. 相対（直接）決済** | 委託会社と直接、データ授受と資金振込を行う | 小規模なら簡易 | ★**照合が手作業になりやすい**。件数が増えると破綻する |

> 💡 **推奨はA（標準インフラの利用）です。** 理由は2つ。
> 1. **ソナーの標準機能に乗りやすい**（＝アドオン回避）。共同利用型システムは業界標準の処理に最適化されています
> 2. **照合が自動化される**。相対決済は、件数が少ないうちは回りますが、増えると必ず人手の限界が来ます
>
> 🔍 **確認事項**：①自社が既に当該インフラを利用しているか、②利用していない場合の加入手続とリードタイム、③委託会社側が対応しているか。**この3点を[⑦](07-management-company.md)の第1回打合せで確認してください。** 決済方式が決まらないと、[④](04-order-correction-cancel.md)の締め時刻も決められません。

### 3-2. どちらを選んでも決めること

| 項目 | 内容 |
| --- | --- |
| 約定照合のタイミング | 締め後、何時までに照合するか |
| 資金決済のタイミング | 受渡日の何時に資金が動くか |
| **ネッティング** | 同日の買付と解約を相殺するか。相殺後の差額のみ決済するか |
| 資金の過不足 | 不足時の対応、資金繰りの管理（[③](03-internal-documents.md)） |
| 決済不履行時 | フェイル時の手続と責任 |
| 締め時刻 | ★[④ 2節](04-order-correction-cancel.md#2-取引サイクルと締め時刻カットオフ設計)の4タイムラインに反映 |

## 4. 資金決済

### 4-1. 資金の流れ

```
【買付（設定）】
  顧客の預り金 ──→ 自社 ──→ 委託会社経由 ──→ 信託口（受託会社）
                             または直接
  ★受渡日に、自社から資金が出ていく

【解約】
  信託口（受託会社）──→ 委託会社経由 ──→ 自社 ──→ 顧客の預り金
                        または直接
  ★受渡日に、自社に資金が入ってくる

【ネッティングする場合】
  当日の買付総額と解約総額を相殺し、差額のみを決済
```

### 4-2. 資金繰り管理の要件

| 要件 | 内容 |
| --- | --- |
| **決済予定額の把握** | 翌営業日に必要な資金額を、当日の締め後に把握する |
| 資金繰り表 | [③ 2節](03-internal-documents.md#2-オペレーション帳票日次)の日次帳票 |
| **大口取引の事前把握** | 大口の買付・解約が入った場合の早期アラート |
| 資金不足時の手当 | 調達手段と手続 |
| 決済照合 | 予定額と実績額の突合 |

> ⚠️ **MMFは「即日性」が売りの商品です。** 大口の解約が突然入ると、当日または翌営業日に資金を用意する必要があります。**大口取引のアラート閾値**を設定し、資金部門に即座に連携する仕組みを要件に入れてください。

## 5. 残高照合（リコンサイル）

**ここが、この章で最も実務的に重要な部分です。**

### 5-1. 何と何を照合するのか

| # | 照合 | 目的 | 頻度 |
| --- | --- | --- | --- |
| **1** | 自社の顧客別残高合計 ⇔ 自社の銘柄別残高 | 内部整合 | 日次 |
| **2** | 自社の銘柄別残高 ⇔ **ほふりの振替口座簿** | 制度上の残高一致 | 日次 |
| **3** | 自社の銘柄別残高 ⇔ **委託会社の記録** | 発行者との一致 | 日次／月次 |
| **4** | 自社の約定 ⇔ 委託会社の約定 | 取引の一致 | 日次 |
| **5** | 自社の決済予定 ⇔ 実際の資金移動 | 資金の一致 | 受渡日 |
| **6** | 自社の分配金計算 ⇔ 委託会社の分配金額 | ★**MMF固有・最重要** | 日次 |

> ⚠️ **照合6が、MMFで最も差異が出やすい箇所です。** [⑤ 3節](05-distribution-reinvestment.md#3-最重要端数処理の設計)の端数処理が委託会社と1桁でも違うと、**毎日わずかな差異が出続けます**。しかも金額が小さいため見過ごされやすく、月末の再投資で顕在化します。
> **日次の照合項目に「分配金額の一致」を必ず入れてください。**

### 5-2. 照合の設計

| 観点 | 決めること |
| --- | --- |
| **照合のタイミング** | 夜間バッチのどこで実行するか |
| **照合データの入手** | ほふり／委託会社から、いつ・どの形式で受け取るか |
| **照合の粒度** | 銘柄合計／顧客別／取引明細 |
| **許容差異** | 端数レベルの差異を許容するか。**閾値の設定** |
| **差異の検知** | 自動検知とアラート |
| **★調査の期限** | 翌営業日の何時までに原因を特定するか |
| 未解消差異の管理 | 当日中に解消しない差異の管理台帳 |
| エスカレーション | 一定金額・一定日数を超えた場合の報告先 |

### 5-3. 差異発生時の調査フロー

```
 1. 差異の検知（夜間バッチのリコンサイル）
        ↓
 2. 差異の分類
    ┌─ 数量の差異か、金額の差異か
    ├─ 特定の顧客か、全体か
    └─ 端数レベルか、明らかに大きいか
        ↓
 3. 原因の切り分け
    ┌─ 未反映の取引はないか（タイミング差）
    ├─ 訂正・取消の反映漏れはないか
    ├─ 端数処理の差か（[⑤ 3節]）
    ├─ 相手方のデータ誤りか
    └─ 自社のシステム不具合か
        ↓
 4. 対応
    ┌─ タイミング差 → 翌日解消を確認
    ├─ 端数処理の差 → 計算方法の見直し（[⑦]で委託会社と調整）
    ├─ 相手方の誤り → 委託会社へ連絡・訂正依頼
    └─ 自社の不具合 → 修正＋[④ 6節]の事故訂正フローへ
        ↓
 5. 記録
    ・差異の内容、原因、対応、解消日を台帳に記録
    ・再発防止策
```

> 💡 **「タイミング差」と「真の差異」を自動で切り分ける仕組みを作ってください。** 大半の差異はタイミング差（自社では反映済みだが相手方は翌日反映、など）です。これを毎回人間が判断していると、業務が回りません。**既知のタイミング差パターンを定義し、自動で除外する**設計にすると、調査対象が劇的に減ります。

## 6. 障害時の代替手段

| 事象 | 代替手段 | 決めること |
| --- | --- | --- |
| **決済インフラの障害** | 相対決済への切替 | 切替の判断基準、手順、連絡先 |
| **自社システムの障害** | 手作業でのデータ作成・送信 | 手順書、権限、上限件数 |
| **委託会社の障害** | FAX・メールでの連絡 | 様式、送付先、受領確認 |
| **通信回線の障害** | 代替回線、媒体受渡 | — |
| **照合データの未着** | 翌日に持ち越すか、暫定処理するか | 判断基準 |

> ⚠️ **「手作業でやる」を代替手段にする場合、その手順書を事前に作り、訓練してください。** 障害当日にゼロから手順を考えるのは不可能です。[⑬ BCP](13-compliance-ops.md)と併せて準備します。

### 大和総研への質問リスト（決済・照合編）

1. 投資信託の決済について、標準で対応している決済インフラ・決済方式を教えてください
2. 相対（直接）決済にも対応していますか。その場合の運用負荷はどの程度ですか
3. 投資信託振替制度に係る記録・報告は標準機能でカバーされますか
4. **月末再投資による受益権の数量増加**は、振替制度上どう記録されますか
5. **リコンサイル（残高照合）機能**は標準で提供されますか。照合対象は何と何ですか
6. **日次の分配金額の照合**（委託会社の計算値との突合）は標準で行われますか
7. 差異検知時のアラートと、差異管理台帳の機能はありますか
8. 既知のタイミング差を自動除外する仕組みはありますか
9. ネッティング（買付と解約の相殺）に対応していますか
10. 障害時に手作業でデータを作成・投入する手順は用意されていますか

## 8. この章のチェックリスト

- [ ] **「販売会社と受託会社は直接データ連携しない」**という構造を関係者で共有した
- [ ] 要件定義書の章立てを「決済・照合インフラ連携」に整理した
- [ ] 買付代金の振込先（信託口）と受託会社名を委託会社に確認した
- [ ] 基準価額の照合プロセスと確定時刻を確認した
- [ ] **投資信託振替制度における自社の立場（口座管理機関）**と必要な手続を確認した
- [ ] 新銘柄の取扱開始にあたっての、ほふりへの手続とリードタイムを確認した
- [ ] **決済スキーム（標準インフラ／相対）を決定**し、締め時刻に反映した
- [ ] ネッティングの有無を決定した
- [ ] 資金繰り管理の要件と、**大口取引のアラート閾値**を定義した
- [ ] **リコンサイルの照合6項目**を定義した

- [ ] 許容差異の閾値と、調査の期限を定めた
