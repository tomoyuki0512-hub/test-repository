# ⑫ 証券サイト（フロント）・非機能要件 — 画面・表示・性能・可用性

[← ⑪ 口座・税制・NISA](11-tax-nisa-account.md) ｜ [総合インデックス](README.md) ｜ 次 → [⑬ コンプライアンス・運用・障害対応](13-compliance-ops.md)

顧客が触れるのはこの層だけです。**バックでどれだけ正確に処理していても、画面の表示が誤解を招けば苦情になります。** また、MMFは「月末」「締め時刻直前」という明確なピークを持つ商品であり、非機能要件の設計が読みやすい反面、外すと確実に事故になります。

---

## 0. この章のゴール

1. 必要な画面を列挙し、MMF固有の表示項目を設計できる
2. **注文フローの必須ステップ**（目論見書交付・適合性確認）を組み込める
3. MMFのピーク特性を踏まえた性能要件を設定できる
4. **バッチウィンドウとサービス提供時間の関係**を設計できる

### 1-1. 必要な画面

| # | 画面 | 内容 | 新規／既存改修 |
| --- | --- | --- | --- |
| **情報提供** |
| 1 | ファンド一覧・検索 | 取扱商品の一覧。**NISA絞込みで出ないこと**（[⑪](11-tax-nisa-account.md)） | 既存改修 |
| 2 | **ファンド詳細** | 基準価額、**平均利回り**、費用、リスク、目論見書 | 既存改修 or 新規 |

| 6 | **適合性確認** | 投資経験・リスク許容度 | 既存改修 |
| 7 | 買付注文入力 | 金額／口数、口座区分 | 新規 or 改修 |
| 8 | **買付注文確認** | ★費用・リスクの最終確認 | 新規 or 改修 |
| 9 | 買付注文完了 | 受付番号、約定予定日 | 新規 or 改修 |
| **解約フロー** |
| 10 | 解約注文入力 | 口数／全部解約 | 新規 or 改修 |
| 11 | **解約注文確認** | ★**信託財産留保額**・**未収分配金**の明示 | 新規 or 改修 |
| 12 | 解約注文完了 | 受付番号、入金予定日 | 新規 or 改修 |
| **照会・管理** |
| 13 | 保有残高照会 | 口数、評価額、**未収分配金** | 既存改修 |
| 14 | 注文照会 | 注文状態、訂正・取消 | 既存改修 |
| 15 | 取引履歴 | 買付・解約・**再投資** | 既存改修 |
| 16 | 電子交付書面の閲覧 | 帳票の閲覧・ダウンロード | 既存改修 |
| 17 | 電子交付の同意設定 | 同意・撤回 | 既存 |
| **その他** |
| 18 | よくある質問（FAQ） | ★MMF専用のQ&A | 新規 |
| 19 | お知らせ | 販売開始、障害情報、繰上償還等 | 既存 |

> 💡 **既存の投信画面を流用するか、MMF専用に作るかは重要な判断です。**
> - **流用**：開発コストは低いが、株式投信向けの表示項目（騰落率・シャープレシオ等）がMMFでは無意味になる
> - **専用**：顧客に分かりやすいが、開発コストが増える
>
> **推奨は「流用＋MMF用の表示項目セットを切替」**です。画面は共通でも、表示する指標を商品分類で出し分けます。

### 1-2. 買付フローの画面遷移

```
  ファンド詳細
      │
      ▼
  【目論見書の表示】 ← ★スキップ不可。交付記録を残す
      │
      ▼ 「内容を確認しました」
  【適合性確認】     ← ★未実施なら必須。実施済みなら省略可
      │
      ▼
  買付注文入力（金額／口数、口座区分）
      │              ★口座区分にNISAを出さない
      ▼
  【買付注文確認】   ← ★費用・リスク・元本保証でない旨を明示
      │
      ▼ 取引パスワード等
  買付注文完了       ← 受付番号、約定予定日、取消方法の案内
```

## 2. 【MMF固有】表示項目の設計

### 2-1. 株式投信と同じにしてはいけない項目

| 項目 | 株式投信 | **MMF** |
| --- | --- | --- |
| **主要指標** | 騰落率（1年・3年・5年） | ★**平均利回り（7日間等）**（[⑧ 4節](08-info-vendor.md#4-mmf特有平均利回りの表示)） |
| 基準価額チャート | 値動きが見える | ★ほぼ平坦。**縦軸のスケールに注意**（微小な変動が誇張されないように） |
| リスク指標 | 標準偏差・シャープレシオ | ★意味を持ちにくい。表示を省くか、注記を付ける |
| 分配金 | 決算期ごと | ★**日々計上・月末再投資**である旨の説明 |
| **未収分配金** | — | ★**MMF固有の表示項目** |
| NISA | 対象／対象外 | ★**「対象外」を明示** |

> ⚠️ **基準価額チャートの縦軸に注意してください。** 10,000円〜10,001円の範囲を自動スケールで描くと、**わずか1円の動きが急騰・急落のグラフに見えます**。顧客の誤認を招くため、**縦軸の範囲を固定する**などの配慮が必要です。デザイン段階で必ず検討してください。

### 2-2. 必ず表示すべき注意喚起

| 場所 | 内容 |
| --- | --- |
| ファンド詳細 | **元本保証ではない旨**。過去に元本割れ事例があること |
| ファンド詳細 | **NISA対象外**である旨 |
| ファンド詳細 | 預金保険の対象外である旨 |
| ファンド詳細 | 費用（信託報酬・信託財産留保額） |
| **解約確認画面** | ★**信託財産留保額が発生する旨と金額**（[④](04-order-correction-cancel.md)） |
| **解約確認画面** | ★**未収分配金の精算方法** |
| 平均利回りの表示箇所 | 過去の実績であり将来を保証しない旨 |

> ⚠️ **リスク注記を小さく表示するのは典型的な指摘事項です。** 利回りを大きく、リスクを小さく表示していないか、**デザイン段階でコンプライアンスのレビューを入れてください**（[⑬](13-compliance-ops.md)）。

### 2-3. 「未収分配金」の見せ方

[⑤ 7節](05-distribution-reinvestment.md#7-顧客への表示要件)で扱った論点の、画面側の設計です。

```
 【保有残高画面の表示例】

   ○○MMF
   ┌────────────────────────────────────┐
   │ 保有口数        1,234,567 口        │
   │ 基準価額        10,000 円（1万口あたり）│
   │                 （2026年9月15日現在）  │ ← ★日付を必ず併記
   │ 評価額          1,234,567 円         │
   │ ─────────────────────────────────  │
   │ 未収分配金 ⓘ        123 円          │ ← ★MMF固有
   │  └ 今月分の分配金です。月末最終営業日に│
   │    税金を差し引いた後、自動的に再投資され│
   │    保有口数が増えます                  │
   └────────────────────────────────────┘
```

> 💡 **ツールチップ（ⓘ）での説明を必ず付けてください。** 「未収分配金」は一般の顧客には馴染みのない用語です。説明がないと問合せが増えます。**コールセンターの負荷削減効果が、実装コストを上回ります。**

## 3. 注文フローのUX設計

### 3-1. 顧客に取消させる設計

[④ 3節](04-order-correction-cancel.md#3-注文の状態遷移ステートマシン)で述べたとおり、**締め前に顧客自身に直してもらうのが最もコストが低い**です。

| 設計 | 内容 |
| --- | --- |
| **取消期限の明示** | 完了画面に「◯時◯分まで取消できます」と表示 |
| **注文照会からの取消** | 分かりやすい場所に取消ボタン |
| **確認画面の充実** | 誤りに気づける情報量（金額・口座区分・費用） |
| **受付完了メール** | 注文内容と取消方法を記載 |

### 3-2. 締め時刻まわりのUX

| 事象 | 設計 |
| --- | --- |
| 締め時刻の表示 | ★常時表示。「本日15:00までのご注文は本日約定」 |
| **締め直前の注文** | 残り時間の表示。「あと5分」 |
| **締め時刻をまたいだ場合** | ★入力中に締め時刻を過ぎたらどうするか。**確認画面で再判定が必要** |
| 締め後の注文 | 「翌営業日扱い」と明示して受け付けるか、受付不可にするか |
| 非営業日 | 次の営業日を明示 |

> ⚠️ **「入力中に締め時刻を過ぎる」ケースを必ず設計してください。** 14:59に確認画面を出し、15:01に確定ボタンを押す顧客がいます。**確認画面の内容（約定予定日）と実際の約定日がずれる**ため、確定時に再判定し、変わっていれば再確認を求める設計が必要です。

### 3-3. 適合性確認

| 論点 | 設計 |
| --- | --- |
| 実施のタイミング | 初回買付時／有効期限切れ時 |
| 既存の確認結果の流用 | 他商品で確認済みなら省略できるか |
| **MMFのリスク区分** | 社内のリスク区分で何に該当するか。★コンプラと確認 |
| 不適合時の扱い | 買付不可とするか、警告のうえ受け付けるか |
| 高齢顧客 | 社内の高齢者ルールの適用要否 |

## 4. 非機能要件：性能

### 4-1. MMFのピーク特性

**MMFはピークが読みやすい商品です。** これは設計上の強みです。

| ピークの種類 | いつ | 何が起きるか |
| --- | --- | --- |
| **① 締め時刻直前** | 毎営業日の締め前30分 | 注文の集中 |
| **② 月末（再投資日）** | 月末最終営業日の夜 | ★**バッチのピーク**。オンラインではない |
| **③ 月初（再投資後）** | 月末翌営業日の朝 | ★**残高照会の集中**（口数が増えたか確認） |
| **④ 給料日・賞与日** | 25日前後、6月・12月 | 買付の増加 |
| **⑤ 金利イベント後** | 金融政策の発表後 | ★**平均利回りへの関心が高まる**。ファンド詳細へのアクセス集中 |
| **⑥ 販売開始直後** | リリース後の数日 | ★**最大の未知数**。プロモーション次第 |

> 💡 **⑤は他の投信にない特性です。** MMFは短期金利に連動するため、**金融政策の変更が報道されると、利回りを確認しに来る顧客が急増**します。この経路（ファンド詳細画面）の性能を特に確保してください。

### 4-2. 性能要件の設定

| 項目 | 決めること |
| --- | --- |
| **同時接続数** | 平常時／ピーク時 |
| **応答時間** | 画面ごとの目標値（例：照会系3秒以内、注文系5秒以内） |
| **スループット** | 秒間注文件数のピーク |
| **ソナーIFの応答時間** | ★[⑩ 5節](10-sonar-integration.md#5-インターフェースif一覧)のSLA。**ここがボトルネックになりやすい** |
| 性能試験の条件 | どのピークを想定して試験するか |
| **キャパシティ計画** | 口座数が◯倍になった場合の想定 |

> ⚠️ **フロントの性能は、ソナーのIF応答時間に律速されます。** フロント側をいくら速くしても、ソナーへの照会が遅ければ意味がありません。**IF応答時間のSLAを大和総研と合意し、それを前提に性能設計してください。**

### 4-3. 対策の選択肢

| 対策 | 適用箇所 | 注意 |
| --- | --- | --- |
| **キャッシュ** | 商品情報、基準価額 | ★**残高・余力はキャッシュしない**（誤表示になる） |
| 静的コンテンツのCDN配信 | 目論見書PDF、画像 | — |
| **負荷分散** | アプリケーションサーバ | — |
| 待機列（順番待ち） | 締め直前の集中時 | UXが悪いが、落ちるよりまし |
| **縮退運転** | 障害時 | [7節](#7-縮退運転) |

## 5. 非機能要件：可用性

| 項目 | 決めること |
| --- | --- |
| **サービス提供時間** | 何時から何時まで。★バッチ時間との関係（[6節](#6-バッチウィンドウとサービス提供時間)） |
| 稼働率目標 | 計画停止を除く稼働率 |
| **RTO（目標復旧時間）** | 障害から何分で復旧するか |
| **RPO（目標復旧時点）** | どこまでのデータを保全するか。★**注文データは失ってはならない** |
| 冗長化 | サーバ・ネットワーク・データベース |
| **災害対策** | BCPサイトの要否（[⑬](13-compliance-ops.md)） |
| 計画停止 | 定期メンテナンスの時間帯と告知 |

> ⚠️ **注文データのRPOは実質ゼロです。** 「顧客が注文したのにデータが消えた」は絶対に許されません。**注文の永続化と、ソナーへの到達確認**を確実に設計してください（[④ 8節](04-order-correction-cancel.md#8-二重発注防止と冪等性)）。

## 6. バッチウィンドウとサービス提供時間

**ここが、MMFプロジェクトで最も設計が難しい非機能要件です。**

### 6-1. 何が問題か

```
  【通常日】
   7:00 ─────────── オンライン ─────────── 20:00
                                              │
                                        夜間バッチ開始
                                              │
                                        （残高更新・分配金計上・
                                          リコンサイル・帳票生成）
                                              │
   翌7:00 ← バッチ完了 ───────────────────────┘

  【月末最終営業日】
   7:00 ─────────── オンライン ─────────── 20:00
                                              │
                                        夜間バッチ開始
                                              │
                                        ★通常処理に加えて
                                          ・分配金確定・源泉徴収
                                          ・月末一括再投資（全口座）
                                          ・月末残高確定
                                          ・月次帳票生成
                                              │
   翌?:00 ← ★バッチ完了が遅れると、翌朝のオンライン開始に間に合わない
```

### 6-2. 決めること

| # | 論点 | 内容 |
| --- | --- | --- |
| **1** | **オンライン提供時間** | 何時から何時まで |
| **2** | **バッチウィンドウ** | バッチに使える時間帯 |
| **3** | **月末・年末の想定処理時間** | ★口座数から試算。大和総研に実績値を確認 |
| **4** | **バッチ延伸時の対応** | オンライン開始を遅らせるか、縮退で開始するか |
| **5** | バッチ中の照会可否 | 参照系だけでも提供できるか |
| **6** | **顧客への告知** | メンテナンス時間の事前告知 |
| **7** | 24時間化の要否 | ★将来的な要求。今の設計で対応可能か |

> 🔍 **大和総研への確認（再掲）**：MMF保有口座数が◯万口座に達した場合の、月末バッチの想定処理時間。**この数字がないと、バッチウィンドウが設計できません。**

> 💡 **「月末の翌朝はオンライン開始を1時間遅らせる」という運用も、選択肢として検討する価値があります。** 無理に通常どおり開始して失敗するより、**あらかじめ告知して遅らせるほうが顧客への影響は小さい**です。

## 7. 縮退運転

障害時に「全部止める」か「一部だけ提供する」かを、あらかじめ決めておきます。

| 障害 | 縮退の内容 | 判断基準 |
| --- | --- | --- |
| **ソナーの障害** | 注文受付を停止。**照会は最終更新データで提供** | 注文がソナーに届かない以上、受け付けてはいけない |
| **基準価額の未着** | 基準価額の表示を「取得中」に。★**注文受付の可否を要判断** | [④ 10節](04-order-correction-cancel.md#10-例外エラーパターン一覧) |
| **情報ベンダーの障害** | チャート・参考情報を非表示。取引機能は継続 | 取引に必須でない情報は落としてよい |
| **帳票システムの障害** | 電子交付の閲覧のみ停止。取引は継続 | — |
| フロントの部分障害 | 該当機能のみ停止 | — |

> ⚠️ **「注文受付を停止する」判断基準を事前に決めてください。** 障害発生時に「受け付けてよいか」を現場で議論すると、その間に受け付けた注文が宙に浮きます。
> **原則：ソナーへの到達が保証できない状態では、注文を受け付けない。**

| 縮退時に必要なもの | 内容 |
| --- | --- |
| **告知の仕組み** | サイト上部のお知らせ、メンテナンス画面 |
| 告知文のテンプレート | 事前に用意しておく（障害当日に書く時間はない） |
| 判断者・判断基準 | 誰が縮退を判断するか |
| 復旧手順 | 縮退解除の手順と確認項目 |

## 8. セキュリティ

| 項目 | 内容 |
| --- | --- |
| **認証** | ログイン認証、多要素認証 |
| **取引認証** | 注文確定時の取引パスワード等 |
| 通信の暗号化 | TLS |
| **不正取引の検知** | 普段と異なる操作パターン、出金先の変更直後の大口解約 |
| セッション管理 | タイムアウト、同時ログインの制御 |
| **操作ログ・監査証跡** | 誰が・いつ・何をしたか。★法定帳簿とも関連（[③](03-internal-documents.md)） |
| 権限管理 | オペレータ画面がある場合の権限設計 |
| 脆弱性診断 | リリース前の診断実施 |
| **業界基準への適合** | 金融機関向けのセキュリティ基準への適合確認 |

> 🔍 **確認事項**：自社が準拠しているセキュリティ基準（金融業界の安全対策基準等）において、**新規サービス追加時に必要な確認・申請**があるか。社内のセキュリティ部門に早期に確認してください。**診断のリードタイムが工程に効きます。**

## 9. アクセシビリティ・マルチデバイス

| 項目 | 内容 |
| --- | --- |
| **スマートフォン対応** | ★主要な利用デバイス。レスポンシブか専用画面か |
| タブレット対応 | — |

## 10. 監視・ログ

| 監視対象 | 内容 | 通知先 |
| --- | --- | --- |
| サービス死活 | 画面が表示されるか | システム |
| **注文APIの応答時間** | SLA超過の検知 | システム |
| **注文の滞留** | ソナーへ未到達の注文 | ★業務部・システム |
| エラー率 | 一定率超過 | システム |
| **基準価額の鮮度** | 更新が止まっていないか | 業務部 |
| **締め時刻前の負荷** | 締め直前の集中 | システム |
| バッチの実行状況 | 開始・完了・遅延 | システム・業務部 |
| セキュリティイベント | 不正ログイン試行等 | セキュリティ |

> ⚠️ **「注文の滞留」の監視を必ず入れてください。** フロントで受け付けたがソナーに届いていない注文があると、顧客は「注文した」と思っているのに処理されません。**締め時刻前に検知して手当てする必要があります。**
