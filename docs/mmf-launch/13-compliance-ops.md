# ⑬ コンプライアンス・運用・障害対応 — 商品審査・規程改定・元本割れへの備え

[← ⑫ 証券サイト・非機能要件](12-web-nonfunctional.md) ｜ [総合インデックス](README.md) ｜ 次 → [⑭ テスト・移行・リリース](14-test-release.md)

システムができても、**商品審査が通らなければ売れません**。また、MMFには **過去に元本割れが発生した実績** があります。「起きない前提」で作ると、起きたときに業務が完全に止まります。本章は、その両方に備えるための章です。

---

## 0. この章のゴール

1. 商品審査・広告審査のリードタイムを工程に正しく織り込める
2. 改定すべき社内規程・マニュアルを漏れなく列挙できる
3. 日次の運用手順と障害対応を設計できる
4. **元本割れ・繰上償還という「有事」の手順**を事前に用意できる

## 2. 商品審査プロセス

### 2-1. 典型的な流れ

```
  1. 商品の提案（企画部門）
        ↓
  2. 委託会社へのデューデリジェンス
     ・運用体制、リスク管理体制、コンプライアンス体制
     ・（既存取引先なら簡略化できる場合あり）
        ↓
  3. 商品審査資料の作成
     ・商品性、リスク、想定顧客層、適合性の考え方
     ・費用、収益見込み
     ・★システム対応の実現性（本プロジェクトの状況）
        ↓
  4. ★商品審査会への付議          ← 開催頻度に律速される
        ↓
  5. 審査・指摘事項への対応
        ↓
  6. 取扱開始の決裁
        ↓
  7. 販売開始
```

### 2-2. リードタイムの確認

> ⚠️ **ここがクリティカルパスになるケースが非常に多いです。**
>
> | 確認事項 | 例 |
> | --- | --- |
> | 商品審査会の**開催頻度** | 月1回／隔月 |
> | 資料の**提出期限** | 開催の2週間前 |
> | 審査の**やり直し**が発生した場合 | 次回開催まで待つ＝1か月遅延 |
> | 決裁のプロセス | 審査会の後、経営会議など |
>
> ```
>  販売開始日：X月1日
>       ↑
>  取扱開始の決裁：遅くともX-1月中
>       ↑
>  商品審査会：X-1月の開催回（月1回）
>       ↑
>  資料提出：審査会の2週間前
>       ↑
>  ★商品性の確定：資料提出の前
>       ↑
>  ★つまり、販売開始の2か月前には商品性が固まっている必要がある
> ```
>
> **[⑩ 8節](10-sonar-integration.md#8-リリース枠とスケジュール)のリリース枠からの逆算と併せて、両方の制約を満たす工程表を作ってください。**

### 2-3. 審査で問われること（事前に準備）

| 論点 | 準備すべき回答 |
| --- | --- |
| 想定顧客層 | どのような顧客に、どういうニーズで販売するか |
| **適合性の考え方** | MMFは社内のリスク区分で何に該当するか |
| **元本割れリスクの説明** | ★過去の事例を踏まえ、どう説明するか |
| 費用の妥当性 | 信託報酬・信託財産留保額の水準 |
| **NISA対象外** | 顧客への説明方法（[⑪](11-tax-nisa-account.md)） |
| 収益見込み | 代行手数料収入 vs コスト（★郵送コストを含む。[⑥](06-prospectus-delivery.md)） |
| **システム対応の実現性** | 本プロジェクトの進捗と、リリース可能性 |
| 苦情の想定 | 想定される苦情と対応方針 |
| モニタリング体制 | 販売後のモニタリング（[③ 4節](03-internal-documents.md#4-コンプライアンスモニタリング帳票)） |

## 3. 顧客本位の業務運営と広告審査

### 3-1. 顧客本位の観点で整理すべきこと

| 論点 | 内容 |
| --- | --- |
| **商品の位置づけ** | 誰にとって、どういう価値がある商品か |
| **重要情報シート** | 作成の要否と内容 |
| **費用の明示** | 信託報酬・信託財産留保額を分かりやすく |
| **リスクの明示** | ★元本保証でない旨。MMFは特に誤解されやすい |
| **電子交付必須化の是非** | ★デジタルに不慣れな顧客の排除にならないか（[⑥ 5節](06-prospectus-delivery.md#5-未同意者の扱い買付制御)） |
| 短期解約の抑止 | 信託財産留保額の存在を、買付時に分かりやすく伝える |

### 3-2. 広告審査

| 項目 | 内容 |
| --- | --- |
| 審査対象 | サイトの文言、バナー、メール、パンフレット |
| **審査のリードタイム** | ★何営業日かかるか。修正の再審査も見込む |
| 委託会社の承認 | 自社作成資料に承認が必要か（[⑦](07-management-company.md)） |
| **実績値の表示** | 平均利回りの表示方法（[⑧ 4節](08-info-vendor.md#4-mmf特有-平均利回りの表示)） |
| リスク表示の要件 | 文字サイズ、配置 |
| 表示の更新 | 実績値の更新時に再審査が必要か |

> ⚠️ **広告審査は工程の最後に来がちで、そこで詰まります。**
> **対策**：画面のワイヤーフレーム段階でコンプライアンスにレビューしてもらい、**文言の骨子を早期に固めてください。** 完成品を審査に出すのではなく、途中段階で相談するほうが速く終わります。

## 6. 障害対応

### 6-1. 障害パターンと対応の一覧

| # | 障害 | 影響 | 一次対応 | 判断者 |
| --- | --- | --- | --- | --- |
| 1 | **フロント（自社Web）の障害** | 注文受付不可 | 告知・縮退（[⑫ 7節](12-web-nonfunctional.md#7-縮退運転)） | システム部長 |
| 2 | **ソナーの障害** | 注文・照会不可 | ★**注文受付停止**。大和総研へ連絡 | システム部長 |
| 3 | **フロント〜ソナー間の通信断** | 注文が到達しない | 注文受付停止。滞留注文の確認 | システム部長 |
| 4 | **基準価額の未着** | 約定できない | [6-2節](#6-2-基準価額が届かない) | 業務部長 |
| 5 | **基準価額の誤り・訂正** | 約定済み取引が誤り | [6-3節](#6-3-基準価額が訂正された) | 業務部長・コンプラ |
| 6 | **分配金額の未着・誤り** | 分配計算できない | 委託会社へ連絡 | 業務部長 |
| 7 | **委託会社のシステム障害** | 注文伝送不可 | 代替手段（[⑦ 7節](07-management-company.md#7-障害時異常時の取り決め)） | 業務部長 |
| 8 | **決済インフラの障害** | 決済不可 | 相対決済への切替（[⑨ 6節](09-trustee-settlement.md#6-障害時の代替手段)） | 業務部長 |
| 9 | **情報ベンダーの障害** | 参考情報が出ない | 該当箇所を非表示。取引は継続 | システム |
| 10 | **夜間バッチの失敗** | 翌日の業務に影響 | リラン。翌朝の開始遅延を判断 | システム部長 |
| 11 | **月末再投資バッチの失敗** | ★全顧客に影響 | [6-4節](#6-4-月末再投資バッチが失敗した) | 業務部長・役員 |
| 12 | 帳票出力の失敗 | 交付遅延 | 再出力。交付期限の確認 | 業務部 |
| 13 | 災害・広域障害 | 全業務 | BCP発動 | 経営 |

### 6-2. 基準価額が届かない

```
 【手順】
  1. 所定時刻を過ぎても未着 → 委託会社へ連絡（エスカレーション表に従う）
  2. 到着見込みを確認
       ├─ 当日中に届く見込み → 待機。約定処理を遅らせる
       └─ 当日中に届かない  → ★業務判断
  3. 当日中に届かない場合の選択肢（★事前に決めておく）
       ├─ 当日の注文を翌営業日扱いにする
       ├─ 前日の基準価額で仮約定し、後日精算する
       └─ 注文受付を停止する
  4. 顧客への告知
  5. 復旧後の処理（約定計算、帳票、決済）
```

> ⚠️ **手順3の選択肢を、事前に委託会社と合意しておいてください。** 障害当日に「どうしますか」と相談していると、時間だけが過ぎます。[⑦ 7節](07-management-company.md#7-障害時異常時の取り決め)の取り決めに含めます。

### 6-3. 基準価額が訂正された

```
 【手順】
  1. 委託会社から訂正の連絡を受領
  2. 影響範囲の特定
       ・どの日の基準価額か
       ・その日以降の約定は何件か、顧客は何名か
       ・分配金・再投資に影響するか
       ・帳票は交付済みか
       ・税額に影響するか
  3. 対応方針の決定（業務部長・コンプラ・必要に応じて経営）
  4. 再計算処理（[④ 6節](04-order-correction-cancel.md#6-受渡後の誤り事故訂正)の事故訂正フロー）
  5. 顧客への通知・帳票の再発行
  6. 差額の精算（顧客が不利益を被る場合の対応）
  7. 事故報告・当局報告の要否をコンプラが判断
```

> ⚠️ **「基準価額の訂正」は、遡及訂正機能がないと業務が止まります。** [⑩](10-sonar-integration.md)の質問12・16で、ソナーの遡及訂正機能を必ず確認してください。

### 6-4. 月末再投資バッチが失敗した

**全顧客に影響する、最も重大な障害です。**

```
 【手順】
  1. どこまで処理されたかを特定
       ★冪等性とリラン設計があれば、ここが容易になる（[⑤ 8節]）
  2. 部分処理の状態を確認
       ・一部の顧客だけ再投資済み
       ・源泉徴収だけ済んで再投資が未実行、など
  3. リランの可否を判断
       ├─ リラン可能 → 実行。二重処理がないことを確認
       └─ リラン不可 → 手動での復旧手順
  4. 翌営業日のオンライン開始をどうするか判断
       ・残高が正しくない状態で照会させてよいか
       ★「残高照会のみ停止」という縮退も検討
  5. 顧客への告知
  6. 復旧後の検証（全顧客の口数・分配金額の再計算突合）
  7. 事故報告
```

> 💡 **この手順書を書いてみると、「リラン設計が必須である」ことが実感できます。** 設計段階で[⑤ 8節](05-distribution-reinvestment.md#8-システム負荷とバッチ設計)の冪等性を必須要件に入れてください。

## 7. 【MMF固有】元本割れ（ブレーク・ザ・バック）への備え

### 7-1. なぜ備えが必要か

MMFは元本の安定を目指して運用されますが、**元本保証ではありません**。実際に、**組入債券の発行体が破綻したことで国内MMFに元本割れが発生した事例があります**（[① 2節](01-overview.md#2-なぜ今円建てmmfなのかプロジェクトの背景)）。

**「まず起きない」という前提で設計すると、起きたときに次のすべてが同時に問題になります。**

| 影響 | 内容 |
| --- | --- |
| **システム** | 基準価額 ≠ 10,000円 での計算。★**1:1固定でハードコードしていたら破綻**（[④ 1-2節](04-order-correction-cancel.md#1-2-数量の指定方法)） |
| **表示** | 評価損の表示。顧客が初めて「損失」を目にする |
| **解約の殺到** | 大量解約への対応。資金繰り |
| **苦情の殺到** | 「元本保証だと思っていた」 |
| **コールセンター** | 問合せの急増 |
| **報道対応** | 業界全体のニュースになる可能性 |
| **当局対応** | 説明・報告 |

### 7-2. 事前に準備すべきもの

| # | 準備 | 内容 |
| --- | --- | --- |
| **1** | **システムの検証** | ★基準価額が10,000円以外でも正しく計算されるか。**テストケースに必ず入れる**（[⑭](14-test-release.md)） |
| **2** | **表示の確認** | 評価損が正しく表示されるか。マイナス表示の扱い |
| **3** | **委託会社との連絡ルート** | 元本割れの兆候・発生時の連絡（[⑦ 7節](07-management-company.md#7-障害時異常時の取り決め)） |
| **4** | **想定問答（Q&A）** | ★委託会社と共同作成。「なぜ元本割れしたのか」「今後どうなるのか」 |
| **5** | **コールセンターの体制** | 増員計画、エスカレーション |
| **6** | **顧客への告知文** | サイト掲載、メール。★**テンプレートを事前に用意** |
| **7** | **大量解約時の対応** | 資金繰り、解約制限の発動条件（[⑦ 3-2節](07-management-company.md#3-2-取引条件)） |
| **8** | **社内の報告体制** | 誰が誰に、いつ報告するか |
| **9** | **広報・報道対応** | 広報部との連携 |
| **10** | **販売停止の判断基準** | 買付受付を止めるか |

> ⚠️ **準備4（想定問答）は、平時に作っておくことに意味があります。** 有事に書く時間はありません。[⑦ 9節](07-management-company.md#9-苦情問合せの連携)で委託会社と共同作成する計画を立ててください。

> 💡 **販売時の説明が、有事の苦情の量を決めます。** 買付時に「元本保証ではない」ことを十分に伝えていれば、元本割れが起きても「聞いていない」という苦情は減ります。[⑫ 2-2節](12-web-nonfunctional.md#2-2-必ず表示すべき注意喚起)の注意喚起は、**有事への保険**でもあります。

## 9. 苦情・問合せ対応

### 9-1. MMFで想定される問合せ（事前に回答を用意）

| # | 想定される問合せ | 用意すべき回答 |
| --- | --- | --- |
| 1 | **NISAで買えますか** | ★対象外である旨（[⑪](11-tax-nisa-account.md)） |
| 2 | **元本は保証されますか** | ★保証されない旨。運用の性格 |
| 3 | **分配金はいつもらえますか** | 日々計上・月末再投資の説明 |
| 4 | **未収分配金とは何ですか** | ★[⑤](05-distribution-reinvestment.md)の説明 |
| 5 | **解約したら手数料を引かれました** | ★信託財産留保額の説明。買付時の表示を確認 |
| 6 | **ずっと持っているのに手数料を引かれた** | ★★[④ 9節](04-order-correction-cancel.md#9-信託財産留保額とロット管理mmf固有の難所)の再投資口の論点。**設計次第で発生する** |
| 7 | 利回りはどのくらいですか | 実績であり保証でない旨 |
| 8 | いつ換金できますか | 受渡サイクルの説明 |
| 9 | MRFと何が違うのですか | [① 1節](01-overview.md#1-mmfとは何か) |
| 10 | 預金と何が違うのですか | 預金保険の対象外である旨 |

> ⚠️ **問合せ6は、設計の欠陥が苦情になる典型例です。** [⑦](07-management-company.md)の合意事項#26（再投資口の信託財産留保額の扱い）を確認せずに実装すると、**必ずこの苦情が来ます。** 逆に言えば、設計段階で潰せる苦情です。
