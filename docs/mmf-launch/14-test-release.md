# ⑭ テスト・移行・リリース・プロジェクト管理 — 設定日からの逆算と日付シフトテスト

[← ⑬ コンプライアンス・運用・障害対応](13-compliance-ops.md) ｜ [総合インデックス](README.md) ｜ 次 → [用語集・チェックリスト](glossary.md)

**設定日は動かせません。** そして、MMFの中核ロジック（日々決算・月末再投資）は、**システム日付を動かさないと検証できません**。この2つの制約から工程を逆算するのが、本章のテーマです。

---

## 0. この章のゴール

1. 設定日・リリース枠・商品審査から逆算した工程表を作れる
2. **日付シフトテスト**の必要性と、その環境確保の重要性を理解する
3. MMF固有のテストケースを漏れなく設計できる
4. Go/No-Go判定基準とリリース後の体制を事前に決められる

---

## 1. 【最重要】3つの制約からの逆算

このプロジェクトには、**自社で動かせない3つの日付**があります。

```
  ┌─────────────────────────────────────────────────────┐
  │ 制約① ファンドの設定日・販売開始日                    │
  │        → 委託会社が決める（[⑦](07-management-company.md)）│
  ├─────────────────────────────────────────────────────┤
  │ 制約② ソナーの定例リリース枠                          │
  │        → 大和総研の体系で決まる（[⑩](10-sonar-integration.md)）│
  ├─────────────────────────────────────────────────────┤
  │ 制約③ 商品審査会の開催日                              │
  │        → 社内の規程で決まる（[⑬](13-compliance-ops.md)）│
  └─────────────────────────────────────────────────────┘
```

### 1-1. 逆算の手順

```
 【STEP 1】販売開始日を置く                        … X月1日
       ↓
 【STEP 2】そこから逆算する
   ・リリース後の安定稼働確認期間          → X-0.5月
   ・本番リリース（★ソナーの定例枠に合うか） → X-0.5月
   ・リハーサル・Go/No-Go判定              → X-1月
   ・総合テスト／受入テスト                → X-2月
   ・接続テスト（ソナー・委託会社・ベンダー）→ X-3月
   ・結合テスト                            → X-3.5月
   ・開発・単体テスト                      → X-5月
   ・★ソナー側の開発着手締切               → X-5月（要確認）
   ・設計                                  → X-6月
   ・★要件確定                             → X-6.5月
   ・Fit&Gap                               → X-8月
   ・委託会社との商品性合意                → X-8月
   ・プロジェクト開始                      → X-9月
       ↓
 【STEP 3】制約②③と突き合わせる
   ・ソナーの定例リリース枠は X-0.5月にあるか？
   ・商品審査会は X-2月の開催回に間に合うか？
       ↓
 【STEP 4】合わなければ、以下のいずれかを選ぶ
   ・販売開始日を後ろにずらす（★委託会社と再調整）
   ・スコープを削る（[① 7節](01-overview.md#7-スコープ定義in--out)）
   ・アドオンを減らして開発期間を短縮（[⑩ 7節](10-sonar-integration.md#7-標準機能とアドオンの判断基準)）
```

> ⚠️ **STEP 4の判断は、早ければ早いほど傷が浅くなります。**
> 「やってみて間に合わなかった」は最悪です。**プロジェクト開始から1か月以内に、この逆算をやってください。** 間に合わないと分かったら、その時点で委託会社と設定日を再調整する余地があります。開発が進んでからでは、その交渉ができません。

### 1-2. 工程表に必ず積むもの（忘れられがち）

| 工程 | 忘れると | 章 |
| --- | --- | --- |
| **商品審査会（資料提出＋開催）** | 販売できない | [⑬ 2節](13-compliance-ops.md#2-商品審査プロセス) |

| **セキュリティ診断** | リリース判定が通らない | [⑫ 8節](12-web-nonfunctional.md#8-セキュリティ) |

## 3. 【最重要】日付シフトテスト

### 3-1. なぜ必須なのか

MMFの中核ロジックは、**日付が進まないと動きません**。

| 検証したいこと | 必要な日数 | 通常のテストで可能か |
| --- | --- | --- |
| 日々の分配金計上 | 数日 | △ 数日待てば可能 |
| **月末一括再投資** | **1か月** | ✕ **不可能** |
| 未収分配金のリセット | 2か月 | ✕ 不可能 |
| **信託財産留保額の期間判定**（30日等） | **30日以上** | ✕ 不可能 |
| 月末が非営業日のケース | 該当月まで待つ | ✕ 不可能 |
| **年末処理**（年間取引報告書） | 12月まで待つ | ✕ 不可能 |
| 償還処理 | 信託期間満了まで | ✕ 不可能 |

> ⚠️ **「1か月待ってテストする」は工程に収まりません。** システム日付を任意に進められる環境が**必須**です。

### 3-2. 確認すべきこと（早期に）

| # | 確認事項 | 確認先 |
| --- | --- | --- |
| 1 | **ソナーのテスト環境で日付シフトが可能か** | ★大和総研（[⑩](10-sonar-integration.md)質問46） |
| 2 | 日付シフトの操作手順と、必要なリードタイム | 大和総研 |
| 3 | 他社と共用の環境の場合、**日付シフトが他社に影響しないか** | 大和総研 |
| 4 | フロント側の日付シフトの方法 | 自社 |
| 5 | **フロントとソナーの日付を同期できるか** | 双方 |
| 6 | 日付を戻せるか（巻き戻しテスト） | 大和総研 |

> ⚠️ **確認事項3が現実的な壁になります。** 共同利用型のテスト環境では、日付シフトが他社のテストに影響するため、**自由に日付を動かせない**可能性があります。
> **その場合の代替案**
> - 専用のテスト環境を確保する（費用・リードタイムを確認）
> - 日付シフト可能な期間を予約制で確保する
> - 一部のロジックをスタブで検証する（★本番との差異リスクが残る）
>
> **いずれにせよ、プロジェクトの初期に確認しないと手が打てません。** [⑩](10-sonar-integration.md)の質問票で最優先に挙げている理由です。

### 3-3. 日付シフトテストのシナリオ

```
 【基本シナリオ：2か月通し】

  Day 1   買付（顧客A：100万円、顧客B：1万円 ★少額）
  Day 2-  日々の分配金計上を確認
            ★顧客B（少額）の分配金が0円になっていないか（[⑤ 3節]）
  Day 15  追加買付（顧客A）
  Day 20  一部解約（顧客A）★信託財産留保額が発生するか
  Day 末  ★月末一括再投資
            ・分配金の合計額
            ・源泉徴収額
            ・再投資口数
            ・未収分配金がゼロにリセットされるか
            ・帳票が正しく出るか
  Day 末+1 残高照会で口数が増えているか
  Day 35  ★★ 全部解約 → 未収分配金の精算（[④ 7節]）
  Day 2か月末  2回目の再投資
            ・1回目の影響が正しくリセットされているか

 【追加シナリオ】
  ・月末が土日祝のケース
  ・12月末（年間取引報告書との順序）
  ・★取得から30日目・31日目の解約（信託財産留保額の境界値）
  ・★再投資口を含む解約（[④ 9節]の論点2の検証）
  ・基準価額 ≠ 10,000円 のケース（★元本割れ）
  ・口座閉鎖後に月末を迎えるケース
  ・再投資バッチの途中失敗 → リラン
```

## 6. リハーサル

本番直前に、**当日の手順を通しで実施**します。

| 項目 | 内容 |
| --- | --- |
| **実施タイミング** | リリースの1〜2週間前 |
| **参加者** | 自社（システム・業務・コンプラ・CS）、大和総研、必要に応じて委託会社 |
| **シナリオ** | リリース作業 → 本番確認取引 → 日次業務 → 締め → 夜間バッチ → 翌日確認 |
| **本番確認取引** | ★リリース後に少額の実取引を行い、全工程を確認する |
| 計測 | 各作業の所要時間。当日のタイムテーブル作成に使う |
| 課題の洗い出し | 手順の不備、判断が必要な箇所 |
| **切り戻しの訓練** | ★リハーサルで切り戻しも試す |

> 💡 **「本番確認取引」を計画してください。** リリース後、正式な販売開始前に、社内関係者の口座で少額の買付・解約を行い、**注文〜約定〜残高〜帳票〜決済まで**を実際に確認します。これで発見される問題は少なくありません。

## 8. Go / No-Go 判定

**判定基準を、リリース直前ではなく事前に決めてください。**

### 8-1. 判定基準（例）

| カテゴリ | Go の条件 |
| --- | --- |
| **テスト** | 全テスト工程が完了し、未解決の重大障害がゼロ |
| | ★日付シフトテスト（月末再投資）が完了している |
| | ★異常系テスト（No.27〜32）が完了している |
| **性能** | 性能要件を満たしている。月末バッチがバッチウィンドウ内に収まる |
| **接続** | ソナー・委託会社・決済・ベンダーの全接続テストが完了 |
| **業務** | 手順書が完成し、業務部の受入テストが完了 |
| **コンプラ** | ★**商品審査の決裁が下りている** |
| | ★**広告審査が完了している** |
| | ★**社内規程の改定が決裁されている** |
| **契約** | ★**販売会社契約が締結されている** |
| **体制** | コールセンター研修が完了。当日・初期監視の体制が組まれている |
| **その他** | 目論見書の最新版が配置されている。情報ベンダーの配信が確認できている |

### 8-2. 判定会議

| 項目 | 内容 |
| --- | --- |
| 開催時期 | リリースの1週間前 |

| 条件付きGo | 残課題と、その解消期限を明記 |

## 9. リリース当日と初期監視

### 9-1. 当日のタイムテーブル

| 時刻 | 作業 | 担当 |
| --- | --- | --- |
| リリース前 | 最終確認（マスタ・PDF・設定） | システム・業務 |
| リリース作業 | ソナー・フロントの本番反映 | システム・大和総研 |
| リリース後 | **本番確認取引** | 業務部 |
| 確認後 | サイト公開（販売開始） | システム |
| 日中 | 監視強化 | 全員 |
| 締め後 | 初日の約定・伝送の確認 | 業務部 |
| 夜間 | バッチの監視 | システム |
| 翌朝 | **初日の全工程の確認** | 全員 |

### 9-2. 初期監視期間

**リリース後の一定期間は、通常より手厚い体制を敷きます。**

| 期間 | 重点監視項目 |
| --- | --- |
| **初日〜1週間** | 注文の受付・約定・帳票。苦情の傾向。★**利回り表示**（設定7日未満） |
| **7日目** | ★平均利回りの表示が始まるタイミング |
| **初回の月末** | ★★**最重要**。月末一括再投資を全員で見守る |
| **月末翌営業日** | ★残高照会の集中。顧客からの問合せ |
| **初回の月末+1か月** | 2回目の再投資（未収分配金のリセットの検証） |
| **初回の12月末** | ★年間取引報告書の作成 |
| 30日目以降 | ★信託財産留保額が発生し始める。苦情の有無 |

> ⚠️ **「初回の月末」は、プロジェクトの実質的な最終日です。** リリース日ではありません。**月末一括再投資が正常に完了し、翌日の残高が正しいことを確認するまで、プロジェクト体制を解散しないでください。**

## 10. 切り戻し計画

| 項目 | 内容 |
| --- | --- |
| **切り戻しの判断基準** | どの事象が発生したら切り戻すか |
| 判断者 | 誰が判断するか |
| **切り戻しの手順** | ソナー側・フロント側それぞれ |

## 11. プロジェクト体制とRACI

### 11-1. 体制

| 役割 | 担当 | 主な責務 |
| --- | --- | --- |
| プロジェクトオーナー | 役員 | 意思決定、Go/No-Go判定 |
| **プロジェクトマネージャー** | 企画／システム | 全体統括、課題管理 |
| 企画・商品担当 | 企画部 | 商品性、委託会社との調整、収益計画 |
| **業務担当** | 業務部 | 業務要件、手順書、受入テスト |
| **システム担当（フロント）** | システム部 | 画面・IF・非機能 |
| **システム担当（ソナー窓口）** | システム部 | 大和総研との調整、Fit&Gap |
| コンプライアンス | コンプラ部 | 法令対応、商品審査、広告審査、規程改定 |
| 税務 | 経理・税務 | 税務要件の確認 |
| 経理 | 経理部 | 収益計上、仕訳連携 |
| CS | コールセンター | 想定問答、研修 |
| AML | AML担当 | モニタリング対応 |

### 11-2. RACI（主要タスク）

**R**=実行 **A**=説明責任 **C**=相談 **I**=報告

| タスク | PM | 企画 | 業務 | Sys | コンプラ | 税務 |
| --- | --- | --- | --- | --- | --- | --- |
| 商品性の合意（委託会社） | A | **R** | C | C | C | C |
| Fit&Gap（ソナー） | A | I | C | **R** | I | I |
| 要件定義 | **A** | C | **R** | **R** | C | C |
| 税務要件の確定 | A | I | C | C | C | **R** |
| 帳票設計 | A | I | **R** | R | C | C |
| 商品審査 | A | **R** | C | I | **A** | C |
| 広告審査 | A | R | I | C | **A** | I |
| 規程改定 | A | C | R | I | **A** | I |
| テスト | A | I | **R** | **R** | C | C |
| Go/No-Go判定 | R | C | C | C | C | I |
| リリース | A | I | R | **R** | I | I |

## 12. 主要リスクと対応

| # | リスク | 影響 | 対応 |
| --- | --- | --- | --- |
| 1 | **ソナーのリリース枠が設定日に合わない** | 販売開始できない | ★早期に確認。合わなければ設定日を再調整 |
| 2 | **日付シフトテストができない** | 中核ロジックを検証できない | ★早期に確認。代替案を準備 |
| 3 | **アドオンが想定より多い** | コスト・工期の超過 | Fit&Gapを前倒し。スコープを削る |
| 4 | **商品性パラメータの決定が遅れる** | 設計が始められない | 第1回打合せで★★項目を提示 |
| 5 | **商品審査で差し戻し** | 1か月遅延 | 事前にコンプラと論点をすり合わせ |
| 6 | 広告審査が長引く | サイト公開の遅延 | ワイヤー段階でレビュー |
| 7 | **税務要件の確認が遅れる** | 税計算の設計ができない | 質問票を早期に送付（[⑪](11-tax-nisa-account.md)） |
| 8 | **委託会社との計算値が一致しない** | リコン差異が続く | 端数処理を早期に突合（[⑤](05-distribution-reinvestment.md)） |
| 9 | 郵送コストが収益を上回る | 事業性の問題 | 早期に試算（[⑥](06-prospectus-delivery.md)） |
| 10 | **リリース後の初回月末で問題発生** | 全顧客に影響 | ★初回月末まで体制を維持 |
| 11 | 残高が伸びず繰上償還 | 事業目的の未達 | 販売計画・プロモーションの検討 |
| 12 | **元本割れの発生** | 苦情・報道 | 事前準備（[⑬ 7節](13-compliance-ops.md#7-mmf固有-元本割れブレークザバックへの備え)） |
