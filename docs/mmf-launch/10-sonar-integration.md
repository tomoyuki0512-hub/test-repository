## 1. 【最重要】共同利用型システムの特性を理解する

ソナーのような共同利用型（複数の証券会社が同じ基盤を使う）システムには、自社専用システムとは根本的に異なる制約があります。**この理解がないと、プロジェクト計画そのものが非現実的になります。**

| 特性 | 意味すること | プロジェクトへの影響 |
| --- | --- | --- |
| **標準機能は他社と共通** | 個社固有の要望は通りにくい／通っても高額 | ★**「業務をシステムに寄せる」判断が必要** |
| **アドオンは高コスト・長リードタイム** | 個社開発は見積りも工期も大きくなる | 要件定義段階でアドオンを減らす努力が最大の費用削減 |
| **リリース枠が定例で決まっている** | 好きな日にリリースできない | ★**設定日とリリース枠が合わないと詰む** |
| **他社案件との優先順位競合** | 開発リソースは他社と取り合い | 早期に枠を押さえる必要がある |
| **バージョンアップへの追随義務** | 基盤の更新に合わせた対応が発生 | 中長期の保守計画に影響 |
| **仕様変更の自由度が低い** | 後から「やっぱりこうしたい」が効きにくい | 要件の確定を前倒しする必要がある |

### 1-1. したがって、進め方が変わります

```
【自社専用システムの場合】
  要件定義 → 設計 → 開発 → テスト → リリース
  （要件は自社で決められる。多少の変更も吸収できる）

【共同利用型システムの場合】
  ★Fit&Gap（標準機能の調査）  ← ここが最初
        ↓
  ★業務要件を標準機能に寄せる交渉（社内）
        ↓
  どうしても必要なアドオンだけを特定
        ↓
  ★リリース枠の確保                ← 早期に押さえる
        ↓
  要件定義 → 設計 → 開発 → テスト → リリース
```

> 💡 **最大のコスト削減施策は、「アドオンを1本減らすこと」です。** そのために要件定義の前に Fit&Gap をやる、という順序が重要です。「要件を固めてからベンダーに見せる」と、固めた要件の多くが標準機能と合わず、作り直しになります。

## 2. Fit&Gapの進め方

### 2-1. 手順

| STEP | 作業 | アウトプット |
| --- | --- | --- |
| **1** | ソナーの標準機能仕様（投資信託・公社債投信の範囲）を入手 | 機能一覧 |
| **2** | 既存の類似商品（MRF・外貨建MMF）でどう実現されているかを確認 | 現行の実装方式 |
| **3** | 本ガイド①〜⑨・⑪〜⑬の要件を機能単位に分解 | 要件一覧 |
| **4** | 要件 × 標準機能 のマトリクスを作成 | **Fit&Gap表** |
| **5** | Gapを4分類する（[2-2節](#2-2-gapの4分類)） | 分類済みGap一覧 |
| **6** | 各Gapの対応方針を決定（アドオン／業務対応／スコープ外） | 対応方針書 |
| **7** | アドオン候補の概算見積りとリードタイムを取得 | 見積り |
| **8** | コスト・スケジュールを踏まえて最終決定 | 確定スコープ |

> 💡 **STEP 2が最も効率的です。** 「MRFではどうやっていますか」「外貨建MMFの分配金処理はどうなっていますか」と聞くと、標準機能の実像が最短で分かります。**仕様書を読むより、既存の類似実装を聞くほうが早い**です。

### 2-2. Gapの4分類

| 分類 | 内容 | 対応 | コスト |
| --- | --- | --- | --- |
| **① Fit** | 標準機能でそのまま実現できる | 設定・マスタ登録のみ | 小 |
| **② パラメータ対応** | 標準機能の設定変更で実現できる | 設定値の決定 | 小 |
| **③ 業務対応** | システムでは実現できないが、業務手順でカバーできる | ★**手順書・運用体制** | 中（運用コストが継続） |
| **④ アドオン** | 個社開発が必要 | 開発 | ★**大** |

> ⚠️ **③（業務対応）を安易に選ばないでください。** 開発費はかかりませんが、**運用コストが永続的に発生**します。月100件の手作業は、年1,200件、10年で12,000件です。
> 判断基準：**「発生頻度 × 作業時間 × 想定運用年数」を計算し、アドオン費用と比較**してください。頻度が低ければ業務対応、高ければアドオンです。

### 2-3. 「標準に寄せる」交渉の進め方

Gapが見つかったとき、**まず社内の業務要件を疑ってください。**

| 問い | 例 |
| --- | --- |
| その要件は**法令上の必須**か | 必須なら妥協できない |
| **既存商品と同じにする必要**があるか | 「他の商品と同じ画面にしたい」は、多くの場合は譲れる |
| **顧客が本当に困る**か | 社内の慣習にすぎないことが多い |
| **第2フェーズに回せる**か | 初期リリースに必須でないものは切る |
| 標準機能で**近いこと**ができないか | 100点でなく80点で許容できないか |

> 💡 **要件定義書に「この要件はなぜ必要か」を1行書く欄を作ってください。** 書けない要件は、たいてい慣習です。この欄があるだけで、Gapが自然に減ります。

## 4. 銘柄マスタ登録項目

ソナーに新銘柄を登録する際の項目です。[⑦ 3節の商品性パラメータ50項目](07-management-company.md#3-核心合意すべき商品性パラメータ一覧)がそのまま入力値になります。

| カテゴリ | 主な項目 |
| --- | --- |
| 識別 | ファンドコード（協会コード）、ISINコード、社内銘柄コード、ファンド名（正式・略称・カナ） |
| 分類 | 商品分類（公社債投信）、属性区分、決算頻度（日々決算） |
| 委託・受託 | 委託会社コード、受託会社 |
| 期間 | 設定日、信託期間、償還日、販売開始日、販売終了日 |
| 取引条件 | 最低申込金額、申込単位、締め時刻、約定日ルール、受渡日ルール |
| 費用 | 申込手数料率、信託報酬、**代行手数料率**、**信託財産留保額（料率・判定期間）** |
| 分配 | 分配頻度、再投資区分、**再投資日ルール**、**端数処理** |
| 税 | **所得区分（利子所得）**、税率区分、特定口座受入可否、**NISA対象外フラグ** |
| 帳票 | 帳票出力区分、取引報告書の交付要否 |
| 決済 | 決済方式、資金決済口座 |

> ⚠️ **「所得区分（利子所得）」と「NISA対象外フラグ」を必ず確認してください。** 株式投信と同じ設定で登録すると、税計算とNISAの判定が誤ります。**マスタ登録の時点で間違えると、全部の処理が狂います。**

> 🔍 **大和総研へ**：銘柄マスタの登録項目一覧（レイアウト）を入手し、[⑦](07-management-company.md)の合意事項テーブルと項目対応表を作ってください。**「委託会社に何を聞けばよいか」が、この対応表から逆算できます。**

## 7. 標準機能とアドオンの判断基準

| 判断軸 | 標準を選ぶ | アドオンを選ぶ |
| --- | --- | --- |
| **法令要件** | 標準で満たせる | ★満たせない → **アドオン必須** |
| 発生頻度 | 低い（業務対応で足りる） | 高い（手作業が破綻する） |
| 顧客への影響 | 小さい | 大きい（苦情・誤認につながる） |
| 代替手段 | ある | ない |
| コスト | — | ★**運用コスト10年分 > 開発費** なら合理的 |
| スケジュール | — | ★リリース枠に間に合うか |
| 将来の拡張 | — | 第2フェーズでも間に合うか |

### アドオンを減らすための3つの問い

1. **「その要件は法令上の必須か？」** — 必須でなければ交渉の余地がある
2. **「業務手順で回避できないか？」** — 頻度が低ければ手作業でよい
3. **「第2フェーズに回せないか？」** — 初期リリースの範囲を絞る

> 💡 **要件定義書に「アドオン一覧」という別紙を作り、各アドオンに「なぜ必要か（法令／業務／顧客影響）」を1行で書いてください。** 書けないものは落とせます。経営への説明資料にもそのまま使えます。

## 8. リリース枠とスケジュール

共同利用型システムの**最大の制約**です。

| 確認すべきこと | なぜ重要か |
| --- | --- |
| **定例リリースの日程** | いつリリースできるか。★**設定日と合うか** |
| 開発着手の締切 | 要件を何か月前までに確定すべきか |
| **枠の確保方法** | いつまでに申し込めば枠を押さえられるか |
| 他社案件との競合 | 枠が埋まっている可能性 |
| 緊急リリースの可否 | 定例外でリリースできるか。条件と費用 |
| テスト期間 | ソナー側のテスト工程の期間 |
| **凍結期間** | 年度末・決算期などの変更凍結期間の有無 |

> ⚠️ **これがクリティカルパスになるケースが非常に多いです。**
> ```
>  設定日：X月1日
>       ↑
>  リリース可能日：定例リリースは奇数月の第3土曜のみ
>       ↑
>  開発着手の締切：リリースの4か月前
>       ↑
>  要件確定：開発着手の1か月前
>       ↑
>  ★つまり、設定日の5か月以上前に要件が固まっている必要がある
> ```
> **プロジェクト開始時に、この逆算を必ずやってください。** 「設定日に間に合わない」と分かるのは早いほどよく、その場合は**設定日を委託会社と再調整する**という選択肢が取れます。

## 9. テスト環境

| 確認事項 | なぜ重要か |
| --- | --- |
| **テスト環境の提供有無** | 接続テストができるか |
| 利用可能な期間・時間帯 | 他社と共用の場合、時間が限られる |
| **★日付シフトの可否** | ★**月末再投資のテストに必須**（[⑭](14-test-release.md)） |
| テストデータの準備 | 誰が用意するか |
| 委託会社との3者接続テスト | 実施可能か、時期は |
| スタブ／モックの提供 | フロント単体テスト用 |
| 本番相当の件数でのテスト | 性能検証ができるか |

> ⚠️ **「日付シフトの可否」は、MMFプロジェクトで最も重要な確認事項のひとつです。**
> 日々決算・月末再投資の検証は、**システム日付を進めないと絶対に検証できません**。「1か月待ってテストする」は工程に収まりません。
> **日付シフトができない場合、テスト計画そのものを根本から見直す必要があります。** 早期に確認してください。

10. 締め後・伝送前の社内取消は標準機能で可能ですか
