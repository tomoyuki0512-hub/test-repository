# ① 全体像・商品性・スキーム — 何を売るのか、誰が何をするのか

[← 総合インデックスに戻る](README.md) ｜ 次 → [② 顧客帳票](02-customer-documents.md)

要件定義の最初にやるべきは、画面設計でもIF設計でもありません。**「この商品は何で、誰が何をやるのか」を関係者全員で同じ絵にすること**です。ここが曖昧なまま進むと、後工程のすべてが手戻りします。

---

## 0. この章のゴール

読み終えたとき、次の問いに答えられる状態を目指します。

1. MMFはMRFや株式投信と何が違い、そのシステム的な意味は何か
2. 日々決算・月末再投資という仕組みが、後工程のどこに効いてくるか
3. 委託会社・受託会社・販売会社・ほふり・ソナーは、それぞれ何を担当するのか
4. このプロジェクトのスコープは、どこからどこまでか

---

## 1. MMFとは何か

**MMF（マネー・マネジメント・ファンド）** は、短期の公社債などで運用する **公社債投資信託** です。

| 特徴 | 内容 | システム上の意味 |
| --- | --- | --- |
| **追加型** | いつでも買い増しできる | 単位型のような募集期間管理は不要。常時買付可能 |
| **日々決算型** | 毎営業日に決算し、分配金を計上する | **毎日、分配計算のデータが発生する**。帳票・残高表示・税処理すべてに波及 |
| **実績分配型** | 運用実績に応じて分配する。利率は固定でない | 「予定利率」の概念がない。利回りは事後的な実績表示になる |
| **1口＝1円** | 基準価額は1万口あたりで表示（通常10,000円） | 金額指定注文と口数指定注文がほぼ1:1で対応する。ただし**元本保証ではない** |
| **月末一括再投資** | 日々の分配金を月末最終営業日にまとめて再投資し、口数が増える | 月末に**全保有者の口数更新**が走る。月末がシステム負荷のピーク |
| **信託財産留保額** | 購入から一定期間（従来は30日）未満の解約時に差し引かれるのが一般的 | 保有期間の管理（取得日ごとのロット管理）が必要になる |

> 🔍 **確認事項**：申込単位、信託財産留保額の有無・料率・判定期間、決算日、信託期間は**ファンドごとに委託会社が決める**ものです。[⑦ 委託会社との調整](07-management-company.md)の合意事項テーブルで必ず確定させてください。本章の記載は一般的な設計例であり、実際の商品性ではありません。

### MRFとの違い

同じ「元本の安定を目指す短期運用ファンド」でも、役割が違います。

| | **MRF**（マネー・リザーブ・ファンド） | **MMF**（マネー・マネジメント・ファンド） |
| --- | --- | --- |
| 位置づけ | 証券総合口座の**待機資金置き場** | 顧客が**意思を持って買う投資商品** |
| 買付 | 入金時に**自動**でスイープ買付 | 顧客が注文を出す |
| 解約 | 他の商品の買付時に**自動**で解約充当 | 顧客が注文を出す |
| 信託財産留保額 | なし | 短期解約時にかかる設計が一般的 |
| 運用期間 | より短期・より保守的 | MRFよりやや長めで、利回りを狙う |

**要件定義上の含意**：MRFはシステムが自動で売買するので「注文画面」がほぼ不要ですが、MMFは **顧客が明示的に注文する商品** です。したがって [④ 注文・訂正・取消](04-order-correction-cancel.md) の設計が本格的に必要になります。

> 🔍 **確認事項**：MMFの買付代金をMRFから自動充当するか、出金可能額（買付余力）とどう連動させるかは重要な設計判断です。既存のMRFスイープ仕様との整合を早期に確認してください。

### 株式投資信託との違い（課税区分が効く）

| | 株式投資信託 | **公社債投資信託（MMF）** |
| --- | --- | --- |
| 約款上の株式組入 | 可能 | **不可**（公社債等のみ） |
| 分配金の所得区分 | 配当所得 | **利子所得** |
| NISA | 対象（要件を満たすもの） | **対象外** |
| 配当控除 | 適用余地あり | 適用なし |

この違いが [⑪ 口座・税制](11-tax-nisa-account.md) に直結します。**「投信だから株式投信と同じ処理」は成り立ちません。**

## 2. なぜ今、円建てMMFなのか（プロジェクトの背景）

要件定義書の冒頭に書くべき「背景」の整理です。

```
【歴史】
1992年   国内でMMFの取扱い開始。安全な短期運用商品として普及
2001年   エンロン破綻の影響で組入債券が毀損し、一部MMFで元本割れが発生
         → 「MMFは元本保証ではない」ことが広く認識される
2016年   日銀のマイナス金利政策により、短期金利での運用が成立しなくなる
         → 各運用会社が新規募集を停止し、順次繰上償還
2017年   国内の円建てMMFは実質的に消滅
         （※外貨建MMF（米ドル建て等）は、この間も継続して販売）
2024年〜  日銀の政策転換により短期金利が上昇。円建てでの運用余地が回復
現在     円建てMMFの再設定・販売再開が検討可能な環境に
```

**この背景が要件定義に効く点は3つあります。**

1. **社内に運用ノウハウが残っていない可能性がある** — 円建てMMFの取扱いが約10年空白なら、当時を知る担当者も、当時のシステム資産も残っていない前提で計画を立てる必要があります。「昔やっていたから簡単」は通用しません。
2. **元本割れの前例がある** — [⑬ コンプライアンス・運用](13-compliance-ops.md) で扱う「元本割れ発生時の対応手順」は、机上の空論ではなく**実際に起きた事象への備え**です。
3. **外貨建MMFの既存仕組みが流用できるか** — すでに外貨建MMFを扱っているなら、帳票・注文・分配のロジックの一部は再利用できる可能性があります。ただし為替処理の有無が大きく異なるため、**Fit&Gapを必ず取ってください**。

> 🔍 **確認事項**：自社が現在、外貨建MMFまたはMRFを取り扱っているか。取り扱っている場合、その処理がソナーのどの機能で実現されているか。これが分かると[⑩ ソナー連携](10-sonar-integration.md)の見積り精度が一気に上がります。

## 3. 登場人物と、その役割

投資信託は「3者（委託者・受託者・受益者）」を軸とした仕組みです。ここに決済インフラとシステムベンダーが加わります。

| 登場人物 | 正式な立場 | 何をするか | 自社との関係 |
| --- | --- | --- | --- |
| **委託会社**（運用会社） | 委託者 | ファンドの設定、運用指図、**基準価額の算出**、目論見書・運用報告書の作成 | **最重要の調整相手**（[⑦](07-management-company.md)） |
| **受託会社**（信託銀行） | 受託者 | 信託財産の保管・管理・分別管理、基準価額の照合 | 直接のやり取りは限定的（[⑨](09-trustee-settlement.md)） |
| **販売会社** | 募集・販売の取扱い | **自社**。顧客への販売、注文の集約、口座管理、帳票交付 | — |
| **受益者** | 受益者 | ファンドの持分を保有する顧客 | 自社の顧客 |
| **ほふり**（証券保管振替機構） | 振替機関 | 投資信託振替制度の運営、約定照合・資金決済の基盤 | 制度上の基盤（[⑨](09-trustee-settlement.md)） |
| **大和総研（ソナー）** | システムベンダー | 証券基幹（バックオフィス）システムの提供 | **バック処理の実装主体**（[⑩](10-sonar-integration.md)） |
| **情報ベンダー**（QUICK等） | 情報提供 | 基準価額・分配金・ファンド属性の配信 | サイト表示の情報源（[⑧](08-info-vendor.md)） |
| **投資信託協会** | 自主規制機関 | 商品分類、コード付番、統計、自主規制ルール | 制度・ルールの適用（[⑬](13-compliance-ops.md)） |

### 資金と情報の流れ（買付時）

```
 ①注文           ②注文集約・伝送        ③設定指図
顧客 ──────→ 【自社（販売会社）】 ──────→ 委託会社 ──────→ 受託会社
                    │   ↑                   │                  │
                    │   │                   │                  │
                    │   │ ⑤約定・残高       │ ④基準価額算出     │ 信託財産の
                    │   │                   │   ・照合          │ 保管・管理
                    │   ↓                   ↓                  ↑
                【ソナー（バック）】     基準価額を配信       ⑥買付代金の払込
                    │                      ／情報ベンダー       （信託口へ）
                    │                          ↓
                    └─→ 顧客口座の残高更新 ← 自社サイトに表示
                        ・帳票出力
                        ・税処理
```

**要件定義上の要点**：この図の矢印**1本ごとに、IF仕様（項目・形式・タイミング・エラー時の挙動）が必要**です。矢印を数えることが、そのままIF一覧の作成になります。

## 4. 責任分界点マトリクス

「バックはソナーで対応する」と言ったとき、**具体的に何がソナーの範囲なのか**を機能単位で潰します。これは要件定義の最重要成果物のひとつです。

| 機能 | 自社フロント（Web） | **ソナー（バック）** | 委託会社 | 外部（ほふり／ベンダー） |
| --- | --- | --- | --- | --- |
| 商品マスタ登録 | 表示用マスタ | ◎ 銘柄マスタ | 商品情報の提供 | 協会コード付番 |
| 目論見書の表示・同意取得 | ◎ | 同意結果の保持？ | PDFの提供 | — |
| 注文受付（入力・validation） | ◎ | 注文受理・チェック | — | — |
| 買付余力チェック | 画面表示 | ◎ 残高・余力管理 | — | — |
| 注文の訂正・取消 | 受付画面 | ◎ 状態管理 | リジェクト通知 | — |
| 委託会社への注文伝送 | — | ◎ | 受領 | ほふり経由の場合あり |
| 基準価額の受領 | 表示 | ◎ 取込・約定計算 | 算出・配信 | ベンダー配信 |
| 約定処理・残高更新 | 照会 | ◎ | — | — |
| **分配金計算・月末再投資** | 表示 | ◎ | 分配金額の通知 | — |
| 税計算（特定口座） | 表示 | ◎ | — | — |
| 顧客帳票の作成 | 電子交付の閲覧 | ◎ 帳票データ生成 | 運用報告書の提供 | 印刷・発送会社 |
| 資金決済 | — | ◎ 決済データ | 受領・払出 | ほふり決済 |
| 残高照合（リコンサイル） | — | ◎ | 照合相手 | ほふり |

**◎ = 主担当。「？」が付いた欄が、要件定義で真っ先に潰すべき論点です。**

> 🔍 **最重要の確認事項**：上表の「◎ ソナー」の各機能について、**「標準機能で提供されるのか／個社アドオンが必要なのか」** を大和総研に確認してください。これが[⑩](10-sonar-integration.md)の中心テーマであり、**プロジェクトのコストとスケジュールの8割を決めます**。

## 5. 取引サイクル（申込日・約定日・受渡日）

MMFは「**当日約定・短サイクル決済**」が特徴です。株式投信（翌営業日約定が多い）と感覚が違う点に注意します。

```
【買付】※設計例。実際のサイクルは委託会社との合意による
  T日 15:00まで受付 ─→ T日の基準価額で約定 ─→ T日または T+1 で受渡
       │
       └─ 15:00 以降の注文は T+1 営業日扱いに繰越

【解約】※設計例
  T日 15:00まで受付 ─→ T日の基準価額で約定 ─→ T日または T+1 で出金可能
       │
       └─ 取得から一定期間未満の口は信託財産留保額を控除
```

**この「締め時刻（カットオフ）」が、システム設計の背骨になります。**

- Webの受付締めと、ソナーのバッチ締めと、委託会社への伝送締めは**それぞれ別の時刻**になります。この3つの時刻差（バッファ）を決めることが要件定義の仕事です
- 締め時刻直前はアクセスが集中します（[⑫ 非機能要件](12-web-nonfunctional.md)）
- 営業日カレンダー（銀行休業日・証券休業日・年末年始）の管理主体を決める必要があります

> 🔍 **確認事項**：①Web受付締め時刻、②ソナーの注文確定バッチ時刻、③委託会社への伝送期限、④基準価額の受領時刻。この4つのタイムラインを1枚の図にして、関係者全員で合意してください。

## 6. 「日々決算・月末再投資」が波及する範囲

MMF固有の仕組みが、**どの章に、どう効いてくるか**を先に把握しておきます。これを知らずに個別章を設計すると、必ず矛盾が出ます。

| 波及先 | 何が起きるか | 章 |
| --- | --- | --- |
| **顧客帳票** | 毎日分配が発生するため、素直に作ると**取引報告書が毎日発行**されてしまう。集約・省略の設計が必須 | [②](02-customer-documents.md) |
| **残高表示** | 「保有口数」に加えて **「未収分配金（月末までの累計）」** を別建てで表示する必要がある | [⑤](05-distribution-reinvestment.md)・[⑫](12-web-nonfunctional.md) |
| **解約処理** | 月中に解約すると、**その時点までの経過分配金**を合わせて精算する必要がある | [④](04-order-correction-cancel.md)・[⑤](05-distribution-reinvestment.md) |
| **税処理** | 分配金は源泉徴収後に再投資される。**月末に全口座分の源泉徴収が走る** | [⑪](11-tax-nisa-account.md) |
| **取得単価** | 再投資で口数が増えるたびに取得単価が変わる。信託財産留保額の期間判定にも影響 | [⑪](11-tax-nisa-account.md)・[④](04-order-correction-cancel.md) |
| **システム負荷** | 月末最終営業日に**全保有者の口数更新バッチ**が走る。これが年間最大のバッチ処理 | [⑫](12-web-nonfunctional.md) |
| **テスト** | 「月末をまたぐ」検証は**日付を動かさないとできない**。日付シフト可能なテスト環境の確保が必要 | [⑭](14-test-release.md) |

## 7. スコープ定義（In / Out）

要件定義の初期に、**やらないことを明示する**のが最も効きます。ここは案の提示であり、プロジェクトで正式に合意してください。

### スコープ In（このプロジェクトでやる）

- 新規MMF 1銘柄の、Webチャネル（PC・スマートフォン）での買付・解約
- ソナーへの銘柄マスタ登録、および注文・約定・残高・分配・税処理の対応
- 顧客帳票・社内帳票の新規対応または既存帳票への銘柄追加
- 目論見書の電子交付および郵送対応
- 委託会社・情報ベンダー・決済インフラとの連携
- 関連する社内規程・業務マニュアルの改定
- コールセンターの対応手順整備と研修

### スコープ Out（このプロジェクトではやらない ＝ 要合意）

| 項目 | 判断 | 理由・備考 |
| --- | --- | --- |
| 対面・コールセンターからの**発注**受付 | 要判断 | Webのみに絞れば大幅にスコープ縮小できる。ただし顧客からの要望は出る |
| **積立**（定時定額買付） | 要判断 | あると便利だが、別スキームの開発が必要。第2フェーズ送りが定石 |
| MRFからの**自動スイープ**連動 | 要判断 | 既存MRF仕様への影響が大きい。慎重に判断 |
| 他ファンドとの**スイッチング** | Out推奨 | MMFでは需要が限定的 |
| 外貨建MMFの同時リニューアル | Out推奨 | 為替処理が絡み、複雑さが跳ね上がる |
| **法人口座**への提供 | 要判断 | 源泉徴収の扱いが個人と異なる（[⑪](11-tax-nisa-account.md)）。個人限定なら簡素化できる |
| **非居住者**への提供 | Out推奨 | 租税条約の考慮が必要でコストに見合わないことが多い |
| 分配金の**受取（現金）コース** | 要判断 | MMFは再投資専用が一般的。受取コースを設けると帳票・税処理が倍増 |

> 💡 **実務のコツ**：「要判断」の項目は、**第1フェーズはOut、第2フェーズで検討**と明記して合意を取るのが最も安全です。曖昧に残すと、テスト工程で「やっぱり必要」が出ます。
