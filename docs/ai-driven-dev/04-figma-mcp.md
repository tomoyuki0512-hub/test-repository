# ④ Figma MCPの接続と使い方

[← 総合インデックスに戻る](README.md) ｜ 前 → [③ Code Connect](03-code-connect.md) ｜ 次 → [⑤ AI駆動開発のワークフロー](05-ai-workflow.md)

ここまでで土台（[②トークン](02-design-tokens.md)・[③Code Connect](03-code-connect.md)）が整っている前提で、AIとFigmaを繋ぎます。**この順序が逆だと効果が出ません。**

---

## 1. MCPとは何か（前提の整理）

**MCP（Model Context Protocol）は「AIに外部データ・機能を提供するための共通規格」**です。

```
        ┌──────────────┐
        │ Claude Code  │  ← AIクライアント
        └──────┬───────┘
               │ MCP（共通規格）
    ┌──────────┼──────────┐
    ▼          ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐
│ Figma  │ │ GitHub │ │  ...   │  ← MCPサーバー
│  MCP   │ │  MCP   │ │        │
└────────┘ └────────┘ └────────┘
```

USBのようなもので、**規格が同じなら差し替えられる**のが利点です。Figma MCP を繋げば、AIがFigmaのデザイン情報を直接読めるようになります。

---

## 2. リモート版とデスクトップ版

Figma MCPサーバーには2種類あり、**リモート版が推奨**です。

| | **リモート版**（推奨） | デスクトップ版 |
| --- | --- | --- |
| エンドポイント | `mcp.figma.com/mcp` | ローカル（Figmaアプリ経由） |
| プラン要件 | **全プラン・全シートで利用可** | **Dev または Full シート＋有料プラン** |
| Figmaアプリ | 不要 | **起動しっぱなしが必要** |
| 機能範囲 | **広い**（`use_figma` の書き込みを含む） | 選択ベースの操作に強い |
| セットアップ | 認証のみ | ローカル設定が必要 |

> ⚠️ **デスクトップ版の落とし穴**：Starterプランやコラボシートで有効化しようとすると、**エラーを出さずに黙って失敗**します。「設定したのに動かない」場合はまずシート種別を確認してください。

---

## 3. Claude Code への接続

Figmaは公式プラグインを提供しているため、非公式のMCPサーバーを使う必要はありません。

```
/plugin
  → マーケットプレイスを開く
  → Installed タブ
  → figma を選択して Enter（認証が始まる）
  → ブラウザで「Allow access」をクリック
```

### 接続確認

```
/mcp        # 接続中のMCPサーバー一覧を表示
```

`figma` が表示され、ツールが列挙されれば成功です。

> 💡 **このリポジトリのようなリモート実行環境では**、Figmaの認証はブラウザ経由になります。ローカルのClaude Code（CLI／VS Code拡張）で設定するのが最も素直です。

---

## 4. 主なツールと使い分け

| ツール | 何を返すか | いつ使うか |
| --- | --- | --- |
| **`get_code`** | 選択範囲を React + Tailwind で生成 | 実装の起点 |
| **`get_variable_defs`** | 使われている変数・スタイル | **ハードコード回避** |
| **`get_code_connect_map`** | Figmaノード → 実コンポーネントの対応 | ★これが効くと精度が跳ね上がる |
| `get_screenshot` | 選択範囲の画像 | 見た目の確認・検証 |
| `use_figma` | キャンバスへの書き込み | 双方向連携（リモート版） |

### 実際の呼ばれ方

```
あなた: 「このフレームを実装して https://figma.com/design/...?node-id=5-120」

Claude Code の内部動作:
  1. get_code_connect_map    → 「node 5:121 は Button」「5:130 は Card」と判明
  2. get_variable_defs       → 「color-primary, spacing-4 を使っている」
  3. get_code                → レイアウト構造を取得
  4. リポジトリを読む         → 既存の規約・型・類似実装を確認
  5. 実装                    → <Card><Button variant="primary">…
```

**①②③の順で「意味」が与えられている**ことがポイントです。Code Connectが無いと1がスカになり、4以降の精度が落ちます。

## 5. 効果的な指示の出し方

### ❌ 効果が出にくい指示

```
「Figmaの画面を実装して」
```

範囲が曖昧で、既存コンポーネントを使うべきかも伝わりません。

### ✅ 効果的な指示

```
https://figma.com/design/AbCd/App?node-id=5-120 のカード部分を実装して。

- 配置先: src/features/dashboard/components/StatCard.tsx
- 既存の components/ui/ 配下のコンポーネントを必ず使う
- 色・余白はデザイントークンを使い、任意値記法は使わない
- Server Component にする（'use client' は付けない）
- 実装後に npm run lint と npm run build を通す
```

| 指示に含めるべき要素 | 理由 |
| --- | --- |
| **node-id付きURL** | 範囲を特定できる |
| **配置先パス** | ファイル構成の規約を守らせる |
| **既存コンポーネントの利用** | 再実装を防ぐ |
| **トークン利用の明示** | ハードコードを防ぐ |
| **Server/Client の指定** | [Next.js④](../nextjs/04-server-client-components.md) の設計を守らせる |
| **検証コマンド** | 自己検証させる |

> 🔑 これらを毎回書くのは大変なので、**`CLAUDE.md` に恒久ルールとして書きます**（→ [⑤](05-ai-workflow.md)）。そうすれば指示は「このフレームを実装して」だけで済みます。

## 6. 生成の単位を小さく保つ

**画面まるごとの一発生成は避けてください。**

| 単位 | 結果 |
| --- | --- |
| ❌ ページ全体 | 巨大な差分・レビュー不能・どこが違うか分からない |
| ⚠️ セクション単位 | 場合による |
| ✅ **コンポーネント単位** | レビュー可能・テスト可能・修正が局所的 |

```
推奨サイクル:
  1コンポーネント生成
      ↓
  型チェック・Lint・テスト
      ↓
  スクリーンショットで見た目確認
      ↓
  コミット
      ↓
  次のコンポーネントへ
```

このサイクルなら、途中で品質が崩れてもすぐ戻せます。

---

## 7. 検証の方法

生成後は**必ず検証**します。AIの自己申告を信用しないでください。

### ① 静的チェック

```bash
npm run lint        # ハードコード検出も含む（→ ②章）
npx tsc --noEmit    # 型チェック
npm run build       # 本番ビルドが通るか
```

### ② 見た目の比較

```
1. get_screenshot でFigmaの画像を取得
2. Playwrightで実装のスクリーンショットを撮る
3. 並べて比較する
```

```ts
// e2e/visual.spec.ts
import { test, expect } from '@playwright/test'

test('StatCard の見た目', async ({ page }) => {
  await page.goto('/dashboard')
  await expect(page.getByTestId('stat-card')).toHaveScreenshot('stat-card.png')
})
```

**AIに「Figmaと実装のスクショを比較して差分を報告して」と指示する**のも有効です。人間の目視より漏れが少なくなります。

### ③ アクセシビリティ

```bash
npx playwright test --grep a11y
```

生成コードでよく壊れるポイント（→ [React⑧](../react/08-practice-patterns.md#4-アクセシビリティa11y)）:

- [ ] `<div onClick>` になっていないか（`<button>` を使う）
- [ ] 入力に `<label>` が紐付いているか
- [ ] 画像に `alt` があるか
- [ ] フォーカス順序が破綻していないか

## 8. 双方向連携（`use_figma`）

リモート版には**キャンバスへ書き戻すツール**があります。

| 用途 | 例 |
| --- | --- |
| 実装済みマークを付ける | 対応完了したフレームに印 |
| 実装との差異をコメント | 「この余白はトークンに無いため8pxに調整」 |
| 実装から逆生成 | コードの状態をFigmaに反映 |

> 🚨 **書き込み権限は慎重に扱ってください。** AIがデザインファイルを直接変更できるということです。**まず読み取りのみで運用を始め**、必要性が明確になってから書き込みを許可することを推奨します。誤操作の影響がデザイナー全員に及びます。

## 9. トラブルシューティング

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| MCPに接続できない | 認証が切れている | `/mcp` で確認、再認証 |
| デスクトップ版が動かない | シート種別・プラン | リモート版に切り替える |
| `get_code` が汎用HTMLを返す | **Code Connect未設定** | → [③](03-code-connect.md) |
| 色がハードコードされる | 変数が使われていない | Figma側でVariablesを適用 |
| レイアウトが絶対配置になる | **Auto Layout未使用** | Figma側を修正 |
| 出力が毎回違う | コンポーネントが複雑すぎる | Figma側を分割する |
| 一部の状態しか出ない | 同上 | バリアントを整理する |
| 大量のトークンを消費する | 選択範囲が広すぎる | コンポーネント単位に絞る |

> 🔑 **上記の多くは「Figma側の問題」**です。AIやMCPの設定をいじる前に、**Figmaの構造（Auto Layout・Variables・コンポーネント化・命名）を疑ってください**。

---

## 10. この章のまとめ

- MCPは「AIに外部データを提供する共通規格」。Figma MCPでデザイン情報を直接読める
- **リモート版（`mcp.figma.com/mcp`）が推奨**。全プラン・全シートで動く
- デスクトップ版は **Dev/Fullシート＋有料プラン必須**。条件を満たさないと**無言で失敗**
- Claude Code へは **公式プラグイン（`/plugin`）** で接続する
- 主要ツールは `get_code` / `get_variable_defs` / **`get_code_connect_map`**
- 指示には **node-id・配置先・既存コンポーネント利用・トークン利用・検証コマンド**を含める
- **生成はコンポーネント単位**。画面まるごとはレビュー不能な差分を生む
- 検証は **Lint・型・ビルド・スクショ比較・a11y**。AIの自己申告を信用しない
- 🚨 **書き込み権限（`use_figma`）は最初は与えない**
- 出力が悪いときは、まず **Figma側の構造を疑う**
