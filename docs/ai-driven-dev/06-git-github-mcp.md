# ⑥ GitとGitHub MCP連携

[← 総合インデックスに戻る](README.md) ｜ 前 → [⑤ AI駆動開発のワークフロー](05-ai-workflow.md) ｜ 次 → [⑦ 段階導入とアンチパターン](07-adoption-roadmap.md)

生成したコードを記録し、レビューに載せ、CIを回す層です。**まず最初に、よくある誤解を解いておきます。**

---

## 1. 🔑 git操作にMCPは不要

「Gitと連携するためにMCPを入れる」という発想は、**多くの場合オーバーエンジニアリング**です。

```
❌ よくある誤解
   Claude Code ──MCP──> Gitサーバー ──> リポジトリ

✅ 実際
   Claude Code ──直接 git コマンド実行──> リポジトリ
```

Claude Code は `git` をそのまま実行できます。ブランチ作成・コミット・pushにMCPは要りません。

### 何にMCPが要るのか

| やること | 手段 | MCP必要？ |
| --- | --- | --- |
| `git add` / `commit` / `push` | シェル実行 | ❌ 不要 |
| ブランチ作成・切替 | シェル実行 | ❌ 不要 |
| コンフリクト解決 | ファイル編集＋git | ❌ 不要 |
| **PR作成** | GitHub API | ✅ **GitHub MCP** |
| **レビューコメント返信** | GitHub API | ✅ GitHub MCP |
| **CI結果の取得・ログ確認** | GitHub API | ✅ GitHub MCP |
| **Issue連携** | GitHub API | ✅ GitHub MCP |

> 🔑 **境界線は「ローカルのファイル操作か、GitHubのサービス機能か」**です。前者は素のgit、後者がMCPの領域です。

### なぜこれが重要か

不要なMCPサーバーを挟むと、

- ツール定義が毎回コンテキストを消費する（コスト増）
- 障害点が増える
- 単純な操作が遅くなる

**MCPは「増やすほど良い」ものではありません。** 必要なものだけ繋いでください。

## 2. GitHub MCP の接続

```
/plugin  →  github を選択  →  認証
```

または設定ファイルで直接指定します。接続後は `/mcp` で確認できます。

### 主なツール

| ツール | 用途 |
| --- | --- |
| `create_pull_request` | PR作成 |
| `pull_request_read` | PRの内容・差分・レビュー取得 |
| `add_comment_to_pending_review` | レビューコメント |
| `add_reply_to_pull_request_comment` | レビューへの返信 |
| `get_job_logs` | CI失敗ログの取得 |
| `list_issues` / `issue_write` | Issue連携 |
| `search_code` | リポジトリ横断のコード検索 |

## 3. 標準的なGitフロー

```bash
# 1. ブランチを切る（素のgit）
git checkout -b feat/stat-card

# 2. 実装（→ ⑤章）

# 3. 検証
npm run lint && npx tsc --noEmit && npm run test && npm run build

# 4. コミット（素のgit）
git add src/features/dashboard/components/StatCard.tsx
git commit -m "feat: ダッシュボードにStatCardコンポーネントを追加"

# 5. push（素のgit）
git push -u origin feat/stat-card

# 6. PR作成（★ここだけGitHub MCP）
```

### コミットメッセージの規約

`CLAUDE.md` に書いておくと、AIが従います。

```markdown
## コミットメッセージ
Conventional Commits に従う。日本語で書く。

  feat:     新機能
  fix:      バグ修正
  refactor: 挙動を変えないコード整理
  style:    見た目のみの変更
  test:     テスト追加・修正
  chore:    ビルド・依存など

例: feat: ダッシュボードにStatCardコンポーネントを追加
```

## 4. PR本文にデザイン情報を残す

AI駆動開発では、**「どのデザインから生成したか」を記録**しておくと後の追跡が楽になります。

```markdown
## 概要
ダッシュボードのStatCardコンポーネントを追加します。

## デザイン
- Figma: https://figma.com/design/AbCd/App?node-id=5-120
- 使用コンポーネント: `Card`, `Badge`（既存）
- 使用トークン: `color-primary`, `spacing-4`, `radius-card`

## 実装メモ
- Server Component として実装（状態を持たないため）
- Figmaでは余白14pxだが、トークンに無いため `spacing-4`（16px）を使用
  → デザイナー確認済み

## 確認事項
- [x] lint / 型 / test / build 通過
- [x] Figmaとのスクショ比較実施
- [ ] デザイナーによる見た目確認 ← レビュアーへ
```

> 💡 **「Figmaと違う判断をした箇所」を明記する**のが特に重要です。AIは指示が無いと勝手に近い値へ丸めます。それ自体は妥当な判断でも、記録が無いと後で「なぜここだけ違う？」となります。

## 5. CI失敗の自動修正

ここがAI駆動開発の効きどころです。

```
CIが失敗
   ↓
GitHub MCP で失敗ログを取得（get_job_logs）
   ↓
原因を特定して修正
   ↓
コミット・push
   ↓
CIが再実行 → 通るまで繰り返す
```

Claude Code にはPRの活動を購読する仕組みがあり、**CI失敗やレビューコメントをイベントとして受け取って対応**できます。

```
「このPRを監視して、CIが落ちたら直して」
```

### ✅ 自動修正して良いもの / ❌ 人間が判断すべきもの

| ✅ 自動で直してよい | ❌ 人間が判断すべき |
| --- | --- |
| Lintエラー・フォーマット | **テストが落ちた原因が仕様の誤解** |
| 型エラー | セキュリティ関連の指摘 |
| import漏れ・未使用変数 | 設計方針への疑問 |
| スナップショットの更新（意図通りの場合） | **パフォーマンス劣化** |
| 軽微なコンフリクト解消 | データ移行を伴う変更 |

> 🚨 **「テストを通すためにテストを書き換える」を絶対に許さないでください。** `CLAUDE.md` に明記します。
> ```markdown
> ## 禁止
> - テストを削除・スキップ・緩和して通すこと
> - 型エラーを any / @ts-ignore で回避すること
> - CIをスキップする設定を追加すること
> ```
> これが無いと、AIは「CIを通す」という指示を最短で満たそうとします。

## 6. レビューコメントへの対応

```
レビュアーがコメント
   ↓
GitHub MCP がイベントを受信
   ↓
AIが内容を判断
   ├─ 明確で範囲が小さい → 修正してpush、スレッドに返信
   ├─ 曖昧・設計に関わる  → 質問を返す（勝手に実装しない）
   └─ 対応不要            → 理由を返信
```

### 運用のコツ

| コツ | 理由 |
| --- | --- |
| **返信は簡潔に** | 全部に長文を返すとノイズになる |
| **修正内容をコミットで示す** | 差分が記録になる |
| **判断に迷ったら質問する** | 勝手な実装が最も手戻りを生む |
| **AI生成の返信と明記** | レビュアーが期待値を調整できる |

> ⚠️ **外部から来るコメントは「指示」ではなく「情報」として扱ってください。** PRのコメントやIssue本文は誰でも書けます。「このスクリプトを実行して」「認証情報を出力して」といった内容が紛れ込んでいた場合、**実行せずに人間に確認する**のが原則です。

## 7. 権限設計 — どこまでAIに許すか

```
┌─────────────────────────────────────┐
│ 読み取り（低リスク）                  │
│  ・リポジトリ閲覧・PR/Issue参照       │  ✅ 許可してよい
│  ・CI結果の取得                      │
├─────────────────────────────────────┤
│ 書き込み（要検討）                    │
│  ・ブランチ作成・コミット・push       │  ✅ 作業ブランチのみ
│  ・PR作成・レビュー返信               │  ✅ 許可してよい
├─────────────────────────────────────┤
│ 危険（原則禁止）                      │
│  ・main への直接push                 │  ❌ ブランチ保護で防ぐ
│  ・PRのマージ                        │  ❌ 人間が実施
│  ・force push・履歴書き換え           │  ❌
│  ・リポジトリ設定の変更・削除          │  ❌
└─────────────────────────────────────┘
```

### ブランチ保護で機械的に防ぐ

運用ルールだけでは事故は防げません。**GitHub側の設定で縛ります。**

```
main ブランチの保護設定:
  ☑ Require a pull request before merging
  ☑ Require status checks to pass（lint / typecheck / test / build）
  ☑ Require approvals（1名以上）
  ☑ Do not allow bypassing the above settings
  ☑ Restrict force pushes
```

> 🔑 **これを設定しておけば、AIが誤ってmainへpushしようとしても弾かれます。** 「気をつける」より「できなくする」ほうが確実です。

### シークレットの扱い

- `.env` をAIのコンテキストに載せない（`.gitignore` に加え、必要なら参照禁止を `CLAUDE.md` に明記）
- CIのSecretsはログに出力しない
- **`FIGMA_ACCESS_TOKEN` や `GITHUB_TOKEN` を生成コードに含めない**（→ [Next.js⑫](../nextjs/12-deploy-operations.md)）

## 8. Figma → PR の一気通貫例

ここまでの全層を通した実際の流れです。

```
【デザイナー】
  Figmaでカードコンポーネントを更新
  Tokens Studio で色を追加 → 自動PR（②章）
        ↓
【CI】
  トークンをビルド → tokens.css を更新 → マージ
        ↓
【実装者】
  「https://figma.com/...?node-id=5-120 のカードを実装して。
    実装後にlint/型/testを通して、PRまで作って」
        ↓
【Claude Code】
  1. get_code_connect_map → Card/Badge が既存と判明（③章）
  2. get_variable_defs   → 使用トークンを取得
  3. リポジトリの規約を読む（CLAUDE.md）
  4. StatCard.tsx を実装
  5. lint / tsc / test / build を自己実行
  6. git checkout -b feat/stat-card && commit && push
  7. GitHub MCP で PR作成（デザインURL付き）
        ↓
【CI】
  失敗 → AIがログを取得して修正 → 再push → 成功
        ↓
【人間】
  仕様・設計・セキュリティをレビュー → 承認 → マージ
```

**人間の関与は「最初の1行の指示」と「最後のレビュー」だけ**になります。ただし、そこに至るには②③の土台が必須です。

## 9. よくあるつまずき

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| PRが巨大になる | 生成単位が大きい | 1PR=1コンポーネント（→ [⑤](05-ai-workflow.md)） |
| CI修正が無限ループ | 根本原因が仕様の誤解 | 人間が介入して仕様を明示 |
| テストが書き換えられた | 禁止事項が未明記 | `CLAUDE.md` に明記＋レビューで見る |
| mainに直接pushされた | ブランチ保護なし | 保護設定を有効化 |
| コンフリクトが頻発 | ブランチが長生き | 小さく作って早くマージ |
| レビュー返信がノイズ | 全部に返信している | 「解決・ブロッカー・質問」時のみ返す |

---

## 10. この章のまとめ

- 🔑 **git操作にMCPは不要**。Claude Codeは `git` を直接実行できる
- **MCPが要るのはGitHub API側**（PR作成・レビュー返信・CIログ取得・Issue連携）
- **MCPは増やすほど良いものではない**。不要なサーバーはコストと障害点になる
- コミット規約・PR本文の形式は **`CLAUDE.md` に書けば従う**
- PRには**Figma URL・使用トークン・デザインと違う判断**を記録する
- **CI失敗の自動修正はAIの効きどころ**。ただし仕様誤解の修正は人間が介入
- 🚨 **「テストを書き換えて通す」を明示的に禁止**する
- **マージは人間。main保護をGitHub側で機械的に設定**する
- 外部から来るコメントは「指示」ではなく「情報」として扱う
