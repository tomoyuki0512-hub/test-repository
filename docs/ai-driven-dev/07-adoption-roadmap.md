# ⑦ 段階導入とアンチパターン

[← 総合インデックスに戻る](README.md) ｜ 前 → [⑥ GitとGitHub MCP連携](06-git-github-mcp.md) ｜ 次 → [用語集](glossary.md)

**導入に失敗するチームの大半は、順番を間違えているだけ**です。この章では正しい順序と、失敗パターンをまとめます。

---

## 1. 🚨 最も多い失敗：順番が逆

```
❌ 失敗する順番
  1. Figma MCPを繋ぐ           ← ここから始めてしまう
  2. 生成コードの品質が低い
  3. プロンプトを工夫する
  4. それでも改善しない
  5. 「AIは使えない」と結論づける

✅ 成功する順番
  1. コード側のデザインシステムを用意
  2. Figmaを構造化する
  3. トークンを整えて同期
  4. Code Connect を張る
  5. ★ここで初めてFigma MCPを繋ぐ
  6. Git/CI連携で回す
```

**MCPは「最後に繋ぐもの」**です。土台が無い状態で繋いでも、AIには「色のついた四角形の集まり」しか見えません。

---

## 2. 段階導入ロードマップ

### フェーズ0：現状評価（1日）

まず自分たちの状態を確認します。

| 確認項目 | Yes / No |
| --- | --- |
| コード側に共通UIコンポーネントがある（`components/ui/`） | |
| FigmaでAuto Layoutが使われている | |
| Figmaでコンポーネント化されている | |
| Figma Variables（色・余白）を使っている | |
| Figmaの命名が英語で構造化されている | |
| Organizationプラン以上を契約できる | |
| CIがある（lint / 型 / test / build） | |
| PRレビューの文化がある | |

```
Yesが6個以上 → フェーズ1から順調に進められます
Yesが3〜5個  → 不足部分の整備から。3〜4週間見てください
Yesが2個以下 → まず土台作り。AI連携は2〜3ヶ月後の話です
```

> 🔑 **Noが多いこと自体は問題ありません。** 問題は「Noのまま MCP を繋ぐこと」です。

### フェーズ1：コード側の土台（1〜2週間）

```
□ components/ui/ に共通コンポーネントを整備（shadcn/ui 推奨）
□ Button / Input / Select / Checkbox / Radio / Card を用意
□ CIを整える（lint / typecheck / test / build）
□ CLAUDE.md に配置ルールと禁止事項を書く（→ ⑤章）
```

**この時点でAIは使えます。** Figma連携は無くても、規約が明文化されていればAIの出力は安定します。

### フェーズ2：Figmaの構造化（1〜2週間・デザイナー主導）

```
□ Auto Layout に置き換える（絶対配置をやめる）
□ 繰り返す要素をコンポーネント化する
□ 命名を英語・階層構造に統一（「Frame 427」を撲滅）
□ バリアントを整理する（状態を漏れなく作る）
□ Variables で色・余白を定義（3階層設計 → ②章）
```

> ⚠️ **ここを飛ばすと、以降のすべてが無駄になります。** デザイナーの協力が得られない場合、導入自体を見送る判断も妥当です。

### フェーズ3：トークン同期（3〜5日）

```
□ Tokens Studio を導入し、GitHubへ同期
□ Style Dictionary で CSS変数を生成
□ Tailwind v4 の @theme inline に接続
□ 生成物をコミットする
□ ハードコード検出のLintを追加  ← ★効果大
□ CIでトークンビルドを検証
```

→ 詳細は [② デザイントークン連携](02-design-tokens.md)

**この時点で効果が出始めます。** AIにFigmaを見せなくても、トークンが揃っているだけでハードコードは激減します。

### フェーズ4：Code Connect（1〜2週間）

```
□ Organizationプランを確認
□ @figma/code-connect をインストール
□ figma.config.json（importPaths を忘れずに）
□ 優先度1の5個に .figma.tsx を作成
   Button / Input / Select / Checkbox / Radio
□ npx figma connect publish
□ CIで parse を必須化
□ 「新規コンポーネントは .figma.tsx もセット」をルール化
```

→ 詳細は [③ Code Connect](03-code-connect.md)

**ここが最大の投資であり、最大のリターン**です。

### フェーズ5：Figma MCP接続（1日）

```
□ Claude Code に公式プラグインで接続
□ 読み取りのみで開始（use_figma の書き込みは後回し）
□ 1コンポーネントで試す
□ 出力を確認 → Code Connectが効いているか検証
```

→ 詳細は [④ Figma MCPの接続と使い方](04-figma-mcp.md)

### フェーズ6：Git/CI連携（3〜5日）

```
□ GitHub MCP を接続
□ main のブランチ保護を設定
□ PR本文テンプレート（Figma URL・トークン・判断メモ）
□ CI失敗の自動修正を試す
□ 「テスト書き換え禁止」を CLAUDE.md に明記
```

→ 詳細は [⑥ GitとGitHub MCP連携](06-git-github-mcp.md)

## 3. アンチパターン集

### ❌ 1. MCPから始める

**最頻出。** 前述のとおり順番が逆です。土台無しのMCPは期待外れに終わります。

### ❌ 2. 生成コードをそのままコミットする

```tsx
// Figma MCPの出力をそのまま貼った例
<div className="absolute left-[24px] top-[16px] w-[328px] h-[120px] bg-[#FFFFFF]">
```

絶対配置・ハードコード・レスポンシブ非対応。**レビューで必ず落としてください。**

### ❌ 3. 画面まるごと一発生成

+2,400行のPRはレビューできません。**1PR = 1コンポーネント**（→ [⑤](05-ai-workflow.md)）。

### ❌ 4. Figmaが汚いままAIに読ませる

```
「Frame 427」「Group 12」「Rectangle 5」
絶対配置、コンポーネント化なし、色は直接指定
```

**汚さがそのままコードになります。** Figma整理のほうが投資対効果が高いです。

### ❌ 5. Code Connect を作って放置

Figma側のプロパティ名が変わると静かに壊れます。**CIで `figma connect parse` を必須化**してください。

### ❌ 6. 「AIに全部任せてコスト削減」という期待

レビュー工数はむしろ**重要度が上がります**。削減されるのは「手を動かす時間」であって「考える時間」ではありません。

### ❌ 7. 自動マージ

CIが通ることと仕様を満たすことは別です。**マージは人間**（→ [⑥](06-git-github-mcp.md)）。

### ❌ 8. MCPサーバーを繋ぎすぎる

ツール定義が毎回コンテキストを消費し、コスト増と精度低下を招きます。**必要なものだけ。**

### ❌ 9. デザイナーを巻き込まない

実装側だけで進めると、フェーズ2で必ず詰まります。**最初から一緒に始めてください。**

### ❌ 10. 「テストを通す」を最短で満たさせる

禁止事項が未明記だと、AIはテストを緩めて通します。**`CLAUDE.md` に明記**してください。

## 4. 導入チェックリスト

### 着手前

- [ ] Figmaプランを確認した（Code ConnectにはOrganization以上が必要）
- [ ] デザイナーの協力が得られる
- [ ] Figma整理の工数を確保した
- [ ] レビュー体制がある
- [ ] 「85%は動く、15%は手直し」という期待値をチームで共有した

### フェーズ1〜3完了時

- [ ] `components/ui/` に共通コンポーネントがある
- [ ] トークンがGit経由で同期されている
- [ ] ハードコード検出のLintが動いている
- [ ] CIで lint / typecheck / test / build が回る
- [ ] `CLAUDE.md` に配置ルール・禁止事項がある

### フェーズ4〜6完了時

- [ ] 主要5コンポーネントに Code Connect がある
- [ ] CIで `figma connect parse` が動く
- [ ] Figma MCPが接続され、`get_code_connect_map` が対応を返す
- [ ] mainがブランチ保護されている
- [ ] PR本文にFigma URLが記録される運用になっている
- [ ] 「テスト書き換え禁止」が明記されている

## 5. トラブル時の切り分けフロー

```
期待した品質が出ない
  │
  ├─ ハードコードが多い
  │   → トークン整備・Lint（フェーズ3）を確認
  │
  ├─ 既存コンポーネントを使わない
  │   → Code Connect（フェーズ4）を確認
  │   → CLAUDE.md に「既存優先」と書いたか
  │
  ├─ 絶対配置になる
  │   → Figma側のAuto Layout（フェーズ2）を確認
  │
  ├─ ファイル配置がバラバラ
  │   → CLAUDE.md の配置ルールを確認
  │
  ├─ 出力が毎回違う
  │   → Figma側のコンポーネントが複雑すぎる
  │
  ├─ PRが巨大
  │   → 生成単位のルールを確認（1PR=1コンポーネント）
  │
  └─ 状態遷移・データ連携が変
      → これはAIの領域外。人間が仕様を与える
```

**大半は「AIの問題」ではなく「土台の問題」**です。

---

## 6. 効果測定

感覚ではなく数値で判断してください。**導入前にベースラインを取っておく**のが重要です。

| 指標 | 測り方 | 期待する変化 |
| --- | --- | --- |
| **デザイン受領→PR作成のリードタイム** | Issue作成〜PR作成の時間 | 短縮 |
| **デザインレビューの指摘件数** | PRのレビューコメント数 | **減少（最重要）** |
| **ハードコードの出現数** | Lintエラー数を計測 | ゼロへ |
| **コンポーネント再実装の件数** | 類似コンポーネントの数 | 減少 |
| **手戻り工数** | 差し戻しPRの割合 | 減少 |
| **AI利用コスト** | 月額 | 工数削減分と比較 |

> 🔑 **「デザインレビューの指摘件数」が最も本質的な指標**です。ここが減っていれば、デザインと実装のズレが構造的に減っている証拠になります。逆にここが減らないなら、フェーズ2〜4のどこかが機能していません。

---

## 7. 導入しない判断も正しい

次に当てはまるなら、**見送るほうが合理的**です。

```
・画面数が少ない（10画面未満で今後も増えない）
・デザインが毎回ゼロから作られる（システム化されていない）
・デザイナーがFigma整理の工数を取れない
・Professionalプランから上げられず、Code Connectが使えない
・レビュー体制が無い
・プロトタイプ段階で仕様が毎日変わる
```

この場合でも、**フェーズ1（コード側の整備＋CLAUDE.md）とフェーズ3（トークン）だけは価値があります**。Figma連携抜きでAIを使うだけでも十分に効果が出ます。

---

## 8. この章のまとめ

- 🚨 **最も多い失敗は「MCPから始めること」**。MCPは最後に繋ぐ
- 正しい順序：**コード側の土台 → Figma構造化 → トークン → Code Connect → MCP → Git連携**
- **フェーズ0の現状評価**で、自分たちがどこから始めるべきか判断する
- **フェーズ2（Figma構造化）を飛ばすと以降がすべて無駄になる**
- アンチパターンの筆頭は「生成コードをそのままコミット」「画面まるごと生成」「Figmaが汚いまま」
- **効果測定は「デザインレビューの指摘件数」が最重要指標**
- **導入しない判断も正しい**。その場合もフェーズ1・3は単体で価値がある
