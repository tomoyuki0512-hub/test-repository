# ① 全体像と導入判断 — 何ができて、何ができないか

[← 総合インデックスに戻る](README.md) ｜ 次 → [② デザイントークン連携](02-design-tokens.md)

導入を判断するための章です。**できることを誇張せず、できないことを明示**します。ここだけ読めば「自分たちがやるべきか」が決まります。

---

## 1. そもそも何が起きるのか

理想の1サイクルはこうなります。

```
デザイナーがFigmaでコンポーネントを更新
        ↓
実装者がClaude Codeに指示
  「Figmaのこのフレームを実装して」（URLを渡す）
        ↓
Claude Code が Figma MCP でデザイン情報を取得
  ・レイアウト構造
  ・使われている変数（色・余白）
  ・★Code Connectの対応表 → 「これはButtonコンポーネントだ」
        ↓
リポジトリの既存コード・規約・型を読んで実装
        ↓
テスト実行 → ブランチ作成 → コミット → PR作成
        ↓
CIが落ちたら自動で修正 → 人間がレビュー → マージ
```

**人間の仕事は「指示」と「レビュー」に寄ります。** 手を動かす部分が減るのであって、判断が要らなくなるわけではありません。

---

## 2. 4層アーキテクチャの意味

[README](README.md#2-全体アーキテクチャ4層) の図を、なぜこの構造なのかという観点で補足します。

```
┌─ ① トークン層 ─────────────────────────┐
│ 「この青は #3B82F6 ではなく brand-500」  │ ← 値の意味を与える
├─ ② 対応表層 ───────────────────────────┤
│ 「このFigmaノードは <Button> である」    │ ← 構造の意味を与える
├─ ③ AI実装層 ───────────────────────────┤
│ 意味を与えられた情報をもとに実装         │
├─ ④ Git層 ──────────────────────────────┤
│ 記録・レビュー・自動修正                 │
└────────────────────────────────────────┘
```

**①と②は「AIに意味を教える層」**です。これが無いと、AIには「青い角丸の四角形」としか見えません。だから `<div className="bg-[#3B82F6] rounded-[6px]">` が出てくるわけです。

逆に言えば、**①②を整えることは、AIを使わなくてもデザインシステムの資産として価値があります**。ここが投資判断のポイントです。

## 3. できること / できないこと

### ✅ 現実的にできること

| できること | 補足 |
| --- | --- |
| 既存コンポーネントを組み合わせた**画面の実装** | Code Connectがある前提 |
| デザイントークンに沿った**スタイリング** | ハードコード値が消える |
| レイアウト構造（Flex/Grid）の**再現** | Auto Layoutが正しく組まれていれば精度が高い |
| **レスポンシブの雛形**生成 | 微調整は人間 |
| 命名・ファイル配置の**規約遵守** | `CLAUDE.md` に書けば従う（→ [⑤](05-ai-workflow.md)） |
| **PR作成・CI失敗の自動修正** | → [⑥](06-git-github-mcp.md) |
| デザイン変更の**差分反映** | 「このボタンの余白が変わった」等 |

### ❌ できない・期待すべきでないこと

| できないこと | 理由 |
| --- | --- |
| **複雑な状態遷移の実装** | Figmaに情報が無い。仕様は人間が与える |
| **データ連携**（API・DB） | 生成されるのは構造の雛形まで |
| **チャート・可視化の実装** | プレースホルダは出るが、ライブラリ統合は人間 |
| **アクセシビリティの完全担保** | 補助はするが、キーボード操作・スクリーンリーダー検証は人間 |
| **デザインの良し悪しの判断** | AIはFigmaを正としてしまう |
| **既存の汚い設計の自動改善** | 規約が無ければ、汚さを再生産する |
| **一貫性のある大規模生成** | コンポーネントの複雑さによって出力の質がぶれる |

> 🔑 **実測の目安**：「**85%は動く。残り15%は予測可能で対処可能**」という評価が実務での相場観です。100%を期待すると必ず失望します。逆に「15%は手を入れる前提」で運用すると、十分に投資対効果が出ます。

### 出力がぶれる典型

同じFigmaファイル内でも、**コンポーネントの複雑さによって出力の粒度が変わります**。

```
シンプルなボタン    → 全バリアント・全状態を含むコードが出る
複雑なテーブル      → デフォルト状態だけのコードが出る
```

「なぜこの部分だけ手抜きなのか」と感じたら、Figma側のコンポーネント構造が複雑すぎるサインです。**Figma側を整理するほうが早い**ことが多くあります。

## 4. プラン要件 — 実質的な足切りライン

ここが導入可否の分かれ目です。

| 項目 | 必要な条件 | 備考 |
| --- | --- | --- |
| Figma MCPサーバー（リモート） | **全プラン・全シートで利用可** | ベータ。現在無料 |
| Figma MCPサーバー（デスクトップ） | **Dev または Full シート＋有料プラン** | Figmaアプリ起動中のみ動作 |
| **Code Connect** | **Organization プラン以上** | ★ここが足切り |
| Dev Mode | 有料プラン | — |

### 判断フロー

```
Organizationプラン以上を契約している/できる？
  │
  ├─ Yes → ✅ フル構成が可能。②③から着手（→ ⑦章）
  │
  └─ No  → Code Connect が使えない
            │
            ├─ トークン層（②）だけ導入する
            │   → Tokens Studio + Style Dictionary は
            │      プラン制約が緩く、単体でも価値がある ✅
            │
            └─ Figma MCP は「参考情報の取得」に留める
                → レイアウト構造の把握・変数の確認には有用
                → コード生成の精度は期待しない
```

> 💡 **Professionalプランでの現実解**：Code Connectは使えませんが、**①トークン層＋⑤AIワークフロー＋⑥Git連携**だけでも十分に効果があります。「Figmaを見ながらAIに実装させる」際、トークンが揃っているだけでハードコードは大きく減ります。

## 5. 費用対効果をどう見るか

### コストの内訳

| 種類 | 内容 |
| --- | --- |
| **ライセンス** | Figmaプラン差額（Professional → Organization） |
| **初期構築** | トークン整備・Code Connect作成・CI構築 |
| **継続運用** | Code Connectの保守（コンポーネント追加・変更時） |
| **将来コスト** | Figma MCPの従量課金（ベータ終了後） |
| **AI利用料** | Claude等の利用料 |

### 効果が出やすい / 出にくい

| ✅ 効果が出やすい | ❌ 効果が出にくい |
| --- | --- |
| デザインシステムが**すでにある** | デザインが毎回ゼロから作られる |
| 同種の画面を**多数作る**（管理画面・LP群） | 画面が数枚しかない |
| デザイナーと実装者が**分かれている** | 一人で両方やっている |
| Figmaの**Auto Layoutが整っている** | 絶対配置だらけのFigma |
| コンポーネントが**命名・整理されている** | 「Frame 427」だらけ |

> 🚨 **Figma側が汚いと、投資は回収できません。** 「Frame 427」「Group 12」のような命名、Auto Layout未使用、コンポーネント化されていないデザイン——この状態でAIに読ませても、汚さがそのままコードになります。**まずFigmaの整理が先**です。

### 定量的に測る

導入効果は感覚ではなく数値で見てください（→ [⑦](07-adoption-roadmap.md#6-効果測定)）。

- デザイン受領からPR作成までのリードタイム
- 実装後のデザインレビュー指摘件数（**ここが減れば成功**）
- ハードコードされた色・余白の出現数（Lintで計測可能）
- 手戻り工数

## 6. 向いているチーム / 向いていないチーム

```
✅ 向いている
   ・デザインシステムを運用している、または作る意思がある
   ・Organizationプラン以上を許容できる
   ・Figmaの構造化にデザイナーが協力してくれる
   ・レビュー体制がある（生成コードを検証できる）

⚠️ 慎重に検討
   ・デザイナーが1人で手一杯（Figma整理の工数が取れない）
   ・プロトタイプ段階で仕様が毎日変わる
   ・コンポーネント設計がまだ固まっていない

❌ 向いていない
   ・Figmaが絶対配置・命名なしの状態で改善予定がない
   ・レビューせずマージする文化
   ・「AIに全部やらせてコストを下げたい」という期待
```

## 7. セキュリティ・ガバナンスの観点

AIとMCPを開発フローに入れる以上、次は事前に決めておいてください。

| 論点 | 決めること |
| --- | --- |
| **MCPの権限範囲** | Figma MCPに書き込み権限（`use_figma`）を与えるか |
| **GitHub MCPの権限** | PR作成まで許すか、マージまで許すか（**マージは人間推奨**） |
| **秘密情報** | `.env`・APIキーをAIのコンテキストに載せない仕組み |
| **生成コードの責任** | レビュー必須。**AI生成であることを理由に検証を省かない** |
| **ライセンス** | 生成コードに外部由来のコードが混ざらないか |
| **監査ログ** | 誰がいつどの指示で生成したかを追えるか（PRに記録） |

> 🚨 **自動マージは推奨しません。** CIが通ることと、仕様を満たすことは別です。特に認証・認可・課金に関わる箇所は必ず人間がレビューしてください（→ [Next.js⑥](../nextjs/06-server-actions-forms.md)・[⑧](../nextjs/08-auth-database.md)）。

## 8. この章のまとめ

- 理想サイクルは「**指示 → 実装 → テスト → PR → レビュー**」。人間の仕事は指示とレビューに寄る
- ①トークン層・②対応表層は「**AIに意味を教える層**」。無いと「青い四角」としか見えない
- **できるのは「既存部品の組み立て」**。状態遷移・データ連携・a11y検証は人間の仕事
- 実測の相場観は「**85%は動く、15%は予測可能な手直し**」
- **Code Connect には Organization プラン以上が必要**。ここが足切りライン
- Professional なら **トークン層だけでも導入価値がある**
- 🚨 **Figma側が汚いと投資は回収できない**。まずFigmaの整理が先
- **自動マージはしない**。生成コードもレビューは必須
