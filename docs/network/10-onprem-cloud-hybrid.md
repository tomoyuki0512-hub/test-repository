# ⑩ オンプレ・クラウド・ハイブリッド構成

> **この章のゴール**：3つの配置方式を、構成図・コスト構造・向き不向きで比較できるようになる。そして「うちは何をどこに置くべきか」を、感覚ではなく判断基準で決められるようになる。

← [⑨ 規模別ネットワーク構成パターン](09-scale-patterns.md) ／ 次章 → [⑪ 監視・運用・トラブルシューティング](11-operations.md)

---

## 0. まず結論（30秒）

```
【オンプレ】     全部自社の設備に置く
                → 制御できる。安定する。でも重い（初期投資・拡張の遅さ・災害耐性）

【クラウド】     全部事業者のサービスを使う
                → 速い。軽い。でも通信費と依存が発生する

【ハイブリッド】  適材適所で分ける
                → 現実の大多数はここ。ただし最も設計と運用が難しい
```

そして最も伝えたいことがこれです。

> ⚠️ **「クラウドにすれば安くなる」は条件付きです。**
> 安くなるのは **①需要の変動が大きい ②小さく始めて捨てられる ③運用人件費を削減できる** ケース。
> **常時フル稼働で、データ転送量が大きく、性能要件が固定的なワークロードは、オンプレの方が安いことが普通にあります。**
> 実際、クラウドからオンプレに戻す（リパトリエーション）事例も珍しくありません。

---

## 1. 3方式の全体比較

| 観点 | オンプレ | クラウド | ハイブリッド |
| --- | --- | --- | --- |
| **初期費用** | **高い（CAPEX）** | ほぼゼロ | 中 |
| **月額費用** | 低い（電気・保守） | **従量（OPEX）** | 両方＋接続回線 |
| **調達スピード** | **数週間〜数ヶ月** | **数分** | 部分により異なる |
| **拡張性** | 機器追加が必要 | **即時・自動** | 部分的 |
| **性能の予測可能性** | **高い（占有）** | 変動あり | 混在 |
| **レイテンシ** | **社内は最速** | 経路次第 | 設計次第 |
| **災害耐性** | **自社で作り込む必要** | **標準で複数AZ/リージョン** | 組み合わせ可能 |
| **データの所在** | **完全に自社管理** | 事業者のDC | 分離可能 |
| **運用負荷** | 高い（機器・電源・空調） | **低い** | **最も高い（二重管理）** |
| **必要スキル** | 物理・機器 | クラウド・IaC | **両方** |
| **ベンダー依存** | 機器ベンダー | **クラウド事業者** | 両方 |

## 2. パターンA：オンプレ構成

### 2-1. 構成図

```
                    インターネット
                          │
                ┌─────────┴──────────┐
                │   NGFW（HA構成）     │
                └─────────┬──────────┘
                          │
              ┌───────────┴───────────┐
              │       DMZ セグメント    │
              │  公開Web / リバースプロキシ / メールGW │
              └───────────┬───────────┘
                          │
              ┌───────────┴───────────┐
              │    コアL3スイッチ（冗長）│
              └──┬──────────┬─────────┘
                 │          │
        ┌────────┴───┐  ┌───┴─────────────────┐
        │クライアント  │  │  サーバーセグメント    │
        │ VLAN群      │  │ ┌─────────────────┐ │
        └────────────┘  │ │ 仮想化基盤        │ │
                        │ │ (VMware/Hyper-V/ │ │
                        │ │  Proxmox/KVM)    │ │
                        │ └────────┬────────┘ │
                        │ ┌────────┴────────┐ │
                        │ │ 共有ストレージ    │ │
                        │ │ (SAN / NAS)      │ │
                        │ └─────────────────┘ │
                        │ ＋ バックアップ装置    │
                        └─────────────────────┘
                        
   ＋ UPS・発電機・空調・入退室管理（サーバールーム設備）
   ＋ 遠隔地バックアップ（DR拠点 or クラウドへのバックアップ）
```

### 2-2. 向いているケース

| ケース | 理由 |
| --- | --- |
| **低遅延が必須**（工場の制御・トレーディング） | ネットワーク遅延が事業に直結する |
| **データを外に出せない** | 法規制・契約・機密度（防衛・一部の医療・金融） |
| **常時フル稼働・大量データ** | 従量課金だとクラウドの方が高くなる |
| **既存資産がまだ償却中** | 捨てるとコストが二重になる |
| **回線が細い／不安定な立地** | クラウド依存はリスク |
| **特殊なハードウェアが必要** | 専用機器・レガシーな接続方式 |

### 2-3. コスト構造の実際

```
【5年間の総コスト（TCO）で考える】

  初期投資（CAPEX）
    サーバー・ストレージ    1,500万円
    ネットワーク機器          800万円
    ソフトウェアライセンス     500万円
    構築費（設計・工事）       600万円
    ────────────────────────────
    小計                    3,400万円

  運用費（5年分）
    保守契約（年 機器費の12%）  1,380万円
    電気代（年150万円）          750万円
    サーバールーム設備・空調      300万円
    運用人件費（0.5人 × 5年）  3,000万円  ← ★見落とされがち
    ────────────────────────────
    小計                     5,430万円

  5年TCO 合計              8,830万円
```

> ⚠️ **オンプレのコスト比較で最も見落とされるのが「運用人件費」と「電気代」**です。機器の購入費だけを見て「クラウドより安い」と結論づけると、実態を大きく外します。逆に、既に人員がいて他の業務と兼任できるなら、この費用は限界費用としては小さくなります。

### 2-4. オンプレの設計ポイント

| 項目 | 推奨 |
| --- | --- |
| **仮想化** | 物理サーバー1台1用途は非効率。**必ず仮想化基盤に集約** |
| **ストレージ冗長** | RAIDだけでなく、**コントローラも冗長**に |
| **電源** | UPS 必須。**2系統受電＋発電機**があれば理想 |
| **バックアップ** | **3-2-1ルール**。うち1つは**オフライン/イミュータブル**（ランサム対策） |
| **DR** | 遠隔地にバックアップ or DR拠点。**クラウドをDR先にするのが今の主流** |
| **監視** | ハードウェア障害（ディスク・電源・ファン）の予兆検知 |
| **ライフサイクル** | 5年更改。**EOLの2年前から予算化** |

## 3. パターンB：クラウド構成

### 3-1. 構成図

```
   利用者（オフィス・在宅・出張先）
        │
        │  インターネット
        ↓
   ┌────────────────────────────────────────────┐
   │  CDN / WAF / DDoS防御（CloudFront・Front Door等）│
   └───────────────────┬────────────────────────┘
                       │
   ┌───────────────────┴────────────────────────┐
   │  クラウド VPC 10.100.0.0/16                  │
   │                                             │
   │   ┌─────────── AZ-a ────┐ ┌──── AZ-c ─────┐ │
   │   │ パブリックサブネット   │ │ パブリック     │ │
   │   │  ┌───────────────────────────────┐    │ │
   │   │  │   ロードバランサ（ALB）         │    │ │
   │   │  └────┬─────────────────┬────────┘    │ │
   │   │ プライベートサブネット  │ │ プライベート  │ │
   │   │  ┌────┴────┐        ┌───┴─────┐      │ │
   │   │  │ App      │        │ App      │      │ │
   │   │  │(EC2/ECS/ │        │(EC2/ECS/ │      │ │
   │   │  │ Lambda)  │        │ Lambda)  │      │ │
   │   │  └────┬────┘        └───┬─────┘      │ │
   │   │ DBサブネット           │ │             │ │
   │   │  ┌────┴────┐        ┌───┴─────┐      │ │
   │   │  │ DB Primary│◄──────►│DB Standby│     │ │
   │   │  └─────────┘        └─────────┘      │ │
   │   └──────────────────────┘ └─────────────┘ │
   │                                             │
   │   ＋ VPCエンドポイント（NAT費用削減）          │
   │   ＋ オブジェクトストレージ（S3等）            │
   └─────────────────────────────────────────────┘

   ID・端末管理：Entra ID / Okta（SSO＋MFA＋条件付きアクセス）
   セキュリティ：SASE / SSE（→ ⑥章）
   オフィス側：インターネット回線 ＋ Wi-Fi ＋ 小型ルータ のみ
```

### 3-2. 「オフィスに何も置かない」構成が成立する

クラウド全振りの最大のインパクトは、**オフィスのネットワークが極端にシンプルになる**ことです。

```
【従来のオフィス】
  UTM・サーバー・ストレージ・バックアップ装置・
  APコントローラ・電話交換機・UPS・サーバールーム

【クラウド全振りのオフィス】
  インターネット回線 ＋ ルータ ＋ スイッチ ＋ Wi-Fi AP
  （必要ならローカルNASのみ）
  
  → サーバールーム不要。空調・電源工事も不要
  → 移転が圧倒的に楽
```

### 3-3. 向いているケース

| ケース | 理由 |
| --- | --- |
| **需要の変動が大きい** | 繁忙期だけスケールできる。オンプレはピークに合わせた投資が必要 |
| **スモールスタート／新規事業** | 初期投資ゼロ。失敗しても捨てられる |
| **リモートワーク中心** | そもそも「社内」という概念が薄い |
| **拠点が分散・海外拠点あり** | どこからでも同じ距離 |
| **IT人員が少ない** | 機器の保守・故障対応から解放される |
| **DR/BCPを手軽に確保したい** | マルチAZ/リージョンが標準機能 |
| **最新技術を使いたい** | AI・分析基盤などマネージドサービスが豊富 |

### 3-4. クラウドのコスト構造と落とし穴

```
【クラウドの請求書で驚く上位】
  1. データ転送（Egress）      … 外向き通信は高い
  2. NAT Gateway              … 時間課金＋処理課金（→ ⑧章）
  3. AZ間通信                 … マルチAZ設計の副作用
  4. 消し忘れリソース          … 検証環境・スナップショット・未使用IP
  5. ログの保管               … 出力しっぱなしで肥大化
  6. 高性能インスタンスの常時稼働 … オンデマンド価格のまま放置
```

**コスト最適化の定石**：

| 手法 | 削減効果 |
| --- | --- |
| **リザーブド／Savings Plans／コミット割引** | **30〜70%**。常時稼働なら必須 |
| スポット／プリエンプティブ | 最大90%（中断可能な処理のみ） |
| **検証環境の自動停止**（夜間・休日） | **50〜70%**（検証環境分） |
| VPCエンドポイントの活用 | NAT費用の大幅削減 |
| **CDNでEgressを肩代わり** | 転送費の削減 |
| ストレージのライフサイクル管理 | 古いデータを安いクラスへ自動移行 |
| 適正サイジング（rightsizing） | 過剰スペックの是正 |

> 💡 **「クラウドは使った分だけ」は「使わない分は止めれば無料」という意味**です。止める仕組み（自動停止・タグによる棚卸し・予算アラート）を作らないと、コストは必ず膨らみます。**FinOps という運用領域が生まれたのはこのためです。**

### 3-5. クラウド特有のリスク

| リスク | 対策 |
| --- | --- |
| **クラウド障害で全停止** | マルチAZ、重要システムはマルチリージョン。**SLAの内容を確認** |
| **回線障害＝全業務停止** | オフィス回線の冗長化が**むしろ重要になる** |
| **ベンダーロックイン** | マネージドサービスに依存するほど移行困難。**IaC・コンテナで緩和** |
| **設定ミスによる公開事故** | ストレージの公開設定・SGの `0.0.0.0/0`。**IaC＋自動チェック（CSPM）** |
| **コストの予測困難** | 予算アラート・タグ付け・定期レビュー |
| **データ主権・法規制** | リージョンの選択。国内リージョン限定の要件がある場合も |

> ⚠️ **クラウドにすると、オフィスのインターネット回線が「生命線」になります。** オンプレ時代は回線が落ちても社内システムは使えましたが、クラウドでは何もできません。**クラウド移行と同時に、回線の冗長化を必ずセットで検討してください。** これは見落とされやすい重要ポイントです。

## 4. パターンC：ハイブリッド構成

### 4-1. 構成図

```
   ┌──────────────── オンプレミス ─────────────────┐
   │                                                │
   │  ┌────────────┐   ┌──────────────────────┐    │
   │  │クライアント  │   │  基幹システム          │    │
   │  │ VLAN群      │   │  ・生産管理           │    │
   │  └────────────┘   │  ・会計/ERP           │    │
   │                    │  ・制御系（OT）        │    │
   │  ┌────────────┐   └──────────────────────┘    │
   │  │ファイル/AD  │                                │
   │  └────────────┘   ┌──────────────────────┐    │
   │                    │ NGFW / ルータ         │    │
   │                    └───┬──────────────┬───┘    │
   └────────────────────────┼──────────────┼────────┘
                            │              │
              ┌─────────────┘              └──────────┐
              │ 専用線                       インターネット
              │ (Direct Connect/            （VPNバックアップ）
              │  ExpressRoute)                        │
              ↓                                       ↓
   ┌──────────┴───────────────────────────────────────┴──┐
   │                     クラウド                          │
   │  ┌──────────────┐  ┌──────────────┐  ┌───────────┐ │
   │  │ Webシステム   │  │ データ分析基盤 │  │ バックアップ│ │
   │  │ （変動が大きい）│  │ （一時的に大量）│  │ / DR      │ │
   │  └──────────────┘  └──────────────┘  └───────────┘ │
   └──────────────────────────────────────────────────────┘
   
   ＋ SaaS（Microsoft 365 / Salesforce 等）は各拠点から直接
   ＋ ID基盤：オンプレAD ⇔ Entra ID を同期（ハイブリッドID）
```

### 4-2. 「何をどこに置くか」の判断基準

これが本章の核心です。**ワークロードごとに判断**します。

| 特性 | オンプレ向き | クラウド向き |
| --- | --- | --- |
| **負荷の変動** | 一定 | **変動が大きい・季節性がある** |
| **遅延要件** | **1ms以下が必要** | 数十msで問題ない |
| **データ量** | **大量・常時転送** | 小〜中量 |
| **機密度** | **法規制で外部保管不可** | 通常の業務データ |
| **稼働期間** | 5年以上使い続ける | **短期・一時的・実験的** |
| **既存資産** | **償却中の設備がある** | 新規 |
| **可用性要件** | 自社で作り込める | **標準機能で高可用性が欲しい** |
| **成長速度** | 予測可能 | **読めない・急成長する可能性** |

### 4-3. 実務でよくある分担パターン

| パターン | オンプレに残すもの | クラウドに置くもの |
| --- | --- | --- |
| **① 基幹はオンプレ、周辺はクラウド**（最も多い） | ERP・生産管理・AD・ファイルサーバー | Web・メール・グループウェア・分析 |
| **② クラウドをDR先にする** | 本番環境すべて | **バックアップ・災害時の待機環境** |
| **③ バースト（クラウドバースティング）** | 通常時の処理 | **繁忙期の追加処理能力** |
| **④ 開発はクラウド、本番はオンプレ** | 本番 | 開発・検証環境（作って壊す） |
| **⑤ データはオンプレ、計算はクラウド** | 機密データ | AI学習・分析（データはマスクして送る） |
| **⑥ 工場はオンプレ、情報系はクラウド** | 制御系（OT）・現場システム | 情報系すべて |

> 💡 **中堅製造業で最も多いのは ① ＋ ⑥ の組み合わせ**です。工場の制御系は絶対に止められず、レガシー機器も多いのでオンプレに残す。一方、メール・グループウェア・営業系はクラウドへ。この分離が現実解になります。

### 4-4. ハイブリッド特有の設計課題

| 課題 | 内容 | 対策 |
| --- | --- | --- |
| **IPアドレスの重複** | オンプレとクラウドで同じ帯を使ってしまう | **③章の設計で最初から分けておく**。既に重複したらNAT or VPCの作り直し |
| **DNSの二重管理** | 社内名・クラウド名の解決が噛み合わない | **条件付きフォワーダ**／Resolver の相互設定 |
| **ID管理の分断** | オンプレADとクラウドIDが別 | **ID同期（Entra Connect等）＋SSO**（→ [SSO ガイド](../sso/README.md)） |
| **監視の二重化** | オンプレ監視とクラウド監視が別画面 | **統合監視ツール**／少なくともアラートの通知先は1つに |
| **セキュリティポリシーの不一致** | オンプレはFW、クラウドはSG。ルールがずれる | ポリシーの一元管理・定期的な突合 |
| **データ転送コスト** | 頻繁にオンプレ⇔クラウドを往復する設計 | **データと処理を同じ側に寄せる**。往復させない |
| **障害切り分けが困難** | どちら側が原因か分からない | 境界（専用線・VPN）での監視ポイント設置 |

> ⚠️ **ハイブリッドで最も多い失敗は「往復する設計」**です。オンプレのDBをクラウドのアプリから参照する——これは遅延も転送費も最悪です。**アプリとデータは同じ側に置く**のが鉄則です。

### 4-5. 接続方式の選び方

| 用途 | 推奨方式 |
| --- | --- |
| 検証・小規模データ | **インターネットVPN**（即日、月数万円） |
| 本番・安定性が必要 | **専用線**（Direct Connect / ExpressRoute） |
| 中小規模・早く欲しい | **接続事業者経由の専用線**（数日〜2週間、小帯域から） |
| 複数クラウド | **クラウドエクスチェンジ**（1本から複数クラウドへ） |

**冗長化の定石**：専用線をメイン、**インターネットVPNをバックアップ**にする（→ [⑧ 6-3節](08-cloud-network.md)）。専用線2本より安価で、大半の障害をカバーできます。

## 5. コスト比較の実例（同じシステムを3方式で）

**前提**：Webシステム（アプリサーバー4台相当＋DB冗長）、月間データ転送 2TB、5年間

| 項目 | オンプレ | クラウド | ハイブリッド |
| --- | --- | --- | --- |
| 初期費用 | 2,500万円 | 50万円（設計のみ） | 1,500万円 |
| 月額 | 25万円（保守・電気・回線） | **95万円**（オンデマンド） | 60万円 |
| 月額（最適化後） | 25万円 | **45万円**（RI・自動停止適用後） | 40万円 |
| 運用人件費（月） | 40万円（0.5人） | 15万円（0.2人） | 45万円（**最も重い**） |
| **5年TCO** | **6,400万円** | **3,650万円** | **6,600万円** |

**読み取れること**：

1. **クラウドの最適化（RI・自動停止）は必須**。していないと1.5〜2倍かかる
2. **ハイブリッドは「両方の運用コスト」がかかる**。中間ではなく、むしろ最も高くなることがある
3. オンプレは初期が重いが、**5年使い切れば月額は安い**
4. ただしこの試算は**負荷が一定**の前提。**繁忙期に3倍のリソースが必要**ならクラウドが圧勝する

> ⚠️ **この表の数字は例示です。** 実際は、扱うデータ量・必要な可用性・既存人員の有無で大きく変わります。**自社の条件で必ず試算してください。** 重要なのは「初期費用だけ／月額だけ」で比較せず、**5年TCO＋人件費**で比べることです。

## 6. 移行のパターンと進め方

### 6-1. 移行の6つのアプローチ（6R）

| 手法 | 内容 | 難易度 | 効果 |
| --- | --- | --- | --- |
| **Rehost**（リフト＆シフト） | そのままVMを移す | 低 | 小（コスト削減は限定的） |
| **Replatform** | OS・DBをマネージドに置き換え | 中 | 中 |
| **Repurchase** | SaaSに乗り換える | 低〜中 | **大**（運用が消える） |
| **Refactor** | クラウド前提に作り直す | **高** | **最大** |
| **Retire** | 廃止する | 低 | **大**（使われていないシステムは意外と多い） |
| **Retain** | オンプレに残す | — | — |

> 💡 **最初にやるべきは Retire（棚卸しと廃止）です。** 移行対象を減らすことが、最も確実なコスト削減になります。「誰も使っていないサーバー」は、どの企業にも必ずあります。

### 6-2. 現実的な移行ステップ

```
Phase 0: 現状把握（3〜6ヶ月）
   □ 全システムの棚卸し（サーバー・アプリ・依存関係・利用者）
   □ 通信フローの可視化（何が何と通信しているか）
   □ 使われていないシステムの特定 → 廃止
   □ IPアドレス設計の見直し（クラウド用ブロックの確保）

Phase 1: 足場づくり（3〜6ヶ月）
   □ ID基盤の統合（AD ⇔ クラウドID の同期・SSO・MFA）
   □ ネットワーク接続（VPN → 専用線）
   □ 監視・ログ基盤の準備
   □ IaC・命名規則・タグ設計のルール策定

Phase 2: 影響の小さいものから移行（6〜12ヶ月）
   □ 検証・開発環境
   □ 社内向けの小さなシステム
   □ バックアップ・DR
   → ここで運用ノウハウを蓄積する

Phase 3: 本命の移行（1〜2年）
   □ 業務システム（利用部門と調整しながら）
   □ 段階的に切り替え、切り戻し手順を必ず用意

Phase 4: 最適化（継続）
   □ コスト最適化（RI・サイジング・自動停止）
   □ マネージドサービスへの置き換え
   □ オンプレ設備の縮小・撤去
```

### 6-3. 移行で失敗する典型パターン

| 失敗 | 内容 | 回避策 |
| --- | --- | --- |
| **リフト＆シフトだけで終わる** | VMを移しただけ。コストは変わらず運用も楽にならない | Replatform / Repurchase を組み合わせる |
| **依存関係の見落とし** | 移行したら別システムが動かなくなった | **Phase 0 の通信フロー可視化を省略しない** |
| **IPアドレスが重複** | 接続した瞬間に通信不能 | 事前にIP設計を統一（→ [③](03-ip-subnet.md)） |
| **回線を冗長化していない** | クラウド移行後、回線障害で全社停止 | **移行とセットで回線冗長化** |
| **コスト管理の仕組みがない** | 請求書が想定の3倍 | 予算アラート・タグ・月次レビュー |
| **スキル移行を計画していない** | 運用チームがクラウドを扱えない | 教育・外部支援・段階移行で慣らす |
| **オンプレ設備を止められない** | 一部が残り、二重コストが続く | **撤去計画まで含めて移行計画とする** |

## 7. 規模 × 配置 の推奨組み合わせ

⑨章の規模と、本章の配置を掛け合わせた実務上の推奨です。

| | **オンプレ** | **クラウド** | **ハイブリッド** |
| --- | --- | --- | --- |
| **小規模** | △ 過剰。サーバー保守の負担が重すぎる | ◎ **最適**。SaaS中心で機器を持たない | △ 管理が複雑になりすぎる |
| **中規模** | ○ 既存資産があれば合理的 | ◎ **成長企業には最適**。SASEで拠点も軽くなる | ◎ **最も現実的**。基幹オンプレ＋周辺クラウド |
| **大規模** | ○ 基幹・制御系は残る | ○ 全面移行例もあるが慎重に | ◎ **ほぼ必然**。適材適所が前提になる |

### 小規模の推奨構成（クラウド中心）

```
オフィス：回線＋UTM＋スイッチ＋Wi-Fi のみ
業務    ：Microsoft 365 / Google Workspace ＋ 業務SaaS
ID      ：Entra ID / Google（SSO＋MFA必須）
端末    ：MDM＋EDR
バックアップ：クラウドのバックアップ機能＋ローカルNAS
サーバー：持たない（どうしても必要ならクラウドVM 1〜2台）

→ ネットワーク担当の仕事は「回線とWi-Fiの面倒を見る」だけになる
```

### 中規模の推奨構成（ハイブリッド）

```
オンプレ：基幹システム（ERP・生産管理）、AD、ファイルサーバー
クラウド：Web、メール、分析、バックアップ/DR、開発検証環境
SaaS    ：グループウェア、営業支援、人事
接続    ：専用線（接続事業者経由）＋インターネットVPNバックアップ
拠点    ：SD-WAN or SASE でローカルブレイクアウト
ID      ：オンプレAD ⇔ クラウドID を同期。SSO＋MFA
```

### 大規模の推奨構成（ハイブリッド＋SASE）

```
オンプレDC：基幹・制御系・大量データ処理・低遅延要件
クラウド  ：新規開発・分析・AI・DR・変動の大きいワークロード
接続      ：複数の専用線（冗長・異キャリア・異拠点）
セキュリティ：SASE/ZTNA で拠点・在宅を統一制御
運用      ：IaC・自動化・統合監視・SOC 24/365
```

## 8. 判断のためのチェックリスト

自社の状況に当てはめてみてください。**該当が多い方が向いています。**

### オンプレを選ぶべきサイン

```
□ 法規制・契約でデータの外部保管が禁止されている
□ 1ms 以下の遅延が事業要件になっている（制御・取引）
□ 24時間フル稼働で、負荷がほぼ一定
□ 月間のデータ転送量が数十TB以上
□ 既存設備の償却が3年以上残っている
□ 拠点の回線が細い・不安定（地方の工場等）
□ 特殊なハードウェア・レガシー接続が必要
```

### クラウドを選ぶべきサイン

```
□ 負荷の変動が大きい（繁忙期が通常の3倍以上）
□ 新規事業・スモールスタート・PoC
□ IT運用に割ける人員が1人未満
□ リモートワークが常態化している
□ 拠点が分散している／海外拠点がある
□ DR/BCPを整えたいが、DR拠点を作る予算がない
□ AI・分析など最新のマネージドサービスを使いたい
□ 3年以内に事業規模が読めない
```

### ハイブリッドを選ぶべきサイン

```
□ 基幹システムは移せないが、周辺は軽くしたい
□ オンプレ設備がまだ償却中だが、新規はクラウドで始めたい
□ 制御系（OT）と情報系（IT）が両方ある
□ 段階的に移行したい（一気に切り替えられない）
□ DR先としてクラウドを使いたい
□ データはオンプレ、分析だけクラウドで行いたい

  ※ ただし「運用が二重になる」覚悟と体制が必要
```

## 9. よくある疑問（FAQ）

**Q. 結局、どれを選べばいいのか一言で？**
A. **小規模ならクラウド、中〜大規模ならハイブリッド**が現代の標準解です。純粋なオンプレ全振りは、明確な理由（法規制・低遅延・大量データ）がある場合に限られます。ただし**「ハイブリッドは運用が二重になる」**という代償を、必ず体制計画に織り込んでください。

**Q. クラウドに移したらネットワーク担当は不要になる？**
A. なりません。**仕事の内容が変わる**だけです。機器の面倒を見る仕事は減りますが、VPC設計・セキュリティグループ・専用線・IDと端末の管理・コスト最適化という新しい領域が増えます。むしろ**設計能力の比重が上がります**。

**Q. 「クラウドの方が安全」or「オンプレの方が安全」、どっち？**
A. **どちらでもありません。** クラウド事業者の物理・基盤セキュリティは、多くの企業の自社DCより高水準です。一方で、**クラウドの設定ミス（公開設定・過剰な権限）による事故は多発**しています。これが**責任共有モデル**です——「基盤は事業者、設定とデータは利用者の責任」。安全性は**運用の質**で決まります。

**Q. 一度クラウドに行ったら戻れない？**
A. 戻せます（リパトリエーション）。ただし**マネージドサービスに深く依存しているほど困難**になります。将来の移行可能性を残したいなら、**コンテナ・IaC・オープンな技術**を選び、独自マネージドサービスへの依存を意識的に抑えてください。ただしこれは「クラウドの利点を捨てる」ことでもあるので、トレードオフです。

**Q. SaaSはクラウドに含まれる？**
A. 含まれます。むしろ**最も費用対効果の高いクラウド活用がSaaS（Repurchase）**です。自社でメールサーバーやグループウェアを運用する合理性は、現在ほぼありません。「クラウド移行」を考える際は、**まずSaaSに置き換えられるものを探す**のが先決です。

**Q. 小規模でもオンプレにサーバーを置きたい理由があるとしたら？**
A. ①大容量ファイル（動画・CAD・医療画像）を日常的に扱う、②回線が細い・従量課金、③特殊なソフトウェアがオンプレ前提、④法規制。この4つ以外なら、**NAS 1台とクラウドで足ります**。

## まとめ

- **「クラウドは安い」は条件付き**。変動が大きい・小さく始める・人件費を減らせる場合に成立する
- コスト比較は**5年TCO＋運用人件費**で。初期費用だけ／月額だけの比較は必ず外す
- **オンプレの隠れコストは「運用人件費」と「電気代」**
- **クラウドの隠れコストは「データ転送」「NAT Gateway」「消し忘れ」**。最適化（RI・自動停止）で半減する
- **ハイブリッドは中間ではなく、運用コストは最も高くなり得る**
- **クラウド移行後は、オフィス回線が生命線**。冗長化を必ずセットで
- ハイブリッド最大の失敗は**「オンプレとクラウドを往復する設計」**。アプリとデータは同じ側に置く
- 移行はまず **Retire（棚卸しと廃止）** から。移行対象を減らすのが最も効く
- **IPアドレス設計の重複**が、接続時の最頻出事故。③章の設計を最初から守る
- 推奨：**小規模＝クラウド／中〜大規模＝ハイブリッド**。純オンプレは明確な理由がある場合のみ
