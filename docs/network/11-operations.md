# ⑪ 監視・運用・トラブルシューティング

> **この章のゴール**：障害を「気づける」体制を作り、起きたときに最短で切り分けられるようになる。そして、冗長化とBCPを「機器の話」ではなく「事業継続の話」として設計できるようになる。

← [⑩ オンプレ・クラウド・ハイブリッド構成](10-onprem-cloud-hybrid.md) ／ 付録 → [用語集・チートシート](glossary.md)

---

## 0. まず全体像（30秒）

運用の目的は3つだけです。

```
1. 気づく    （監視）  ← 最も重要。気づけない障害は対応できない
2. 直す      （切り分けと復旧）
3. 繰り返さない（記録と改善）
```

そして最も見落とされるのがこれです。

> ⚠️ **冗長化しても、切り替わったことに気づかなければ意味がありません。**
> 片系が落ちたまま数ヶ月運用し、もう片方も落ちて初めて全断——という事故は本当によくあります。
> **冗長化と監視は必ずセットで設計してください。**

## 1. 監視の設計

### 1-1. 何を監視するか（4つの層）

| 層 | 監視対象 | 手段 |
| --- | --- | --- |
| **死活** | 機器・回線が生きているか | ping、SNMP、ポーリング |
| **性能** | 帯域使用率・CPU・メモリ・エラー数 | SNMP、ストリーミングテレメトリ |
| **フロー** | 誰が何とどれだけ通信しているか | **NetFlow / sFlow / IPFIX** |
| **体験** | **利用者から見て実際に使えるか** | 合成監視、RUM、SLA測定 |

> 💡 **最も価値があるのは「体験」の監視**です。「機器は全部正常なのに、ユーザーは繋がらないと言っている」という状況を防げます。**主要な業務システムに定期的にHTTPアクセスして応答時間を測る**だけでも、大きく変わります。

### 1-2. 主要なプロトコル

| プロトコル | 用途 | 注意点 |
| --- | --- | --- |
| **SNMP** | 機器の状態・カウンタ取得 | **v3を使う**（v1/v2cはコミュニティ名が平文） |
| **Syslog** | ログの集約 | UDP 514。**時刻同期（NTP）が前提** |
| **NetFlow / sFlow** | 通信フローの可視化 | 「何が帯域を食っているか」の特定に必須 |
| **ICMP** | 死活監視 | 軽量。ただし機器がping応答を優先度低で扱う場合あり |
| **ストリーミングテレメトリ** | 秒単位のリアルタイム取得 | 新しい機器向け。SNMPより高頻度 |

> ⚠️ **NTPによる時刻同期は運用の前提条件**です。機器の時刻がバラバラだと、複数機器のログを突き合わせられず、障害の原因究明が不可能になります。**全機器のNTP設定を最初に確認**してください。

### 1-3. 監視すべき項目と閾値の目安

| 項目 | 警告 | 危険 | 備考 |
| --- | --- | --- | --- |
| **回線帯域使用率** | 70% | 85% | **ピーク値で見る**。平均では輻輳を見逃す |
| CPU使用率（機器） | 70% | 85% | 継続的な高負荷は要調査 |
| メモリ使用率 | 80% | 90% | メモリリークの兆候にも注意 |
| **インタフェースエラー** | 増加傾向 | 継続増加 | **CRC・input errorは物理層の異常**（→ [②](02-physical-datalink.md)） |
| パケットロス | 0.1% | 1% | 音声・映像は0.1%でも影響 |
| **RTT（遅延）** | 通常の1.5倍 | 通常の2倍 | **絶対値でなく「普段との差」で見る** |
| 温度 | メーカー基準 | 同左 | 空調障害の早期検知 |
| **冗長構成の状態** | — | 片系ダウン | **最重要。必ず監視する** |
| 電源・ファン | — | 異常 | 予備品の手配トリガー |
| 証明書の有効期限 | 30日前 | 7日前 | **失効事故は毎年どこかで起きる** |
| ライセンス期限 | 60日前 | 30日前 | 失効すると機能停止する製品も |

### 1-4. アラート設計 — 「オオカミ少年」を作らない

**監視で最も失敗するのは、アラートが多すぎて誰も見なくなること**です。

| 原則 | 内容 |
| --- | --- |
| **アクション可能なものだけ通知する** | 「見るだけで何もできない」アラートは削除する |
| **重要度を分ける** | 緊急（即対応）／警告（翌営業日）／情報（記録のみ） |
| **通知先を分ける** | 緊急は電話/SMS、警告はチャット、情報はダッシュボードのみ |
| **フラッピング対策** | 「3回連続失敗で通知」など。1回の瞬断で鳴らさない |
| **依存関係を考慮** | **上位スイッチが落ちたら配下100台分のアラートが出る**のを抑制する |
| **定期的な棚卸し** | 鳴りっぱなしのアラートは、閾値が間違っているか監視対象が不適切 |

> 💡 **「アラートが鳴ったら必ず誰かが何かをする」状態を維持してください。** これが崩れると、本当の障害を見逃します。鳴っても無視するアラートは、**消すか閾値を直すかのどちらか**です。

### 1-5. 監視ツールの選択肢

| 種類 | 例 | 向いている規模 |
| --- | --- | --- |
| OSS | Zabbix、Prometheus＋Grafana、LibreNMS、Netdata | 中〜大（構築工数は必要） |
| 商用オンプレ | PRTG、SolarWinds、Nagios XI | 中〜大 |
| **クラウド型** | Datadog、New Relic、Mackerel、機器ベンダーのクラウド管理 | **小〜中（構築不要）** |
| 機器付属 | UTM/APコントローラの標準機能 | 小 |

**小規模での現実解**：機器のクラウド管理機能＋外形監視（UptimeRobot等）だけでも、「気づけない」状態からは脱出できます。**完璧を目指して何もしないより、簡易でも始めることが重要**です。

## 2. トラブルシューティングの手順

### 2-1. 基本フロー

```
1. 事実確認     いつから／誰が／何ができないか／範囲はどこまで
2. 範囲の特定   1人？1島？1フロア？全社？拠点間だけ？
3. 変更の確認   直前に何か変更したか（設定・工事・アップデート・停電）
4. 層で切る     L1 → L2 → L3 → L4 → L7 の順に確認
5. 仮説と検証   1つずつ試す。同時に複数変えない
6. 復旧        まず業務を戻す（原因究明は後でもよい）
7. 記録        原因・対処・再発防止を残す
```

> 💡 **「3. 直前の変更確認」で7割は解決します。** 障害の最大の原因は「何かを変えたこと」です。変更管理の記録が残っていれば、ここで即座に当たりが付きます。

### 2-2. 範囲から原因を絞る

**これが最も効率的な切り分けです。**

| 影響範囲 | 疑うべき箇所 |
| --- | --- |
| **1台だけ** | 端末側（NIC・ドライバ・設定・ケーブル・認証） |
| **1つの島・1つのポート群** | **島のスイッチ・そのポート・ケーブル** |
| **1フロア** | フロアのスイッチ・アップリンク |
| **1つのVLANだけ** | **VLAN設定・そのVLANのゲートウェイ・DHCP** |
| **全社（社内は通信可・外だけ不可）** | **ルータ・FW・回線・ISP** |
| **全社（社内も不可）** | **コアスイッチ・ループ・電源** |
| **特定のサービスだけ** | そのサーバー・DNS・そのポートのFWルール |
| **拠点間だけ** | WAN回線・VPN・拠点間ルーティング |
| **無線だけ** | AP・コントローラ・無線側の認証（RADIUS） |
| **時間帯依存** | 輻輳・バックアップジョブ・近隣の電波（2.4GHz） |

### 2-3. 層別の確認手順（実践版）

```
【L1：物理】
  □ リンクランプは点いているか（両端）
  □ ケーブルを別のものに交換して再現するか
  □ 別ポートに挿して再現するか
  □ show interface でエラーカウンタが増えているか
  □ PoE給電が足りているか（AP・IP電話）
  □ 配線長は100m以内か

【L2：データリンク】
  □ MACアドレステーブルに端末が載っているか
  □ VLANの割り当ては正しいか（アクセス/トランク）
  □ ポートが err-disable になっていないか
  □ STPでブロックされていないか
  □ ループの兆候（CPU高騰・全ポート点滅）はないか

【L3：ネットワーク】
  □ IPアドレス・マスク・GWは正しいか（169.254.x.x になっていないか）
  □ 自セグメント内の他機器にpingは通るか
  □ デフォルトゲートウェイにpingは通るか
  □ 8.8.8.8（IP直打ち）にpingは通るか
  □ traceroute でどこまで到達するか
  □ 戻りの経路は存在するか ← 見落としやすい

【L4：トランスポート】
  □ 目的のポートに繋がるか（nc -zv / Test-NetConnection）
  □ タイムアウトか、接続拒否か ← この違いが決定的
  □ ss -tan で異常な状態（SYN_SENT滞留・CLOSE_WAIT大量）はないか

【L7：アプリケーション】
  □ 名前解決はできるか（dig / nslookup）
  □ 証明書は有効か（期限・チェーン・ドメイン一致）
  □ プロキシ設定は正しいか
  □ サーバー側のログに何か出ているか
```

### 2-4. 症状別 早見表

| 症状 | 最も可能性が高い原因 | 最初に打つ手 |
| --- | --- | --- |
| **全社が突然停止** | **ループ**・コア機器障害・電源 | スイッチのCPU/ポート点滅を確認。直近で挿されたケーブルを探す |
| 全社で外部だけ不可 | 回線障害・ISP障害・FW | ISPの障害情報を確認、回線のリンク状態 |
| **一部の人だけ繋がらない** | VLAN・DHCP枯渇・ポートセキュリティ | `ipconfig /all` でIPの取得状況 |
| **「なんか遅い」** | **帯域輻輳・Wi-Fi干渉・DNS・サーバー側** | まず**どこが遅いか**を測る（後述） |
| 名前解決だけ失敗 | DNS | `ping 8.8.8.8` と `nslookup` を比較 |
| 大きいファイルだけ失敗 | **MTU / PMTUD** | `ping -M do -s 1472` でサイズを詰めて特定 |
| **VPN越しだけ不調** | MTU・IPsecパラメータ・IP重複 | MSSクランプ設定を確認 |
| 特定サイトだけ不可 | FW/プロキシのフィルタ・相手側の障害 | 別回線（スマホテザリング）で再現確認 |
| **時々切れる** | ケーブル不良・PoE不足・DFS・IPアドレス重複 | ログでup/down回数、DFSイベント |
| 朝だけ遅い | 一斉ログイン・ウイルス定義更新・バックアップ | スケジュールの分散 |

### 2-5. 「遅い」の切り分け方

**「遅い」は最も難しい相談です。** 順番に測って原因を特定します。

```
Step 1: 何が遅いのか特定する
  □ 全部？ 特定のサイト・システムだけ？
  □ 有線も無線も？ 無線だけ？
  □ 特定の時間帯だけ？

Step 2: どこで遅いか測る
  □ ping で RTT を測る（社内GW → ISP → 目的地）
     → どこで急に跳ねるか
  □ traceroute で各ホップの遅延を見る
  □ 速度測定サイトで回線速度を測る（有線で・複数回）

Step 3: 原因を判定する
  ・回線速度が契約値より大幅に低い    → 回線・ISP・輻輳
  ・RTTは正常だが転送が遅い          → ウィンドウサイズ・サーバー側
  ・無線だけ遅い                     → 電波干渉・チャネル・端末密度
  ・特定サーバーだけ遅い              → サーバー側（ネットワークではない）
  ・帯域使用率が高い                  → 輻輳。誰が使っているかNetFlowで特定
```

> ⚠️ **「遅い＝回線を増速すれば解決」は多くの場合誤りです。** 実際の原因は、Wi-Fiの干渉、DNSの応答遅延、サーバー側の処理、遅延（RTT）とウィンドウサイズの問題であることが大半です（→ [⑤ 2-5節](05-transport-application.md)）。**増速契約の前に必ず測定してください。**

## 3. 冗長化の設計

### 3-1. 単一障害点（SPOF）を洗い出す

冗長化の第一歩は、**「これが壊れたら全部止まるもの」のリスト化**です。

```
チェックリスト:
  □ インターネット回線（1本しかない？）
  □ ISP（同じ会社の2回線は「1つのSPOF」）
  □ 建物への引込経路（同じ管路を通っていないか）
  □ ルータ/FW（1台？）
  □ コアスイッチ（1台？）
  □ コアへのアップリンク（1本？）
  □ 電源（同じブレーカー・同じUPS？）
  □ 空調（1台？）
  □ DNSサーバー（1台？）
  □ DHCPサーバー（1台？）
  □ 認証サーバー（RADIUS/AD が1台？）
  □ 仮想化ホスト（1台に全VMが載っていないか）
  □ 担当者（1人しか分からない業務はないか）← 人的SPOF
```

> 💡 **「担当者のSPOF」を必ずリストに入れてください。** 技術的に完璧に冗長化されていても、「その人しか操作できない」なら、それは冗長化されていません。

### 3-2. 冗長化のレベルと費用対効果

| レベル | 内容 | 費用 | 効果 |
| --- | --- | --- | --- |
| **1** | **バックアップ（3-2-1）** | 低 | ★★★ **最優先。復旧の最終手段** |
| **2** | **WAN回線の冗長化（モバイル予備）** | 低 | ★★★ **費用対効果が最も高い** |
| 3 | 電源の冗長化（UPS） | 低 | ★★ 瞬停・短時間停電に対応 |
| 4 | コア機器の冗長化 | 中 | ★★ |
| 5 | 全経路の冗長化 | 高 | ★★ |
| 6 | 拠点/DCの冗長化（DR） | **非常に高い** | ★ （事業影響が大きい場合のみ） |

**小規模なら 1 と 2 だけで十分な効果が得られます。** 高価な機器の二重化より、**バックアップとモバイル回線**の方が投資対効果は圧倒的に高いです。

### 3-3. 冗長化の落とし穴

| 落とし穴 | 内容 |
| --- | --- |
| **切り替わりに気づかない** | 監視していないと、片系運用のまま放置される |
| **切り替えが動かない** | **一度もテストしていない**。設定ミスで切り替わらない |
| **同じ経路・同じ電源** | 「2台あるが、同じ電源タップに挿さっている」 |
| **同じロット・同じ時期の機器** | 同じ製造不良で同時に壊れることがある |
| **切り替え後の性能不足** | 副系のスペックが低く、切り替わっても業務が回らない |
| **設定が同期されていない** | 主系だけ設定変更し、副系が古いまま |

> ⚠️ **「切り替えテストを一度もしていない冗長構成」は、冗長化ではなく「気休め」です。** 年1回でよいので、**計画的に片系を落として切り替わることを確認**してください。テストで問題が見つかることは、非常によくあります。

## 4. BCP / DR — 事業継続の設計

### 4-1. RTO と RPO

すべての議論の出発点になる2つの指標です。

```
     障害発生
        │
  ──────┼──────────────────────→ 時間
        │
   ←────┤ RPO（目標復旧時点）      ← どこまでのデータを失ってよいか
        │                            = バックアップの頻度で決まる
        │
        ├────→ RTO（目標復旧時間）  ← いつまでに復旧すべきか
                                      = 構成と手順で決まる
```

| RTO/RPO | 必要な構成 | コスト |
| --- | --- | --- |
| **RPO 24時間 / RTO 数日** | 日次バックアップ＋機器の再調達 | 低 |
| **RPO 24時間 / RTO 数時間** | 日次バックアップ＋**クラウドに復元環境** | 中 |
| **RPO 1時間 / RTO 1時間** | 定期レプリケーション＋待機環境（コールド/ウォーム） | 高 |
| **RPO ≒0 / RTO ≒0** | **同期レプリケーション＋アクティブ/アクティブ** | 非常に高い |

> 💡 **RTO/RPO は「情報システム部門が決めるもの」ではありません。** 事業部門と経営が「どこまでの停止・データ損失を許容するか」を決め、それに必要なコストを提示するのが情報システムの役割です。**先に構成を決めてはいけません。**

### 4-2. バックアップの 3-2-1 ルール

```
  3 : データのコピーを3つ持つ（本番＋バックアップ2つ）
  2 : 2種類の異なる媒体に保存する
  1 : うち1つは遠隔地（オフサイト）に置く

【現代の追加要件（ランサムウェア対策）】
  ＋ 1つは オフライン または イミュータブル（変更不可）ストレージに
     → ネットワーク経由で消せない状態にしておく
```

> ⚠️ **ランサムウェア被害では、バックアップも同時に暗号化されるケースが大半です。** ネットワークから到達できるバックアップだけでは不十分。**オフライン（テープ・切り離したディスク）またはイミュータブルストレージ**を1つ持ってください。これが最後の砦になります。

### 4-3. 復旧手順は「紙」でも持つ

```
ネットワークが全断した状態で、
  ・手順書がファイルサーバーにある     → 読めない
  ・パスワードがクラウドの金庫にある    → 開けない
  ・連絡先が社内システムにある         → 分からない

→ 最低限の復旧手順・連絡先・機器のログイン情報は
  オフライン（印刷 or 担当者のローカル）にも保持する
```

**必ずオフラインで持つべきもの**：
- ネットワーク構成図・IPアドレス一覧
- 機器の管理IPと認証情報（安全に保管）
- ISP・保守ベンダーの緊急連絡先と契約番号
- 復旧手順書（優先順位付き）
- 関係者の連絡先（社内・社外）

### 4-4. 訓練

| 訓練 | 頻度 | 内容 |
| --- | --- | --- |
| **バックアップからの復元テスト** | **年2回以上** | **「取れている」と「戻せる」は別**。必ず実際に戻す |
| 冗長系の切り替えテスト | 年1回 | 計画停止で片系を落とす |
| 障害対応の机上訓練 | 年1回 | シナリオを決めて手順を確認 |
| 連絡網のテスト | 年1回 | 実際に連絡が回るか |

> ⚠️ **「バックアップを取っているが、復元したことがない」は非常に危険な状態です。** バックアップが壊れている・必要なデータが対象外だった・復元手順が分からない——これらは実際に復元して初めて分かります。

## 5. 運用ドキュメント

### 5-1. 最低限そろえるべきもの

| ドキュメント | 内容 | 更新タイミング |
| --- | --- | --- |
| **ネットワーク構成図** | 論理図（VLAN・IP・経路）＋物理図（機器・配線） | 構成変更のたび |
| **IPアドレス管理表** | セグメント・用途・払い出し状況 | 割当のたび |
| **機器台帳** | 型番・シリアル・設置場所・**保守期限・EOL** | 導入・更改時 |
| **設定バックアップ** | 全機器のコンフィグ | **変更のたび（自動化推奨）** |
| **アカウント一覧** | 管理者アカウント・共有アカウント | 定期棚卸し |
| **手順書** | よくある作業（VLAN追加・ポート開放・機器交換） | 随時 |
| **変更履歴** | いつ・誰が・何を・なぜ変えたか | **変更のたび** |
| **障害記録** | 発生・原因・対処・再発防止 | 障害のたび |
| **連絡先一覧** | ベンダー・キャリア・保守窓口 | 年1回確認 |

### 5-2. ドキュメントが続かない理由と対策

```
【続かない理由】
  ・更新が面倒（手作業）
  ・置き場所が分からない
  ・そもそも誰も見ていない

【対策】
  ・完璧を目指さない。「1枚の構成図＋IP表」から始める
  ・変更手順の中に「ドキュメント更新」を組み込む（作業完了条件にする）
  ・自動化できるものは自動化（機器コンフィグの定期取得など）
  ・Git等でバージョン管理し、変更履歴を自動的に残す
```

> 💡 **構成図は「きれいに描く」より「最新であること」が重要**です。手書きスキャンでも、最新なら価値があります。**古いきれいな図は、むしろ有害**（間違った前提で作業してしまう）です。

## 6. 変更管理

### 6-1. なぜ必要か

**大規模障害の最大の原因は「設定変更の誤り」**です。技術力ではなく、プロセスで防ぎます。

### 6-2. 最低限のプロセス

```
1. 申請     何を・なぜ・いつ・影響範囲
2. レビュー  第三者が設定内容を確認（★これだけで事故が激減する）
3. 承認     影響が大きい変更は上位承認
4. 事前準備 □ 現在の設定をバックアップ
            □ 切り戻し手順を用意 ← 最重要
            □ 影響範囲への事前通知
5. 実施     手順書に沿って。**アドリブ禁止**
6. 検証     事前に決めた確認項目をチェック
7. 記録     実施内容・結果・気づきを残す
```

### 6-3. 作業時の実務ルール

| ルール | 理由 |
| --- | --- |
| **切り戻し手順を先に用意する** | 戻せない変更は実施しない |
| **1回の作業で1つだけ変える** | 複数変えると、問題が起きたとき原因が特定できない |
| **リモート作業では締め出しに注意** | FW/ルータの設定ミスで自分が接続できなくなる。**`reload in 10`（自動ロールバック）を活用** |
| **作業時間帯を決める** | 影響の小さい時間（夜間・休日）。ただし**復旧支援が受けられる時間**も考慮 |
| **単独作業をしない** | 重要な変更は2名以上（実施者と確認者） |
| **設定は事前に作って持ち込む** | その場で考えて打たない |

> 💡 **Cisco の `reload in 10` は命綱です。** 「10分後に再起動」を予約してから設定変更し、正常に接続できたら `reload cancel`。締め出されても10分で元に戻ります。同様の機能は他ベンダーにもあります。**リモート作業では必ず使ってください。**

## 7. キャパシティ管理

「気づいたら限界だった」を防ぐため、**定期的に使用率をレビュー**します。

| 対象 | 見るもの | 増設の検討ライン |
| --- | --- | --- |
| **WAN回線帯域** | ピーク使用率の推移 | **70%を超えたら計画開始** |
| スイッチポート | 空きポート数 | 空きが20%を切ったら |
| **IPアドレス** | DHCPプールの使用率 | **80%で拡張検討**（→ [③](03-ip-subnet.md)） |
| **PoE電力** | バジェット使用率 | 80%（→ [②](02-physical-datalink.md)） |
| Wi-Fi | AP あたり接続数・エアタイム使用率 | 接続数30台超・エアタイム50%超 |
| 機器CPU/メモリ | 平常時の使用率 | 70%が常態化したら |
| **FWのセッション数** | 同時セッション数 | 上限の70% |
| ライセンス数 | 使用/契約 | 更新2ヶ月前 |

> 💡 **回線もライセンスも、増強には時間がかかります。** 光回線の増速は1〜2ヶ月、機器の納期は数ヶ月かかることもあります。**「限界に達してから」では間に合いません。70%を計画開始のトリガー**にしてください。

## 8. インシデント対応（セキュリティ）

ネットワーク担当が関わる場面での動き方です。

### 8-1. 感染・侵害が疑われるとき

```
1. 隔離する（最優先）
   □ 該当端末をネットワークから切り離す
     → スイッチのポートをshutdown、または隔離VLANへ
   □ 電源は切らない（メモリ上の証拠が消える。調査方針次第）

2. 範囲を確認する
   □ 同一セグメントの他端末の挙動
   □ ファイアウォール/プロキシのログで外部通信を確認
   □ 認証ログで不審なログインを確認

3. 報告する
   □ 社内の定められた窓口（CSIRT・情報システム責任者）
   □ 必要に応じて外部専門機関・警察・監督官庁

4. 記録する
   □ 時刻・実施した操作をすべて記録（後の調査で必要）
```

> ⚠️ **「とりあえず再起動」「とりあえず初期化」は絶対にやめてください。** 証拠が消え、原因究明と被害範囲の特定が不可能になります。**まず隔離、次に報告、調査は専門家の指示に従う**が原則です。

### 8-2. 平時に準備しておくこと

```
□ 隔離の手順（どのポートをどう止めるか）を文書化
□ ログの保管期間を確認（最低3ヶ月、可能なら1年）
□ 連絡フロー（誰に・どの順で）を決めておく
□ 外部の支援先（セキュリティベンダー）を決めておく
□ 「隔離しても業務が完全停止しない」構成にしておく
```

## 9. 運用を楽にする自動化

| 対象 | 手段 | 効果 |
| --- | --- | --- |
| **設定バックアップ** | 定期取得スクリプト＋Git管理 | **差分で「いつ誰が変えたか」が分かる** |
| 設定投入 | Ansible・ベンダーのAPI | ヒューマンエラーの削減 |
| クラウド構成 | **Terraform（IaC）** | 環境の再現性・レビュー可能に |
| 構成の検査 | 設定チェックツール・CSPM | 設定ミスの自動検出 |
| 定期レポート | 監視ツールの自動レポート | キャパシティレビューの省力化 |

> 💡 **最初にやるべき自動化は「設定バックアップのGit管理」**です。スクリプト数十行で実現でき、**「昨日まで動いていたのに」の原因究明が劇的に速くなります**。差分を見れば何が変わったか一目瞭然です。

## 10. よくある疑問（FAQ）

**Q. 監視ツールは何から始めればいい？**
A. **無料の外形監視（UptimeRobot等）で、主要システムのHTTP応答を監視する**ところから。5分で始められて、「気づけない」状態からは脱出できます。その後、機器のSNMP監視へ広げてください。

**Q. ログはどのくらい保管すべき？**
A. **最低3ヶ月、可能なら1年**。侵害の発覚は平均して数ヶ月後になることが多く、短いと調査できません。業種によっては法令・ガイドラインで期間が定められている場合があるので確認してください。

**Q. 障害対応で最初にやるべきことは？**
A. **「範囲の特定」**です。1台なのか全社なのかで、疑うべき箇所が全く変わります。焦って機器を再起動する前に、まず範囲を確認してください。

**Q. 保守契約は必要？**
A. **本番機器には必須**です。故障時の代替機提供（先出しセンドバック等）が受けられるかどうかで、復旧時間が数日変わります。特に**EOL品は保守が受けられない**ため、更改計画に直結します。

**Q. 一人情シスで、どこまでやればいい？**
A. 優先度は **①バックアップ（復元テスト込み）→ ②MFA → ③外形監視 → ④構成図とIP表 → ⑤設定バックアップ** です。この5つがあれば、最悪の事態は避けられます。それ以上は外部の保守・監視サービスに任せる判断が合理的です。

## まとめ

- **冗長化と監視は必ずセット**。切り替わったことに気づけなければ冗長化の意味がない
- 監視は **死活・性能・フロー・体験** の4層。**「体験」の監視が最も価値がある**
- **NTPによる時刻同期は運用の前提条件**
- アラートは**アクション可能なものだけ**。鳴っても無視するものは消すか閾値を直す
- トラブル対応は **①事実確認 → ②範囲特定 → ③直前の変更確認 → ④層で切る**
- **「直前の変更」で7割は解決する**
- 「遅い」は**測ってから**。増速契約は原因特定の後
- 冗長化の費用対効果は **①バックアップ ②WAN回線（モバイル予備）** が突出して高い
- **切り替えテストをしていない冗長構成は気休め**。年1回はテストする
- **RTO/RPO は事業部門と経営が決める**。情シスは選択肢とコストを提示する
- バックアップは **3-2-1 ＋ オフライン/イミュータブル**（ランサム対策）
- **「取れている」と「戻せる」は別**。年2回は復元テストを
- 変更管理は **切り戻し手順を先に用意**、**1回に1つだけ変える**、リモートは **`reload in`**
- キャパシティは **70%で計画開始**。増強には時間がかかる
- 侵害時は **まず隔離、次に報告**。再起動・初期化はしない
- 最初の自動化は **設定バックアップのGit管理**
