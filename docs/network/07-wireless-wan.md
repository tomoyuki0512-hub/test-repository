# ⑦ 無線LANとWAN

> **この章のゴール**：Wi-Fiが「なんとなく遅い」原因を設計レベルで潰せるようになる。そして、拠点間をつなぐWAN回線の種類とコスト構造を理解し、SD-WANが何を解決するのかを掴む。

← [⑥ ネットワークセキュリティ](06-security.md) ／ 次章 → [⑧ クラウドネットワーク](08-cloud-network.md)

---

## 0. まず全体像（30秒）

この章は「**LANの外**」を扱います。2つのテーマがあります。

```
【無線LAN】  ケーブルから解放される代わりに、電波という有限資源を共有する
             → 設計の本質は「電波の奪い合いをいかに減らすか」

【WAN】      離れた拠点をつなぐ。自社では所有できないので事業者から借りる
             → 設計の本質は「品質・コスト・冗長性のバランス」
```

**Wi-Fiで最も多い誤解**：「電波が弱いからAPを増やそう」。**多くの場合、APを増やすと電波干渉が増えてかえって遅くなります。**

## 1. 無線LAN（Wi-Fi）の規格

### 1-1. 世代一覧

| 通称 | 規格 | 周波数帯 | 最大速度（理論値） | 主な進化 |
| --- | --- | --- | --- | --- |
| Wi-Fi 4 | 802.11n | 2.4 / 5GHz | 600Mbps | MIMO |
| Wi-Fi 5 | 802.11ac | **5GHz のみ** | 6.9Gbps | MU-MIMO（下りのみ） |
| **Wi-Fi 6** | 802.11ax | 2.4 / 5GHz | 9.6Gbps | **OFDMA**・上り MU-MIMO・**TWT** |
| **Wi-Fi 6E** | 802.11ax | ＋**6GHz** | 9.6Gbps | **6GHz帯（クリーンな新周波数）** |
| **Wi-Fi 7** | 802.11be | 2.4/5/**6GHz** | 46Gbps | **MLO**・320MHz幅・4096-QAM |

### 1-2. 世代の進化で本当に重要なのは「速度」ではない

カタログの最大速度は**理論値であり、実環境では出ません**。実務で効くのは以下です。

| 技術 | 何を解決したか |
| --- | --- |
| **OFDMA**（Wi-Fi 6〜） | **小さいデータを複数端末にまとめて送れる**。多台数環境で劇的に効く |
| **TWT**（Wi-Fi 6〜） | 端末が起きる時間を決めて**バッテリーを節約**。IoT向け |
| **6GHz帯**（Wi-Fi 6E〜） | **既存機器がいない、干渉のない広大な帯域** |
| **MLO**（Wi-Fi 7） | **複数の周波数帯を同時に使う**。片方が混んでももう片方で通信できる |

> 💡 **オフィスで効くのは「速度」ではなく「多台数収容」です。** 1台が速いことより、100台が同時に快適に使えることの方が重要。だから **Wi-Fi 6以降のOFDMA** は大きな価値があります。

### 1-3. 周波数帯の特性

| 帯域 | チャネル数（日本・目安） | 到達距離 | 干渉 | 用途 |
| --- | --- | --- | --- | --- |
| **2.4GHz** | **実質3つ**（1/6/11） | 遠い・壁に強い | **電子レンジ・Bluetooth・近隣AP。極めて多い** | 古い機器・IoT用 |
| **5GHz** | 20ch程度 | 中 | 少ない（ただし**DFS**あり） | **オフィスの主力** |
| **6GHz** | 多数 | 近い・壁に弱い | **ほぼ無し** | 高密度環境の切り札 |

> ⚠️ **2.4GHz帯は「使えるチャネルが実質3つしかない」**のが最大の問題です。オフィスビルでは周囲の会社のAPと必ず干渉します。**可能なら2.4GHzは無効化するか、IoT専用に限定**してください。

#### DFS（気象レーダー回避）の注意

5GHz帯の一部（W53/W56）は気象レーダーと共用のため、**レーダーを検知すると強制的にチャネルを変更**します。

```
症状：突然、全端末のWi-Fiが1分ほど切れる（空港・港湾・気象台の近くで頻発）
対策：DFS不要のチャネル（W52: 36/40/44/48ch）を優先的に使う設定にする
```

## 2. 無線LAN設計の実務

### 2-1. 「APを増やせば速くなる」は間違い

```
【誤り】電波が弱い → APを追加 → もっと遅くなった

理由：
  ・同じチャネルのAPが増えると、電波は「早い者勝ちの共有資源」なので奪い合いになる
  ・APが多いと端末が「どこに繋ぐか」迷い、不安定になる
  ・隣接APの電波が「ノイズ」として干渉する（同一チャネル干渉）
```

**正しいアプローチ**：
1. **チャネル設計**（隣接APが同じチャネルにならないように配置）
2. **送信出力の調整**（**下げる**。強すぎると干渉範囲が広がる）
3. その上で必要ならAP追加

### 2-2. 設計の基本パラメータ

| 項目 | 目安 |
| --- | --- |
| **電波強度（RSSI）** | 業務利用は **−65dBm 以上**（音声利用なら −60dBm 以上） |
| **SNR（信号対雑音比）** | **25dB 以上** |
| **AP 1台あたりの同時接続** | 快適さ重視で **20〜30台**（カタログ値の100台超は非現実的） |
| **AP設置間隔** | オフィスで 10〜15m 程度（環境により大きく変わる） |
| **チャネル幅** | 高密度環境は **20MHz または 40MHz**（80MHz以上は干渉が増える） |
| **セル間の重なり** | 15〜20%（ローミングのため。重なりすぎもNG） |

> 💡 **チャネル幅は広ければ速い、ではありません。** 80MHz幅にすると使えるチャネル数が激減し、干渉が増えます。**高密度オフィスでは40MHzが実用的な上限**です。

### 2-3. 必ずやるべき設定

| 設定 | 理由 |
| --- | --- |
| **最低速度（Basic Rate）の引き上げ** | 低速な古い端末が全体の速度を引きずり下げるのを防ぐ（例：1/2/5.5/11Mbps を無効化） |
| **バンドステアリング** | 5GHz/6GHzに対応した端末を自動的に高い帯域へ誘導 |
| **エアタイムフェアネス** | 遅い端末が電波を占有する時間を制限 |
| **クライアント分離（ゲストWi-Fi）** | 来客端末同士の通信を禁止。**必須** |
| **不要なSSIDを減らす** | SSIDが多いほど管理フレームが電波を消費する。**3〜4個まで** |
| **802.11k/v/r（ローミング支援）** | 移動時の切り替えをスムーズに。音声利用では特に重要 |

### 2-4. サイトサーベイ（電波調査）

本格的な設計では、実地調査を行います。

| 種類 | タイミング | 内容 |
| --- | --- | --- |
| **プレディクティブ** | 設計前 | 図面上でシミュレーション。壁材質を考慮 |
| **プリサーベイ** | 施工前 | 実際にAPを仮設置して測定 |
| **ポストサーベイ** | 施工後 | 設計通りの電波が出ているか検証 |

**建材による減衰の目安**：

| 障害物 | 減衰 |
| --- | --- |
| 石膏ボード | 3〜5 dB |
| 木製ドア | 3〜5 dB |
| ガラス | 6〜8 dB |
| **コンクリート壁** | **10〜20 dB** |
| **金属・エレベータ** | **20〜30 dB（ほぼ遮断）** |
| **人体** | **3〜5 dB（満員の会議室は要注意）** |

> 💡 **「会議室が満員になると急にWi-Fiが不安定になる」**——これは人体による電波減衰と、端末密度の増加が同時に起きるためです。会議室は専用APを検討してください。

### 2-5. 認証方式

| 方式 | 用途 | セキュリティ |
| --- | --- | --- |
| **WPA3-Enterprise** | **企業の社員向け。推奨** | ★★★ 802.1X＋RADIUS |
| WPA2-Enterprise | 企業（移行期） | ★★★ |
| **WPA3-Personal（SAE）** | 小規模・家庭 | ★★ 共有パスワード。辞書攻撃に耐性あり |
| WPA2-Personal | 小規模（既存） | ★★ **KRACK等の既知脆弱性あり** |
| **OWE（Enhanced Open）** | **ゲストWi-Fi** | ★ パスワード無しでも暗号化される |
| Open（暗号化なし） | — | **✗ 使用しない** |

**ゲストWi-Fiの推奨構成**：
```
・OWE または キャプティブポータル（利用規約同意＋簡易認証）
・専用VLAN（社内へは完全遮断）
・クライアント分離ON
・帯域制限（1台あたり 5〜10Mbps 程度）
・DHCPリース時間を短く（30分〜2時間）
```

### 2-6. Wi-Fiのトラブル切り分け

| 症状 | 疑う原因 |
| --- | --- |
| 特定の場所だけ繋がらない | 電波の穴（デッドスポット）。RSSI測定 |
| 繋がるが遅い | **干渉**・チャネル重複・低速端末の混在 |
| 突然全員切れる（数十秒） | **DFS によるチャネル変更** |
| 移動すると切れる | ローミング設計（802.11k/v/r・セル間の重なり不足） |
| 夕方だけ遅い | 近隣オフィスの利用増（2.4GHz帯で顕著） |
| 特定端末だけ不安定 | ドライバ・省電力設定・古いチップ |
| APが再起動を繰り返す | **PoE電力不足**（→ [②](02-physical-datalink.md)） |

## 3. WAN — 拠点をつなぐ回線

### 3-1. 回線サービスの種類

| 種類 | 品質保証 | セキュリティ | コスト | 特徴 |
| --- | --- | --- | --- | --- |
| **ベストエフォート（インターネット）** | なし | 自前でVPN | **安い**（月数千〜数万円） | 光回線。品質は保証されない |
| **帯域確保型インターネット** | 一部保証 | 自前でVPN | 中 | 最低帯域を保証 |
| **広域イーサネット** | **SLAあり** | **閉域網** | **高い** | L2で拠点を接続。**自由にIP設計できる** |
| **IP-VPN** | **SLAあり** | **閉域網** | 高い | L3でキャリアが経路制御（MPLS） |
| **専用線** | **完全保証** | 物理的に占有 | **最も高い** | 帯域を占有。金融・基幹系 |
| **モバイル（LTE/5G）** | なし | 自前でVPN | 中 | **バックアップ回線・仮設拠点に最適** |
| **ローカル5G** | 自社運用 | 自社管理 | 高い | 工場・広大な敷地内 |

### 3-2. 広域イーサネットとIP-VPNの違い

| | 広域イーサネット | IP-VPN |
| --- | --- | --- |
| レイヤ | **L2** | **L3** |
| ルーティング | **自社で制御** | **キャリアが制御** |
| IP設計の自由度 | **高い**（自由） | 制約あり |
| 拠点追加 | 自社で設定 | キャリアに依頼 |
| 運用の手間 | 自社の負担が大きい | キャリア任せで楽 |
| マルチキャスト | 使いやすい | 制約が多い |

**選び方**：ネットワークを自社でコントロールしたい・技術者がいる → 広域イーサ。運用を任せたい → IP-VPN。

### 3-3. SLAで見るべき項目

```
・稼働率        : 99.9%（年間8.7時間停止）／ 99.99%（年間52分）
・遅延（RTT）   : 国内なら 10〜30ms 程度の保証
・パケットロス率 : 0.1%以下 等
・障害復旧時間  : 4時間以内 等
・故障受付      : 24時間365日か、平日日中のみか
```

> ⚠️ **「稼働率99.9%」は年間8.7時間の停止を許容する**という意味です。基幹業務なら99.99%以上、あるいは**2回線構成**を検討してください。

### 3-4. 回線選定の判断フロー

```
Q1. 止まると事業が止まるか？
    YES → 冗長化必須（異なるキャリア・異なる物理経路）
    
Q2. リアルタイム性（音声・映像・制御）が必要か？
    YES → 閉域網（広域イーサ/IP-VPN）または帯域確保型
    NO  → ベストエフォート＋VPNで十分
    
Q3. 通信量はどれくらいか？
    大量・常時 → 帯域固定の方が結果的に安い
    変動が大きい → 従量・バースト可能なサービス
    
Q4. 拠点は今後増えるか？
    増える → SD-WAN で管理を簡素化（後述）
```

### 3-5. コストの目安（日本国内・参考値）

| 回線 | 帯域 | 月額目安 |
| --- | --- | --- |
| 光ベストエフォート（法人） | 1Gbps（共有） | 5,000〜20,000円 |
| 帯域確保型 | 100Mbps保証 | 5万〜15万円 |
| 広域イーサネット | 100Mbps | 10万〜30万円/拠点 |
| IP-VPN | 100Mbps | 10万〜30万円/拠点 |
| 専用線 | 100Mbps | 30万円〜 |
| モバイル（法人・大容量） | — | 5,000〜15,000円/回線 |

※ 地域・距離・キャリア・契約期間で大きく変動します。**必ず相見積もりを取ってください**。

> 📖 光回線の物理的な仕組み（PON・FTTH・幹線）については [光通信ネットワークの全体像](../optical-fiber-network-guide.md) を参照。

## 4. WAN の冗長化

### 4-1. 冗長化のレベル

| レベル | 構成 | 防げる障害 |
| --- | --- | --- |
| **1. 単一回線** | 1本 | なし |
| **2. 同一キャリア2回線** | 主＋副 | 機器故障 |
| **3. 異キャリア2回線** | 例：NTT＋KDDI | **キャリア全体の障害** |
| **4. 異キャリア＋異メディア** | 光＋モバイル5G | **地域の光ケーブル切断** |
| **5. ＋異経路（引込口も分ける）** | 建物への引込を別ルートに | **工事事故・災害** |

> ⚠️ **「2社と契約したから安心」とは限りません。** 契約は別でも、**同じ電柱・同じ管路を通っている**ことがよくあります。重要拠点では**物理経路の確認（ルートダイバーシティ）**をキャリアに依頼してください。

### 4-2. 切り替え方式

| 方式 | 動作 | 特徴 |
| --- | --- | --- |
| **アクティブ/スタンバイ** | 主が落ちたら副に切替 | シンプル。副回線が遊ぶ |
| **アクティブ/アクティブ** | 常時両方使う | 帯域を有効活用。設計が複雑 |
| **フローティングスタティック** | AD値で優先度を付ける | 小規模の定番（→ [④](04-routing.md)） |
| **BGP/OSPF による自動切替** | 動的ルーティングで迂回 | 中〜大規模 |
| **SD-WAN による自動切替** | 品質を測って動的に選択 | **最も柔軟**（後述） |

## 5. SD-WAN — WANをソフトウェアで制御する

### 5-1. 何を解決するのか

```
【従来のWAN】
  問題1: 拠点追加のたびにルータへログインして手作業設定
  問題2: 回線が「生きているか」しか見ておらず、「品質が悪い」を検知できない
  問題3: クラウド利用なのに本社経由（ヘアピン）で遅い
  問題4: 高価なIP-VPNを、重要でない通信にも使っている

【SD-WAN】
  解決1: 中央のコントローラから全拠点を一括管理（ゼロタッチ導入）
  解決2: 遅延・ジッタ・ロスを常時測定し、品質の良い回線を自動選択
  解決3: SaaS宛ては拠点から直接インターネットへ（ローカルブレイクアウト）
  解決4: 通信の重要度で回線を使い分け（アプリケーション単位）
```

### 5-2. アプリケーション単位の経路制御

```
拠点のSD-WANルータ
  ├─ 基幹システム（ERP）        → IP-VPN（高品質・高価）
  ├─ Web会議・音声              → 品質の良い方を動的に選択
  ├─ Microsoft 365 / SaaS       → インターネットへ直接（ローカルブレイクアウト）
  └─ バックアップ・OS更新        → 安いインターネット回線（帯域制限付き）
```

これにより、**高価な閉域網の帯域を、本当に必要な通信だけに使える**ようになります。多拠点企業では回線費用の削減効果が大きくなります。

### 5-3. 導入の判断

| 向いている | 向いていない |
| --- | --- |
| **拠点が5〜10以上ある** | 拠点が1〜2 |
| クラウド/SaaSの利用が多い | 社内システム中心 |
| 拠点の増減が頻繁 | 構成が固定的 |
| 拠点に技術者がいない | 各拠点に技術者がいる |
| 回線費用を最適化したい | 既に最小構成 |

**注意点**：
- **コントローラ（管理基盤）が単一障害点**になり得る → 冗長性を確認
- **ベンダーロックイン**が強い（機器・ライセンス・運用が一体）
- ライセンスが年額課金で、**長期では機器購入より高くなる**場合がある

### 5-4. SD-WAN と SASE の関係

```
SD-WAN  : 「どの回線で送るか」を最適化する（ネットワーク側）
SSE     : 「安全に通す」を担う（セキュリティ側 → ⑥章）
SASE    : SD-WAN + SSE を統合したもの
```

近年は**SD-WANベンダーとセキュリティベンダーの統合**が進み、両者は同じ製品群として提供されることが増えています。

## 6. モバイル回線の活用

### 6-1. 用途

| 用途 | 内容 |
| --- | --- |
| **バックアップ回線** | 光回線障害時に自動切替。**最もコスパが良い冗長化** |
| **仮設・臨時拠点** | 工事現場・イベント会場・催事出店 |
| **新拠点の即日開通** | 光回線の開通には1〜2ヶ月かかる。その間の繋ぎ |
| **車両・移動体** | 配送・営業車 |
| **IoT** | センサー・自販機・デジタルサイネージ（LPWA含む） |

### 6-2. 5Gの実際

| 特性 | 理論値 | 実務での注意 |
| --- | --- | --- |
| 高速大容量 | 20Gbps | **実効速度は数百Mbps程度**。エリアと時間帯に大きく依存 |
| **低遅延** | 1ms | **超低遅延はSA構成＋MEC前提**。一般契約では実現しない |
| 多数同時接続 | 100万台/km² | IoT向け。企業利用では体感しにくい |

> ⚠️ **「5Gだから低遅延」は誤解を招く表現**です。日本の商用5Gの多くはNSA（既存4G設備を併用）で、遅延は4Gと大きく変わりません。**低遅延を要件にするなら、実測してから判断**してください。

### 6-3. ローカル5G

自社の敷地内に自前の5G網を構築する仕組みです。

| 向いている | 課題 |
| --- | --- |
| 工場・倉庫の無線化（Wi-Fiより広範囲・干渉に強い） | **免許が必要**・初期費用が高額 |
| 建設現場・港湾・空港 | 対応端末が限られる |
| 高信頼が必要な制御通信 | 運用に専門知識が必要 |

**現時点では「Wi-Fi 6E/7 で足りないか」を先に検討**するのが現実的です。

## 7. よくある疑問（FAQ）

**Q. Wi-Fi 7 に今すぐ更改すべき？**
A. 端末側がまだ追いついていないため、**急ぐ必要はありません**。ただし**AP更改のタイミングであれば Wi-Fi 6E 以上を選ぶ**べきです。6GHz帯が使えるかどうかが、今後の高密度環境での差になります。

**Q. メッシュWi-Fiは企業で使える？**
A. 小規模オフィス・店舗なら有効です。ただし**中継段数が増えるほど帯域が半減**するため、**有線バックホール（各APを有線で接続）が可能なら必ずそちらを選んでください**。

**Q. インターネットVPNで拠点間を繋ぐのは危険？**
A. 暗号化されるので機密性は保たれます。問題は**品質が保証されないこと**。音声・映像・基幹システムを流すなら閉域網、そうでなければインターネットVPNで十分、という判断になります。

**Q. 回線を増速すれば遅さは解決する？**
A. **原因が帯域不足の場合のみ**です。実際には遅延（RTT）・Wi-Fiの干渉・DNS・サーバー側が原因のことが多く、増速しても変わりません。**増速前に必ずボトルネックを特定**してください（→ [⑪](11-operations.md)）。

**Q. 各拠点にファイアウォールを置くべき？それとも本社集約？**
A. 拠点数が少なく通信量が小さいなら本社集約が安価。拠点が多い・SaaS利用が多いなら**ローカルブレイクアウト＋SASE**の方が快適かつ結果的に安くなります（→ [⑨](09-scale-patterns.md)・[⑩](10-onprem-cloud-hybrid.md)）。
