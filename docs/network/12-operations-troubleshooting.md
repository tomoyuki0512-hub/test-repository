# ⑫ 運用・監視・トラブルシュート

[← 総合インデックスに戻る](README.md) ｜ 前 → [⑪](11-scale-comparison.md) ｜ 次 → [用語集・チートシート](glossary.md)

構築が終わってからのほうが、ネットワークの人生は長いです。
この章は **「止まったことに気づき、原因を突き止め、二度と同じことを起こさない」** ための実務です。

---

## 1. 監視 — 何を見るか

### 監視の4分類

| 分類 | 見るもの | 例 |
| --- | --- | --- |
| **死活監視** | 生きているか | ping・SNMP応答・ポート接続 |
| **性能監視** | 使用率・傾向 | 帯域使用率・CPU・メモリ・セッション数 |
| **品質監視** | 通信が健全か | パケットロス・遅延・ジッタ・エラーカウンタ |
| **ログ監視** | 何が起きたか | Syslog・認証失敗・設定変更 |

### 最低限の監視項目

| 対象 | 項目 | 閾値の目安 |
| --- | --- | --- |
| **回線・上位リンク** | 帯域使用率 | **70%で警告、85%で危険**（バーストを考慮） |
| インターフェース | エラー・破棄カウンタ | 増加傾向があれば調査（0が正常） |
| 機器 | CPU / メモリ | 80% |
| FW | **セッション数** | 上限の70%（枯渇すると新規接続不能） |
| 機器 | 温度・電源・ファン | 機器仕様に従う |
| 無線 | AP死活・チャネル使用率・接続端末数 | チャネル使用率50%超で調査 |
| DHCP | **プールの空き** | 20%を切ったら拡張検討 |
| **証明書** | 有効期限 | **30日前・14日前に通知**（→[⑤](05-application-dns-http.md)） |
| **ライセンス・保守** | 期限 | 90日前に通知 |
| 外部からの到達性 | 公開サービスの応答 | 外部拠点からの合成監視 |

> 🔑 **「エラーカウンタ」と「証明書期限」は見落とされがちですが、事故率が高い項目です。**
> エラーカウンタの緩やかな増加は、ケーブル劣化・コネクタ不良の予兆です。壊れる前に交換できます。

### 監視プロトコル

| 方式 | 用途 | 注意点 |
| --- | --- | --- |
| **SNMP** | 機器のメトリクス取得（帯域・CPU・エラー） | **v1/v2cは平文でコミュニティ名が流れる**。可能なら**v3** |
| **SNMPトラップ** | 機器からの能動通知 | UDPなので**届かないことがある**。ポーリングと併用 |
| **Syslog** | ログの集約 | UDPは欠損する。**重要ログはTCP/TLS**で |
| **NetFlow / sFlow / IPFIX** | **「誰が」「どこと」「どれだけ」通信したか** | 帯域逼迫の原因特定に必須。sFlowはサンプリング |
| **ICMP（ping）** | 死活・RTT | 応答しない設定の機器もある |
| **合成監視（外形監視）** | 実際のユーザー体験を模擬 | **「サーバは生きているがユーザーは使えない」を検知できる** |

> 💡 **NetFlow/sFlowの価値**：「回線が詰まっている」ことはSNMPで分かりますが、**「誰の何の通信が原因か」はNetFlowでしか分かりません**。バックアップ・OS更新・動画視聴・不正な通信——原因が特定できて初めて対処できます。移行前の[通信量実測](11-scale-comparison.md)にも使います。

### アラート設計 — 「無視されない」ようにする

| 原則 | 内容 |
| --- | --- |
| **重要度を分ける** | Critical（即時対応）／Warning（翌営業日）／Info（記録のみ） |
| **フラッピング対策** | 「3回連続失敗で通知」など。1回の瞬断で叩き起こさない |
| **集約する** | スイッチ1台のダウンで配下50ポートが同時にアラート → **親子関係を定義して1通知に** |
| **通知先を明確に** | 誰が対応するか。夜間は誰か |
| **定期的な棚卸し** | 対応不能・意味のないアラートは**消す** |

> ⚠️ **アラート疲れは、監視していないのと同じかそれより危険です。** 毎日100件届く環境では、本当に重要な1件が埋もれます。「対応しないアラートは止める」判断を定期的に。

## 2. トラブルシュートの基本手順

### 鉄則：下位層から順に確認する

```
L1 物理    ケーブルは繋がっているか。リンクLEDは点いているか
   ↓ OK
L2 データリンク  MACは学習されているか。VLANは正しいか。ループはないか
   ↓ OK
L3 ネットワーク  IPは正しいか。ping は通るか。経路は正しいか
   ↓ OK
L4 トランスポート ポートは開いているか。FWで落ちていないか
   ↓ OK
L7 アプリ    DNSは引けるか。証明書は有効か。アプリは正常か
```

> 🔑 **「Webが見られない」と言われて、いきなりWebサーバのログを見に行かないこと。**
> 実際には「LANケーブルが抜けていた」「DHCPが枯渇していた」「DNSが引けなかった」ことが多く、**順に潰すほうが結果的に速い**です。

### 切り分けの3つの質問

障害報告を受けたら、まずこれを聞きます。

| 質問 | 分かること |
| --- | --- |
| **① 誰が影響を受けているか**（1人／1フロア／全社／特定拠点） | **影響範囲＝壊れている機器の位置**が絞れる |
| **② いつから起きているか。直前に何か変更したか** | **変更が原因である確率は非常に高い** |
| **③ 何ができて、何ができないか**（全部ダメ／特定サイトだけ／遅いだけ） | レイヤの当たりがつく |

```
影響範囲から場所を絞る：

  1人だけ        → その端末・ポート・ケーブル
  同じ島の数人    → そのアクセススイッチ
  1フロア        → フロアSW・上位リンク
  1拠点          → 拠点ルータ・WAN回線
  全社           → コアSW・FW・インターネット回線・DNS
  特定サービスのみ → そのサーバ・経路・DNS・証明書
```

### 「特定のサイトだけ見られない」の切り分け例

```
① 他のサイトは見られるか
   → 全部ダメなら回線/DNS。1つだけなら次へ

② 名前解決できるか      dig example.com
   → 引けない → DNS問題（社内DNS？ TTL？ 相手のDNS？）

③ IPに到達するか        ping / traceroute
   → 届かない → 経路 or 相手側のダウン

④ ポートは開いているか   nc -zv example.com 443
   → 開かない → FW/SGで遮断されている

⑤ TLSは成立するか       openssl s_client -connect example.com:443
   → 失敗 → 証明書期限切れ・時刻ずれ・TLSバージョン不一致

⑥ HTTPの応答は          curl -v https://example.com
   → ステータスコードで原因を判別
```

## 3. コマンド集

### 到達性・経路

| コマンド | 用途 |
| --- | --- |
| `ping -c 5 8.8.8.8` | 到達確認・RTT・ロス率 |
| `ping -s 1472 -M do 8.8.8.8` | **MTU検証**（フラグメント禁止で送る） |
| `traceroute 8.8.8.8` / `tracert` | 経路確認 |
| **`mtr -rwbzc 100 8.8.8.8`** | **traceroute＋継続的なロス測定。切り分けに最強** |
| `ip route` / `route print` | ルーティングテーブル |
| `ip neigh` / `arp -a` | ARPテーブル |

### ポート・コネクション

| コマンド | 用途 |
| --- | --- |
| `ss -tlnp` | **LISTENしているポートとプロセス** |
| `ss -ant` | 全TCPコネクションと状態 |
| `ss -ant \| awk '{print $1}' \| sort \| uniq -c` | 状態別の集計（CLOSE_WAIT等の検出） |
| `nc -zv host 443` | ポートの疎通確認 |
| `Test-NetConnection host -Port 443` | 同上（PowerShell） |

### DNS

| コマンド | 用途 |
| --- | --- |
| `dig example.com` | 名前解決 |
| **`dig @8.8.8.8 example.com`** | **外部リゾルバで確認**（社内DNSとの比較） |
| `dig +trace example.com` | ルートから順に追跡 |
| `dig example.com MX` / `TXT` / `NS` | レコード種別を指定 |
| `nslookup` | Windows標準 |

### HTTP・TLS

| コマンド | 用途 |
| --- | --- |
| `curl -v https://example.com` | 詳細な通信内容 |
| `curl -o /dev/null -s -w "%{time_total}\n" URL` | 応答時間の測定 |
| `curl --resolve example.com:443:1.2.3.4 https://example.com` | **DNSを迂回して特定サーバへ**（LBの個別サーバ検証） |
| `openssl s_client -connect example.com:443 -servername example.com` | 証明書チェーンの確認 |
| `echo \| openssl s_client -connect host:443 2>/dev/null \| openssl x509 -noout -dates` | **証明書の有効期限確認** |

### パケットキャプチャ

| コマンド | 用途 |
| --- | --- |
| `tcpdump -i any port 443 -nn` | 443番の通信を表示 |
| `tcpdump -i any host 10.0.0.5 -nn -c 100` | 特定ホストとの通信を100個 |
| `tcpdump -i any -w capture.pcap` | ファイルに保存（**Wiresharkで解析**） |
| `tcpdump -i any 'tcp[tcpflags] & tcp-syn != 0'` | **SYNだけ抽出**（接続試行の確認） |

> 🔑 **「SYNは出ているが SYN+ACK が返らない」を1回確認するだけで、アプリ調査の無駄が省けます。** ほぼ確実にFW/SGの遮断です（→[④](04-transport-tcp-udp.md)）。

### 帯域測定

| コマンド | 用途 |
| --- | --- |
| `iperf3 -s` / `iperf3 -c <server>` | 実効帯域の測定 |
| `iperf3 -c <server> -P 8` | **8並列で測定**（BDPの影響を確認） |
| `iperf3 -c <server> -u -b 100M` | UDPでの測定（ジッタ・ロス） |

## 4. よくある障害と原因の対応表

| 症状 | 最も多い原因 | 確認 |
| --- | --- | --- |
| 1台だけ繋がらない | ケーブル・ポート・**ランダムMAC**・IP競合 | リンクLED・`ipconfig`・別ポートで試す |
| **IPが 169.254.x.x** | **DHCP応答なし** | DHCPサーバ・プール枯渇・リレー設定 |
| フロア全体が停止 | **ループ**・上位リンク断・PoE過負荷 | スイッチLEDの一斉点滅・エラーカウンタ |
| 全社が停止 | コアSW・FW・回線・**DNS** | 上流から順に。**まずFWのセッション数を見る** |
| **遅い（全体的に）** | 帯域逼迫・**上位リンクの収容率不足** | SNMPの帯域グラフ・**NetFlowで原因通信を特定** |
| 遅い（Webだけ） | DNS応答遅延・遠いサーバ・**MTU** | `dig` の応答時間・`curl -w` |
| **特定サイトだけ見られない** | DNS・証明書期限・FWのURLフィルタ | 上記の切り分け手順 |
| **繋がるがファイル転送だけ失敗** | **MTU / MSSクランプ未設定** | `ping -s` でサイズを変えて検証 |
| たまに切れる | **NAT/FWのアイドルタイムアウト**・無線ローミング | キープアライブ設定・無線ログ |
| 夜間だけ遅い | バックアップ・OS更新の集中 | スケジュール確認・QoS |
| **VPNは繋がるが名前解決できない** | **DNS転送設定の漏れ** | 条件付きフォワーダ・Resolverルール（→[⑩](10-hybrid-patterns.md)） |
| クラウドのサーバに繋がらない | **SGの設定漏れ**・ルートテーブル | `tcpdump` でSYNの有無を確認 |
| 認証だけ失敗する | **時刻ずれ**（Kerberos）・証明書 | NTP同期状態 |

## 5. 変更管理 — 事故の大半は変更が原因

> 🔑 **障害原因の統計をとると、「変更作業」が最大の要因になることがほとんどです。** 逆に言えば、**変更のやり方を整えるだけで障害が減ります**。

### 変更作業の型

| 段階 | やること |
| --- | --- |
| **1. 事前準備** | 影響範囲の特定・**作業手順書**・**切り戻し手順**・所要時間の見積り |
| **2. 承認** | 実施日時・影響・**中止の判断基準**を関係者に合意 |
| **3. バックアップ** | **変更前の設定を必ず取得**（自動でも手動でも） |
| **4. 実施** | 手順書どおりに。**アドリブで追加作業をしない** |
| **5. 確認** | 事前に決めた**確認項目リスト**で検証（「なんとなく大丈夫」は禁止） |
| **6. 記録** | **構成図・台帳の更新**（→[⑦](07-design-basics.md)）・作業記録の保存 |

### 必ず決めておくこと

| 項目 | 内容 |
| --- | --- |
| **切り戻し判断基準** | 「開始から30分で疎通しなければ切り戻す」など**時間で決める**。判断を現場の空気に委ねない |
| **確認項目** | 変更対象だけでなく、**影響を受けうる周辺**も確認する |
| **作業時間帯** | 業務影響が最小の時間。ただし**深夜作業は判断力が落ちる**ためリスクもある |
| **立会い体制** | 1人作業を避ける。**確認者を置く** |

> ⚠️ **リモートから機器の設定を変える際、自分の接続経路を切ってしまう事故（自爆）** が定番です。
> 対策：**コミット確認機能**（一定時間内に確認しないと自動で元に戻る）を使う、コンソールサーバ（アウトオブバンド管理）を用意する、危険な変更は必ず現地で行う。

## 6. 構成管理と自動化（IaC）

| レベル | 内容 |
| --- | --- |
| **レベル0** | 設定は機器の中だけ。**バックアップなし** ← 危険 |
| **レベル1** | 設定を**定期的に自動バックアップ**（TFTP/SCP/専用ツール） |
| **レベル2** | 設定を **Gitで管理**。差分がレビューできる |
| **レベル3** | **Ansible等で設定を投入**。手動変更を禁止 |
| **レベル4** | **CI/CDで検証してから適用**。テスト自動化 |

> 💡 **中規模なら最低でもレベル2、大規模ならレベル3以上**が目安です。
> **クラウドは Terraform 等で最初からレベル3〜4を目指せます**。オンプレでもAnsibleでVLAN追加やACL更新を自動化できます。
>
> Git管理の副次的効果は大きく、**「いつ誰が何を変えたか」が自動的に記録される**ため、障害調査が劇的に速くなります（→ [Gitコマンド一覧](../git-commands.md)）。

### 設定バックアップで必ず守ること

- **自動取得**（人間は忘れる）
- **機器の外に保存**（機器が壊れたら取り出せない）
- **世代管理**（直前だけでなく数世代）
- **復元テスト**（取れているが戻せない、が最悪）

## 7. インシデント対応

### 対応の流れ

```mermaid
flowchart LR
    D["① 検知"] --> T["② 一次切り分け<br/>影響範囲の特定"]
    T --> C["③ 情報共有<br/>関係者へ第一報"]
    C --> R["④ 復旧<br/>（原因究明より優先）"]
    R --> RC["⑤ 原因究明"]
    RC --> P["⑥ 再発防止"]
```

> 🔑 **「復旧」と「原因究明」を分けることが最も重要です。**
> 業務が止まっている最中に原因を探し続けるのは間違いです。**まず再起動・切り戻し・迂回で業務を戻し、原因究明はその後**に行います。ただし、**復旧前にログとキャプチャを保存**しておかないと、原因が永遠に分からなくなります。

### 第一報のテンプレート

```
【障害発生】〇〇システムに接続できない事象
・発生時刻：8/21 10:15頃
・影響範囲：大阪支社の全ユーザー（約80名）
・症状   ：社内システムへ接続不可。インターネットは利用可能
・現状   ：拠点ルータのWAN側リンクダウンを確認。回線事業者へ連絡済み
・見込み ：11:30に次報。復旧見込みは事業者回答待ち
・回避策 ：緊急の場合はモバイル回線経由でVPN接続を利用してください
```

**「分かっていないこと」も明示する**のがコツです。憶測での復旧見込みを伝えると、後で信頼を失います。

### ポストモーテム（振り返り）

| 項目 | 内容 |
| --- | --- |
| **時系列** | 何がいつ起きたか（検知・対応・復旧の各時刻） |
| **影響** | 誰が何分間、何をできなかったか |
| **直接原因** | 技術的に何が起きたか |
| **根本原因** | **なぜそれが起きたか**（設計・手順・監視の不備） |
| **再発防止策** | **具体的なアクションと担当者と期限** |

> ⚠️ **個人を責めないこと（ブレームレス）。** 「Aさんが手順を間違えた」ではなく「**手順書が間違えやすい構造だった**」「**確認者がいなかった**」と捉えます。人を責める文化では、次から報告が上がらなくなり、障害は見えなくなるだけです。

## 8. 日常の運用タスク

| 頻度 | タスク |
| --- | --- |
| **毎日** | アラートの確認・障害の一次対応 |
| **毎週** | 帯域・リソースのトレンド確認・バックアップ成否の確認 |
| **毎月** | ファームウェア/パッチの適用検討・**証明書とライセンスの期限確認**・コスト確認（クラウド） |
| **四半期** | FWルールの棚卸し・アカウント棚卸し・**構成図と台帳の更新確認** |
| **半期** | **冗長化の切替試験**・容量計画の見直し |
| **年次** | **DR訓練**・機器のEOL/保守期限の確認・次年度予算策定・セキュリティ診断 |

> 🔑 **「半期の切替試験」と「年次のDR訓練」は、忙しさを理由に最も飛ばされやすく、飛ばした結果が最も高くつく項目**です。カレンダーに固定で入れてください。

## 9. この章のまとめ

| 覚えること | 一言で |
| --- | --- |
| 監視 | 死活・性能・品質・ログの4分類。**証明書期限とエラーカウンタ**を忘れずに |
| NetFlow | 「詰まっている」から「**誰の何の通信が原因か**」へ進むために必須 |
| アラート | **無視されるアラートは害**。集約・重要度分け・棚卸し |
| **切り分け** | **下位層から順に**。①影響範囲 ②いつから・直前の変更 ③何ができないか |
| コマンド | `mtr`・`dig @8.8.8.8`・`ss -ant`・`tcpdump`（SYNの有無）が主力 |
| **変更管理** | **障害原因の最大要因**。切り戻し手順と**時間による判断基準**を事前に決める |
| 構成管理 | **設定はGitへ**。自動バックアップ＋復元テスト |
| インシデント | **復旧を最優先**。ただし**ログとキャプチャは先に保存** |
| 振り返り | **人ではなく仕組みを責める**。具体的な再発防止策に落とす |
| 定期タスク | **切替試験とDR訓練を飛ばさない** |
