# ③ IPアドレスとサブネット

> **この章のゴール**：サブネットマスクを見て「何台入るか」「同じネットワークか」を即答できるようになる。そして、後からやり直しの効かないIPアドレス設計を、最初から正しく引けるようになる。

← [② 物理層とデータリンク層](02-physical-datalink.md) ／ 次章 → [④ ルーティング](04-routing.md)

---

## 0. まず全体像（30秒）

IPアドレスは **「ネットワーク部」＋「ホスト部」** の2つに分かれています。

```
   192.168.10.25 / 24
   └───────┘ └┘  └┘
   ネットワーク部 ホスト部  プレフィックス長
   （どの町か）  （何番地か） （ネットワーク部が何ビットか）

  /24 = 上位24ビットがネットワーク部
      = 192.168.10.0 〜 192.168.10.255 が同じ町
      = 使えるホストは 254台（.0 と .255 は予約）
```

この「町（ネットワーク）」の切り方を決めるのが **サブネット設計** です。そして本章で最も伝えたいのはこれです。

> ⚠️ **IPアドレス設計はやり直しが効きません。** 建物の間取りと同じで、後から変えるにはシステム全体を止める必要があります。**最初に将来の3倍で確保してください。**

## 1. IPv4アドレスの基本

### 1-1. 32ビットを8ビットずつ区切っている

```
  192   .   168   .    10   .    25
11000000 . 10101000 . 00001010 . 00011001
└──8bit┘  └──8bit┘  └──8bit┘  └──8bit┘   合計32ビット
```

各区切りを **オクテット** と呼びます。0〜255の範囲になるのは、8ビットで表せる数が256通りだからです。

### 1-2. グローバルIPとプライベートIP

| 種類 | 範囲 | 用途 |
| --- | --- | --- |
| **プライベートIP（クラスA）** | 10.0.0.0 〜 10.255.255.255（/8） | **大規模。1677万台**。企業・クラウドVPCの定番 |
| **プライベートIP（クラスB）** | 172.16.0.0 〜 172.31.255.255（/12） | 中規模。104万台 |
| **プライベートIP（クラスC）** | 192.168.0.0 〜 192.168.255.255（/16） | 小規模。6.5万台。家庭用ルータの既定 |
| **グローバルIP** | 上記以外の大部分 | インターネット上で一意。ISPから割当 |

**プライベートIPは「社内でだけ通じる住所」**です。インターネットにはそのまま出られないので、NAT（後述）で変換します。

#### その他の特殊なアドレス

| 範囲 | 名称 | 意味 |
| --- | --- | --- |
| 127.0.0.0/8 | ループバック | 自分自身（`127.0.0.1` = localhost） |
| 169.254.0.0/16 | **リンクローカル（APIPA）** | **DHCPに失敗したときに自動で付く**。これが出たら異常 |
| 100.64.0.0/10 | CGNAT | ISPが加入者に配る共有アドレス |
| 224.0.0.0/4 | マルチキャスト | グループ配信用 |

> 💡 **`169.254.x.x` が付いていたら、DHCPサーバーに到達できていません。** ケーブル・VLAN・DHCPサーバーの順に疑ってください。これは現場で頻出の切り分けポイントです。

### 1-3. クラスフルアドレスは「歴史」

古い教科書にある「クラスA/B/C」は、**1993年のCIDR導入で実質廃止**されています。現在は `/24` のようなプレフィックス長で自由に区切ります（クラスレス）。

ただし**用語としては会話に残っている**ため（「クラスCのアドレス帯」＝192.168系、といった言い方）、知識としては知っておく必要があります。

## 2. サブネットマスク — 境界を決める

### 2-1. サブネットマスクとは

「上位何ビットがネットワーク部か」を示す32ビットの値です。**1が連続する部分がネットワーク部**。

```
IPアドレス      : 192.168.10.25
サブネットマスク : 255.255.255.0
                  11111111.11111111.11111111.00000000
                  └──── ネットワーク部（24bit）────┘└ホスト部┘

→ CIDR表記では /24
```

### 2-2. 変換早見表（暗記推奨）

| CIDR | サブネットマスク | ホスト数（使用可） | よくある用途 |
| --- | --- | --- | --- |
| /30 | 255.255.255.252 | **2** | ルータ間のP2Pリンク |
| /29 | 255.255.255.248 | 6 | 小さなDMZ |
| /28 | 255.255.255.240 | 14 | サーバーセグメント（小） |
| /27 | 255.255.255.224 | 30 | 小規模オフィスの1島 |
| /26 | 255.255.255.192 | 62 | 部署単位 |
| /25 | 255.255.255.128 | 126 | フロア単位 |
| **/24** | **255.255.255.0** | **254** | **最も一般的**。1VLAN=1/24が定番 |
| /23 | 255.255.254.0 | 510 | 大きめのクライアントVLAN |
| /22 | 255.255.252.0 | 1022 | 大規模フロア |
| /16 | 255.255.0.0 | 65534 | 拠点全体の集約 |
| /8 | 255.0.0.0 | 16777214 | 全社の予約帯 |

**計算式**：使用可能ホスト数 = 2^(32−プレフィックス長) − 2

−2 する理由は、**ネットワークアドレス（全ビット0）** と **ブロードキャストアドレス（全ビット1）** が予約されているからです。

> 💡 **暗記のコツ**：/24=254 を起点に、**1ビット減るごとに倍、増えるごとに半分**。
> /24=254 → /23=510 → /22=1022 ／ /25=126 → /26=62 → /27=30 → /28=14 → /29=6 → /30=2

### 2-3. 実践：このIPはどのネットワークに属するか

**問**：`192.168.10.100/26` のネットワークアドレス・ブロードキャストアドレス・使えるIP範囲は？

```
/26 → ホスト部6ビット → 1ブロック = 64個
→ 第4オクテットは 0-63 / 64-127 / 128-191 / 192-255 に区切られる
→ 100 は「64-127」のブロックに入る

ネットワークアドレス   : 192.168.10.64
使用可能な範囲        : 192.168.10.65 〜 192.168.10.126  （62台）
ブロードキャスト      : 192.168.10.127
```

**問**：`192.168.10.100/26` と `192.168.10.130/26` は直接通信できるか？

```
100 → ブロック「64-127」
130 → ブロック「128-191」
→ 別ネットワーク。ルータ（L3）を経由しないと通信できない
```

> 💡 **実務での即答テクニック**：256 − マスクの最終値 = ブロックサイズ。
> /26 なら 256−192 = **64** きざみ。/28 なら 256−240 = **16** きざみ。

### 2-4. CIDRと経路集約

複数のネットワークを1つにまとめて表現することを **集約（サマライズ）** といいます。

```
10.10.0.0/24
10.10.1.0/24   →  まとめて 10.10.0.0/22 と表現できる
10.10.2.0/24
10.10.3.0/24
```

これができると**ルーティングテーブルが小さくなり、機器の負荷が下がります**。だからこそ、**IPアドレスは連番で計画的に割り当てるべき**なのです。バラバラに割り当てると集約できません。

## 3. IPアドレス設計の実務

### 3-1. 設計の鉄則

| 鉄則 | 理由 |
| --- | --- |
| **将来の3倍で確保する** | 拠点増・IoT機器増・仮想マシン増は必ず起きる |
| **拠点ごとに大きなブロックを予約** | 後から追加VLANを切っても集約が壊れない |
| **VLAN IDとIPの一部を一致させる** | 運用時に暗算不要になる。事故が減る |
| **クラウドと重複させない** | 後で VPN/専用線を繋ぐときに詰む（**最頻出の事故**） |
| **192.168.0.0/24・192.168.1.0/24 は避ける** | 家庭用ルータの既定値。在宅VPNで衝突する |

> ⚠️ **最も多い設計事故**：本社が `192.168.1.0/24` を使っていて、社員の自宅ルータも `192.168.1.0/24`。**VPN接続すると、自宅のプリンタと社内サーバーのIPが被って通信不能**になります。企業では `10.x.x.x` 帯を使うのが安全です。

### 3-2. 設計例：3拠点＋クラウドの中規模企業

```
全社の予約帯: 10.0.0.0/8

【拠点ごとに /16 を予約】
  10.10.0.0/16  本社
  10.20.0.0/16  大阪支社
  10.30.0.0/16  名古屋支社
  10.40.0.0/16  （将来の拠点用に予約）
  10.100.0.0/16 データセンタ
  10.200.0.0/16 クラウド（AWS VPC など）

【本社の内訳（第3オクテット = VLAN ID）】
  10.10.10.0/24  VLAN10  有線クライアント     254台
  10.10.20.0/24  VLAN20  無線クライアント     254台
  10.10.30.0/24  VLAN30  ゲストWi-Fi
  10.10.40.0/24  VLAN40  サーバー
  10.10.50.0/24  VLAN50  IP電話
  10.10.60.0/24  VLAN60  監視カメラ・IoT
  10.10.99.0/24  VLAN99  機器管理用
  10.10.255.0/24         ルータ間リンク（/30 に細分）
```

この設計の利点：

- 拠点ごとに `/16` なので、**拠点単位で1行に集約**できる（経路表が小さい）
- 「10.20.x.x を見たら大阪」と**IPを見ただけで場所が分かる**
- VLAN番号と第3オクテットが一致しているので、**設定ミスに気づきやすい**
- クラウド用に別ブロックを予約済みなので、**将来のVPC接続で衝突しない**

### 3-3. 各セグメント内の番地割り当てルール

セグメント内も、**役割ごとに範囲を決めておく**と運用が楽になります。

| 範囲 | 用途 |
| --- | --- |
| `.1` | デフォルトゲートウェイ（ルータ/L3スイッチ） |
| `.2 〜 .9` | ネットワーク機器（スイッチ、AP の管理IP） |
| `.10 〜 .99` | **サーバー・プリンタなどの固定IP機器** |
| `.100 〜 .199` | **DHCP動的払い出し範囲** |
| `.200 〜 .250` | 予備・一時利用 |
| `.251 〜 .254` | 冗長化用（VRRP/HSRPの実IP） |

**固定IP範囲とDHCP範囲は必ず分ける**こと。重なるとIPアドレス重複という厄介な障害が起きます。

## 4. DHCP — IPアドレスを自動で配る

### 4-1. 動作の流れ（DORA）

```
1. Discover  端末 →（ブロードキャスト）「誰かIPください」
2. Offer     サーバー → 端末            「192.168.1.100 どう？」
3. Request   端末 →（ブロードキャスト）「それください」
4. Ack       サーバー → 端末            「はいどうぞ。リース期間8時間」
```

頭文字を取って **DORA** と覚えます。

### 4-2. DHCPで配られる情報

IPアドレスだけではありません。ここが重要です。

| 情報 | オプション番号 | 内容 |
| --- | --- | --- |
| IPアドレス／サブネットマスク | — | 住所 |
| **デフォルトゲートウェイ** | 3 | これがないと外に出られない |
| **DNSサーバー** | 6 | これがないと名前解決できない |
| ドメイン名 | 15 | 検索サフィックス |
| NTPサーバー | 42 | 時刻同期 |
| TFTPサーバー | 66/150 | IP電話の設定配布 |

### 4-3. DHCPリレー（IP Helper）

DHCPの Discover は**ブロードキャスト**なので、**ルータを越えられません**。VLANごとにDHCPサーバーを置くのは非現実的なので、**L3スイッチ/ルータがブロードキャストを受け取ってユニキャストで転送**します。

```
設定例（Cisco）:
  interface Vlan10
   ip helper-address 10.10.40.10    ← DHCPサーバーのIP
```

> ⚠️ **VLANを新設したのにIPが取れない**——原因の大半は **`ip helper-address` の設定漏れ**です。VLAN追加時のチェックリストに必ず入れてください。

### 4-4. リース期間の設計

| 環境 | 推奨リース期間 | 理由 |
| --- | --- | --- |
| オフィス（固定席） | 8時間〜1日 | 変動が少ない |
| フリーアドレス・会議室 | 2〜4時間 | 回転が速い |
| **ゲストWi-Fi** | **30分〜2時間** | 来客は短時間。アドレス枯渇を防ぐ |
| サーバーセグメント | 固定IP推奨 | そもそもDHCPを使わない |

## 5. ARP — IPからMACアドレスを調べる

### 5-1. 動作

```
PC: 「192.168.1.1 の人、MACアドレス教えて！」  ← ブロードキャスト
    （宛先MAC = ff:ff:ff:ff:ff:ff）

ルータ: 「私です。aa:bb:cc:dd:ee:ff です」      ← ユニキャストで応答

PC: ARPテーブルに記録（数分〜数時間キャッシュ）
```

確認コマンド：`arp -a`（Windows）／`ip neigh`（Linux）

### 5-2. GARP（Gratuitous ARP）

自分から一方的に「私のIPはこれ、MACはこれ」と宣言するARPです。以下の場面で使われます。

- **IPアドレス重複の検出**（起動時に自分のIPで問い合わせ、返事があれば重複）
- **冗長化の切り替え通知**（VRRPでマスターが切り替わったとき、周囲のARPテーブルを更新させる）
- **仮想マシンのライブマイグレーション後**（物理位置が変わったことを周知）

### 5-3. ARPスプーフィング

攻撃者が偽のARP応答を送り、**「ゲートウェイは私です」と詐称**して通信を横取りする攻撃です（中間者攻撃）。

対策は L2 の **Dynamic ARP Inspection（DAI）** ＋ **DHCPスヌーピング**（→ [②](02-physical-datalink.md)）。

## 6. NAT / NAPT — プライベートIPで外に出る

### 6-1. なぜ必要か

プライベートIPはインターネットで使えません。そこで**出口で グローバルIP に変換**します。

```
【社内】                    【ルータ】                  【インターネット】
192.168.1.10:51234  ──→  変換  ──→  203.0.113.5:40001  ──→  Webサーバー
192.168.1.11:52000  ──→  変換  ──→  203.0.113.5:40002  ──→
192.168.1.12:53100  ──→  変換  ──→  203.0.113.5:40003  ──→

  ポート番号で識別することで、1つのグローバルIPを数千台で共有できる
```

| 名称 | 変換内容 | 別名 |
| --- | --- | --- |
| **NAT（静的）** | IP ↔ IP を1対1 | スタティックNAT |
| **NAPT** | IP＋ポート を多対1 | **IPマスカレード／PAT**。**一般的にはこれ** |
| **ポートフォワーディング** | 外部ポート → 内部の特定機器 | ポート開放。DNAT |

日常会話で「NAT」と言えば、ほぼ **NAPT** のことです。

### 6-2. NATの副作用

| 問題 | 内容 | 対処 |
| --- | --- | --- |
| **外部から接続できない** | 内側からの通信しか通せない | ポートフォワーディング／VPN |
| **セッションテーブルの枯渇** | 同時接続数に上限がある | 上位機種／複数グローバルIP |
| **P2P・SIPが通りにくい** | アドレスがペイロード内にある | ALG／STUN・TURN |
| **ログの追跡が困難** | 全員が同じIPに見える | NATログの保存（法令対応で必要な場合あり） |
| **IPsec との相性** | ヘッダが壊れる | NAT-T（UDP 4500 でカプセル化） |

> 💡 **「NATはセキュリティ機能ではありません」**。外部から入れないのは副作用であって、防御を目的とした設計ではない。**ファイアウォールは別途必要です**（→ [⑥](06-security.md)）。

## 7. IPv6 — 避けて通れない次の標準

### 7-1. なぜIPv6か

IPv4の43億個は既に枯渇しています。IPv6は **128ビット = 約340澗（3.4×10³⁸）個**。事実上無限です。

```
IPv4: 192.168.1.1
IPv6: 2001:0db8:0000:0000:0000:0000:0000:0001
      ↓ 省略ルール（先頭の0を省略、連続する0のブロックを :: に）
      2001:db8::1
```

**`::` は1つのアドレスに1回だけ使えます**（複数使うと復元できないため）。

### 7-2. IPv6アドレスの種類

| 種類 | プレフィックス | 役割 |
| --- | --- | --- |
| **グローバルユニキャスト** | 2000::/3 | インターネットで使う公開アドレス |
| **リンクローカル** | **fe80::/10** | **同一リンク内でのみ有効。必ず自動生成される** |
| ユニークローカル（ULA） | fc00::/7 | IPv4のプライベートIP相当 |
| マルチキャスト | ff00::/8 | グループ配信 |
| ループバック | ::1 | 自分自身 |

**IPv6にブロードキャストは存在しません。** すべてマルチキャストで代替されます（これは効率面で大きな改善です）。

### 7-3. IPv4との主な違い

| 項目 | IPv4 | IPv6 |
| --- | --- | --- |
| アドレス長 | 32ビット | 128ビット |
| アドレス設定 | DHCP or 手動 | **SLAAC（自動構成）** or DHCPv6 |
| ARP | あり | **NDP（近隣探索）** に統合 |
| ブロードキャスト | あり | **なし**（マルチキャストで代替） |
| NAT | ほぼ必須 | **原則不要**（全部グローバル） |
| ヘッダ | 可変長・複雑 | 固定40バイト・シンプル |
| フラグメント | ルータでも実施 | **送信元のみ**（PMTUD必須） |
| 標準サブネット | 可変 | **/64 が事実上固定** |

> 💡 **`/64` は絶対に守る**：SLAAC（自動アドレス構成）が `/64` を前提に設計されているため、`/64` より小さく切ると自動構成が動きません。**IPv6でサブネットをケチる意味はありません**（アドレスは無限にあるので）。

### 7-4. 移行方式

| 方式 | 説明 | 現在の主流 |
| --- | --- | --- |
| **デュアルスタック** | IPv4とIPv6を両方有効にする | ✅ **これが基本** |
| トンネル（6in4等） | IPv4網の中をIPv6が通る | 過渡期の技術 |
| 変換（NAT64/DNS64） | IPv6のみの端末がIPv4サーバーへ | モバイル網で利用 |

日本の家庭用回線では **IPv6 IPoE（IPv4 over IPv6）** が主流になっており、これは「IPv6網を使ってIPv4通信も高速化する」方式です。PPPoEの輻輳を回避できるため、**「夜だけ遅い」の解決策**としてよく使われます。

## 8. ICMP — 疎通確認の道具

`ping` と `traceroute` が使うプロトコルです。

| タイプ | 名称 | 用途 |
| --- | --- | --- |
| 0 / 8 | Echo Reply / Request | **ping** |
| 3 | Destination Unreachable | 到達不能通知。**Code 4 は「要フラグメント」＝PMTUDで必須** |
| 11 | Time Exceeded | TTL切れ。**traceroute の仕組みの根幹** |

> ⚠️ **ICMPを全部ブロックしてはいけません。** セキュリティのつもりで ICMP を全遮断すると、**Path MTU Discovery が壊れて「大きい通信だけ失敗する」**という原因不明のトラブルを招きます。少なくとも **Type 3 Code 4** は通してください。

### traceroute の仕組み

```
TTL=1 で送る → 1台目のルータで破棄され「Time Exceeded」が返る → 1台目が判明
TTL=2 で送る → 2台目のルータで破棄され「Time Exceeded」が返る → 2台目が判明
...これを繰り返して経路全体を可視化する
```

## 9. よくある疑問（FAQ）

**Q. `/24` を超えて 500台入れたい。`/23` にすれば良い？**
A. 技術的には可能ですが、**推奨しません**。1セグメントの端末が増えるとブロードキャストとARPの負荷が上がり、障害の影響範囲も広がります。**VLANを分けて `/24` を複数用意する**のが定石です（目安：1セグメント250台以内）。

**Q. サブネットマスクが違うと通信できないのはなぜ？**
A. 「同じネットワークか外か」の判定結果がズレるからです。片方が「同じネットワークだ」と思ってARPを投げても、相手は「外だ」と思ってゲートウェイに投げる、という食い違いが起きます。**同一セグメント内では全機器のマスクを一致させてください**。

**Q. IPv6にするとNATが要らなくなるが、セキュリティは大丈夫？**
A. NATはもともとセキュリティ機能ではありません。IPv6では**ステートフルファイアウォールで明示的に制御**します。実質的にやることは変わりません（むしろ設計が明確になります）。

**Q. クラウドのVPCも同じ考え方でいい？**
A. 基本は同じですが、**クラウド側は「1サブネット＝1AZ」という制約**があり、可用性のためにAZごとにサブネットを切る必要があります。詳細は [⑧ クラウドネットワーク](08-cloud-network.md) を参照してください。

## まとめ

- IPアドレスは **ネットワーク部＋ホスト部**。境界を決めるのがサブネットマスク
- **/24=254台** を起点に、1ビットで倍/半分と覚える
- **256 − マスク値 = ブロックサイズ** で暗算できる
- **IPアドレス設計はやり直しが効かない**。将来の3倍、拠点ごとに大きなブロック、クラウドと重複させない
- `192.168.0.0/24` `192.168.1.0/24` は在宅VPNで衝突するので企業では避ける
- **`169.254.x.x` が出たらDHCP到達不能**
- 新VLAN作成時は **`ip helper-address` の設定を忘れない**
- **NATはセキュリティ機能ではない**
- IPv6は **デュアルスタック** で共存。サブネットは **`/64` 固定**
