# ⑧ クラウドネットワーク

> **この章のゴール**：オンプレの知識をクラウドに翻訳できるようになる。VPC・サブネット・セキュリティグループ・ロードバランサ・専用線という、クラウド設計の骨格を押さえる。

← [⑦ 無線LANとWAN](07-wireless-wan.md) ／ 次章 → [⑨ 規模別ネットワーク構成パターン](09-scale-patterns.md)

---

## 0. まず全体像（30秒）

クラウドのネットワークは、**オンプレの概念をソフトウェアで再現したもの**です。名前が違うだけで、やっていることは同じです。

| オンプレ | AWS | Azure | Google Cloud |
| --- | --- | --- | --- |
| 拠点のネットワーク全体 | **VPC** | **VNet** | **VPC**（グローバル） |
| VLAN / セグメント | サブネット | サブネット | サブネット |
| L3スイッチ・ルータ | （暗黙のルータ）＋ルートテーブル | システムルート | ルート |
| ファイアウォール（機器） | **セキュリティグループ** / NACL | NSG | ファイアウォールルール |
| インターネット回線 | **Internet Gateway** | パブリックIP | 外部IP |
| NATルータ | **NAT Gateway** | NAT Gateway | Cloud NAT |
| ロードバランサ | ALB / NLB | Load Balancer | Cloud Load Balancing |
| 専用線 | **Direct Connect** | **ExpressRoute** | **Cloud Interconnect** |
| VPN装置 | Site-to-Site VPN | VPN Gateway | Cloud VPN |
| 内部DNS | Route 53 Resolver | Private DNS | Cloud DNS |

**この対応表を頭に入れておけば、クラウドのネットワーク設計は「知っているものの名前が違うだけ」になります。**

## 1. VPC — クラウド上の自社ネットワーク

### 1-1. VPCとは

**論理的に隔離された、自分専用のネットワーク空間**です。他の利用者からは完全に分離されています。

```
VPC: 10.0.0.0/16   ← 最初に決めるCIDR。ここが設計の起点
 │
 ├─ パブリックサブネット  10.0.1.0/24  (AZ-a)  ← インターネットから到達可能
 ├─ パブリックサブネット  10.0.2.0/24  (AZ-c)
 ├─ プライベートサブネット 10.0.11.0/24 (AZ-a)  ← 外部から直接到達不可
 ├─ プライベートサブネット 10.0.12.0/24 (AZ-c)
 ├─ DBサブネット         10.0.21.0/24 (AZ-a)  ← さらに制限
 └─ DBサブネット         10.0.22.0/24 (AZ-c)
```

### 1-2. CIDR設計の鉄則

> ⚠️ **VPCのCIDRは、後から縮小できません**（追加はできても変更・縮小は不可）。**最初の設計が最も重要です。**

| 鉄則 | 理由 |
| --- | --- |
| **オンプレと絶対に重複させない** | 将来VPN/専用線で接続したときに通信不能になる |
| **他のVPCとも重複させない** | VPCピアリング・Transit Gatewayで接続できなくなる |
| **`/16` で大きめに取る** | 縮小できないので、大きく取っておく方が安全 |
| **環境ごとに別ブロック** | 本番 10.100.0.0/16、検証 10.101.0.0/16 など |
| **クラウド事業者の予約IPを考慮** | 各サブネットの先頭数個と末尾は予約されている |

```
【推奨する全社IPアドレス設計（③章の続き）】
  10.10.0.0/16    本社
  10.20.0.0/16    大阪支社
  10.30.0.0/16    名古屋支社
  10.100.0.0/16   AWS 本番VPC       ← クラウド用に別ブロックを予約
  10.101.0.0/16   AWS 検証VPC
  10.110.0.0/16   Azure 本番VNet
```

> 💡 **AWSでは1サブネットあたり5個のIPが予約されています**（ネットワークアドレス、VPCルータ、DNS、将来用、ブロードキャスト）。`/28` を切ると使えるのは 11個 だけ。**サブネットは `/24` 以上で切る**のが実務上の安全策です。

### 1-3. パブリックサブネットとプライベートサブネットの違い

技術的な違いは1つだけです。

```
パブリックサブネット   : ルートテーブルに 0.0.0.0/0 → Internet Gateway がある
プライベートサブネット : それがない（代わりに 0.0.0.0/0 → NAT Gateway など）
```

「パブリック」という属性があるわけではなく、**ルーティングの結果としてそうなっている**だけです。ここを理解すると、トラブル時に「なぜインターネットに出られないのか」を正しく追えます。

### 1-4. AZ（アベイラビリティゾーン）とサブネットの関係

**1つのサブネットは1つのAZにしか属せません。** これがオンプレとの決定的な違いです。

```
【重要】可用性を確保するには、必ず複数AZにサブネットを作る

    VPC 10.0.0.0/16
      ├─ AZ-a: 10.0.1.0/24（パブリック）, 10.0.11.0/24（プライベート）
      └─ AZ-c: 10.0.2.0/24（パブリック）, 10.0.12.0/24（プライベート）
                          ↑
        ロードバランサとサーバーを両AZに配置して初めて、AZ障害に耐えられる
```

> ⚠️ **「マルチAZにしたつもりが、実はシングルAZだった」は非常に多い設計ミス**です。サーバーを2台にしても同じAZなら、AZ障害で両方落ちます。

## 2. インターネットとの出入り

### 2-1. 主要なゲートウェイ

| 機能 | 役割 | 課金の注意 |
| --- | --- | --- |
| **Internet Gateway（IGW）** | VPCとインターネットの接続点 | IGW自体は無料 |
| **NAT Gateway** | プライベートサブネットから**外向きのみ**通信 | **時間課金＋データ処理課金。高額になりやすい** |
| **VPCエンドポイント** | クラウドサービスへ**インターネットを経由せず**接続 | **NAT Gateway費用の削減に有効** |
| **Egress-Only IGW** | IPv6用の外向き専用 | 無料 |

### 2-2. NAT Gateway のコスト問題

これは**クラウド請求書で驚く原因の常連**です。

```
NAT Gateway の費用構造（AWS の例）
  ・時間課金        : 約 $0.062/時 × 24h × 30日 ≒ $45/月（1台あたり）
  ・データ処理課金  : 約 $0.062/GB
  
  マルチAZで2台 → $90/月
  ＋ 月1TB のデータ転送 → 約 $62
  ＝ 月 $150 前後（約2万円強）
```

**削減策**：

| 手法 | 効果 |
| --- | --- |
| **VPCエンドポイント（Gateway型）を使う** | **S3・DynamoDBへの通信は無料**。NAT経由をやめられる |
| VPCエンドポイント（Interface型） | 他のAWSサービスも直接接続。ただしこちらは有料 |
| コンテナイメージの取得元を見直す | ECRへの通信をエンドポイント化 |
| 検証環境はシングルAZのNATにする | 可用性を落として費用削減（本番では不可） |

> 💡 **クラウドのネットワーク設計は「性能」より「課金構造」の理解が重要**です。特に **データ転送（Egress）課金** は、設計次第で桁が変わります。

### 2-3. データ転送課金の基本原則

| 通信 | 課金（AWS の一般的な傾向） |
| --- | --- |
| インターネット → クラウド（In） | **無料** |
| **クラウド → インターネット（Out）** | **有料（最も高い）** |
| 同一AZ内・同一サブネット | 無料 |
| **AZ間** | **有料（往復とも）** |
| リージョン間 | 有料 |
| **専用線経由** | 有料だがインターネット経由より安い |

> ⚠️ **「マルチAZ構成にしたら通信費が跳ね上がった」**——AZ間通信は課金対象です。**DBのレプリケーションやマイクロサービス間通信が頻繁にAZをまたぐ設計**になっていないか確認してください。

## 3. クラウドのファイアウォール

### 3-1. セキュリティグループ と ネットワークACL

AWSを例にすると、2階層のフィルタがあります。**この違いは頻出の混乱ポイント**です。

| | **セキュリティグループ（SG）** | **ネットワークACL（NACL）** |
| --- | --- | --- |
| 適用先 | **インスタンス（ENI）単位** | **サブネット単位** |
| ステート | **ステートフル**（戻りは自動許可） | **ステートレス**（戻りも明示的に許可が必要） |
| ルール | **許可のみ**（拒否は書けない） | 許可と**拒否**が書ける |
| 評価順 | すべてのルールを評価 | **番号順**に評価し、最初に一致したものを適用 |
| 既定 | インバウンド全拒否／アウトバウンド全許可 | すべて許可 |

**実務での使い分け**：

```
セキュリティグループ  → メインの制御。ここで細かく作る
ネットワークACL      → 「特定IPを全面ブロック」など、粗い防御に限定
```

> ⚠️ **NACLはステートレス**なので、インバウンドを許可しただけでは戻りが通りません。**エフェメラルポート（1024-65535）のアウトバウンド許可**が必要です。ここを忘れて「なぜか通信できない」となるケースが非常に多いです。基本的には**NACLは既定のまま触らず、SGで制御する**のが安全です。

### 3-2. セキュリティグループの参照機能

クラウドならではの強力な機能です。**IPアドレスではなく、セキュリティグループそのものを送信元に指定できます。**

```
【従来のオンプレ的な書き方】
  DBサーバーのSG: 「10.0.11.0/24 からの 3306 を許可」
  → サブネット内の全サーバーが対象になってしまう

【クラウド的な書き方】
  DBサーバーのSG: 「sg-web（Webサーバーのセキュリティグループ）からの 3306 を許可」
  → Webサーバーが増減してもルール変更不要
  → 同じサブネットの他のサーバーからは接続できない
```

**これが実質的なマイクロセグメンテーション**（→ [⑥](06-security.md)）です。オンプレで実現するには専用製品が必要ですが、クラウドでは標準機能で実現できます。**必ず活用してください。**

## 4. ロードバランサ

### 4-1. 種類

| 種類 | レイヤ | 判断材料 | 用途 |
| --- | --- | --- | --- |
| **L4（NLB / Network LB）** | L4 | IP・ポート | **超高速・固定IP**・TCP/UDPそのまま流す |
| **L7（ALB / Application LB）** | L7 | **URLパス・ホスト名・ヘッダ** | Webアプリ・パスベースのルーティング |
| **グローバル（DNS/Anycast）** | — | 地理・リージョン | リージョン間の振り分け・DR |

### 4-2. L7ロードバランサでできること

```
  https://example.com/api/*      → APIサーバー群
  https://example.com/static/*   → 静的コンテンツ配信
  https://example.com/*          → Webサーバー群
  https://admin.example.com/*    → 管理画面（社内IPのみ許可）
  
  ＋ TLS終端（証明書をLBで一元管理）
  ＋ ヘルスチェック（異常なサーバーを自動的に切り離す）
  ＋ スティッキーセッション（同じユーザーを同じサーバーへ）
  ＋ WAF連携
```

### 4-3. ヘルスチェックの設計が重要

ロードバランサの価値は**「壊れたサーバーを自動的に外す」**ことです。だからこそ設計が重要になります。

| 設定 | 考え方 |
| --- | --- |
| **チェック先パス** | `/` ではなく **`/health` のような専用エンドポイント**を作る |
| チェック内容 | **DBへの接続確認まで含める**か（含めるとDB障害で全台落ちるリスクもある） |
| 間隔・閾値 | 短すぎると誤検知、長すぎると障害検知が遅れる（例：10秒間隔・2回連続失敗で切離） |
| 正常判定 | HTTP 200 のみ。**リダイレクトを正常扱いにしない** |

> ⚠️ **「ヘルスチェックが `/` を見ていて、トップページが重いせいで全台が異常判定される」**という事故があります。ヘルスチェック用の軽量エンドポイントを必ず用意してください。

## 5. CDN — 配信を速く・安くする

### 5-1. 仕組み

```
【CDNなし】
  日本のユーザー → 米国のサーバー （RTT 150ms、毎回オリジンまで往復）

【CDNあり】
  日本のユーザー → 東京のエッジ（キャッシュ）→ ヒットすれば即応答（RTT 10ms）
                                          ↓ ミス時のみ
                                       米国のオリジン
```

### 5-2. 効果

| 効果 | 内容 |
| --- | --- |
| **高速化** | 物理的に近い場所から配信。RTTが劇的に短縮 |
| **オリジンの負荷軽減** | キャッシュヒット分はオリジンに届かない |
| **転送コストの削減** | **CDNのデータ転送料金はクラウド直送より安いことが多い** |
| **DDoS耐性** | 巨大なCDN網が攻撃を吸収する |
| **WAF・Bot対策の統合** | エッジで防御できる |

### 5-3. キャッシュ設計の要点

| 論点 | 指針 |
| --- | --- |
| **キャッシュ対象** | 静的ファイル（画像・CSS・JS）は長期キャッシュ |
| **キャッシュキー** | クエリパラメータ・Cookie・言語ヘッダをキーに含めるか慎重に判断 |
| **パージ（無効化）** | デプロイ時にどう無効化するか。**ファイル名にハッシュを付ける方式**が確実 |
| **動的コンテンツ** | 原則キャッシュしない。**個人情報を含むページを誤ってキャッシュする事故に注意** |

> ⚠️ **CDN最大の事故は「ログイン後のページをキャッシュして、他人に見せてしまう」**ことです。Cookie の有無でキャッシュを分ける、あるいは認証が必要なパスは明示的にキャッシュ無効にしてください。

## 6. オンプレとクラウドをつなぐ

### 6-1. 接続方式の比較

| 方式 | 帯域 | 遅延 | 品質 | コスト | 開通期間 |
| --- | --- | --- | --- | --- | --- |
| **インターネットVPN** | 回線次第 | 変動 | 保証なし | **安い**（月数万円） | **即日〜数日** |
| **専用線**（Direct Connect / ExpressRoute） | 50Mbps〜100Gbps | **安定** | **SLAあり** | 高い（月10万円〜） | **1〜2ヶ月** |
| **接続事業者（パートナー）経由** | 10Mbps〜 | 安定 | SLAあり | 中（月数万円〜） | **数日〜2週間** |

> 💡 **中小規模では「接続事業者経由の専用線」が現実解**になることが多いです。自前で専用線を引くには最低帯域や設備要件のハードルがありますが、パートナー経由なら小さい帯域から始められ、開通も早いです。

### 6-2. 専用線でもBGPが必要

専用線接続は **BGPで経路を交換**します（→ [④](04-routing.md)）。

```
オンプレのルータ ←── BGPセッション ──→ クラウド側のルータ
  「10.10.0.0/16 はこちらです」
                    「10.100.0.0/16 はこちらです」
```

**設計時の注意**：
- **プライベートAS番号**（64512〜65534）を使うのが一般的
- **経路のフィルタリングを必ず入れる**（オンプレの全経路をクラウドに流さない）
- **冗長化する場合は2本の専用線＋2セッション**。片系のみだと専用線障害で全断

### 6-3. 専用線を冗長化する構成

```
       ┌─ 専用線A（キャリアA・拠点1） ─┐
オンプレ ┤                              ├─ クラウド
       └─ 専用線B（キャリアB・拠点2） ─┘
              ＋ バックアップとしてインターネットVPN

・BGPのLocal Preference で通常はAを優先
・A障害時はBへ自動切替
・両方落ちたらVPNへフォールバック（AD値/優先度で制御）
```

## 7. マルチVPC・マルチクラウドの接続

### 7-1. VPC間の接続方式

| 方式 | 特徴 | 適する規模 |
| --- | --- | --- |
| **VPCピアリング** | 1対1接続。シンプル・安価 | **VPCが数個まで** |
| **Transit Gateway / 仮想WAN** | **ハブ&スポーク**。中央集約 | **VPCが多数・拠点も接続** |
| PrivateLink / Private Endpoint | **サービス単位**で公開。VPC全体を繋がない | 特定サービスのみ共有したい |

> ⚠️ **VPCピアリングは推移的ルーティングができません**。A-B、B-C を繋いでも、A-C は通信できません。VPCが増えると接続数が `n(n-1)/2` で爆発するため、**4〜5個を超えたらTransit Gatewayへ**移行するのが定石です。

### 7-2. マルチクラウド接続

```
  オンプレ ─┬─ 専用線 ─→ AWS
            └─ 専用線 ─→ Azure
            
  または
  
  オンプレ ─→ 相互接続点（IX/接続事業者のクラウドエクスチェンジ）
                 ├─→ AWS
                 ├─→ Azure
                 └─→ Google Cloud
```

**接続事業者のクラウドエクスチェンジを使うと、1本の回線から複数クラウドへ論理的に接続**でき、コストと管理を抑えられます。

## 8. コンテナ・Kubernetesのネットワーク

### 8-1. 押さえるべき3つの概念

| 概念 | 役割 |
| --- | --- |
| **Pod ネットワーク（CNI）** | Pod同士が通信するための内部ネットワーク。Calico・Cilium など |
| **Service** | Podは増減してIPが変わるため、**安定した仮想IP**を提供 |
| **Ingress / Gateway API** | 外部からのHTTP(S)を受けて、内部のServiceへ振り分ける（L7ロードバランサ相当） |

### 8-2. Serviceの種類

| 種類 | 用途 |
| --- | --- |
| ClusterIP | **クラスタ内部のみ**（既定） |
| NodePort | ノードのポートを開けて外部公開（開発向け） |
| LoadBalancer | **クラウドのLBを自動作成**して公開 |
| ExternalName | 外部DNS名へのエイリアス |

### 8-3. ネットワーク設計での注意

> ⚠️ **Kubernetesは大量のIPアドレスを消費します。** Pod 1つに1 IPを割り当てる方式（AWS VPC CNI など）では、**ノード数 × Pod数 分のIPが必要**です。`/24` のサブネットではすぐ枯渇します。**クラスタ用のサブネットは `/20` 以上**で確保してください。

**NetworkPolicy** を使うと、Pod間の通信をL3/L4で制御できます（マイクロセグメンテーションのK8s版）。**既定では全Pod間が通信可能**なので、本番環境では必ず設定してください。

## 9. クラウドネットワークのトラブルシューティング

| 症状 | 確認する順序 |
| --- | --- |
| **インスタンスからインターネットに出られない** | ①ルートテーブル（0.0.0.0/0 の宛先）→ ②NAT Gateway/IGW の存在 → ③SGのアウトバウンド → ④NACL |
| **外部からインスタンスに繋がらない** | ①SGのインバウンド → ②NACL → ③パブリックIPの有無 → ④ルートテーブル → ⑤OS内のファイアウォール |
| **VPC間で通信できない** | ①ピアリング/TGWの状態 → ②**両側**のルートテーブル → ③SG → ④CIDR重複 |
| **オンプレから繋がらない** | ①BGPセッションの状態 → ②広告されている経路 → ③**オンプレ側の戻り経路** → ④SG |
| **DNSが解決できない** | ①VPCのDNS設定（enableDnsSupport / enableDnsHostnames）→ ②Resolver設定 → ③プライベートホストゾーンの関連付け |
| **急に通信費が増えた** | ①NAT Gateway のデータ処理量 → ②AZ間通信 → ③インターネットへのEgress |

**クラウド特有の便利な機能**：
- **フローログ**（VPC Flow Logs）：どの通信が許可/拒否されたかを記録。**「なぜ通らないか」の特定に最強**
- **到達性アナライザ**（Reachability Analyzer 等）：設定上、通信が到達可能かを静的に解析してくれる

## 10. よくある疑問（FAQ）

**Q. VPCのCIDRは大きくして損はない？**
A. ありません。プライベートIPは無料で、大きく取っても課金されません。**`/16` で取っておくのが安全**です。ただしオンプレや他VPCとの重複だけは絶対に避けてください。

**Q. パブリックサブネットにDBを置いてはいけない？**
A. 置くべきではありません。DBはプライベートサブネットに配置し、必要なら踏み台（bastion）または**セッションマネージャ系のサービス**経由で接続します。近年は踏み台サーバー自体を廃してエージェント経由の接続にする方が安全です。

**Q. セキュリティグループとNACL、両方設定すべき？**
A. **基本はセキュリティグループだけで設計**し、NACLは既定のまま触らないのが安全です。NACLはステートレスで事故が起きやすいため、「特定IPを全面拒否したい」といった明確な目的があるときだけ使ってください。

**Q. クラウドにすればネットワークの知識は不要になる？**
A. **逆です。** クラウドは「ネットワークを自分で設計する」ことを前提にしています。オンプレでは機器のデフォルト設定に助けられていた部分も、クラウドでは明示的に設計する必要があります。本シリーズの ①〜⑤ の知識がそのまま必要です。

**Q. マルチクラウドにすべき？**
A. 可用性のためのマルチクラウドは、**運用の複雑さに見合わないことが多い**です。単一クラウド内のマルチAZ/マルチリージョンで十分な可用性が得られます。マルチクラウドを選ぶのは、**各クラウドの得意なサービスを使い分けたい**場合や、**調達方針上の要件**がある場合です。

## まとめ

- クラウドのネットワークは**オンプレ概念の名前替え**。対応表を押さえれば設計できる
- **VPCのCIDRは後から縮小できない**。オンプレ・他VPCと重複させず、`/16` で大きく取る
- **1サブネット = 1AZ**。可用性には複数AZへの配置が必須
- パブリック/プライベートの違いは**ルートテーブルだけ**
- **セキュリティグループはステートフル、NACLはステートレス**。基本はSGで設計する
- **SGを送信元に指定する参照機能**が、実質的なマイクロセグメンテーションになる
- **NAT Gateway とデータ転送（Egress・AZ間）が請求書の主犯**。VPCエンドポイントで削減
- ヘルスチェックは**専用の軽量エンドポイント**を用意する
- CDNの事故で最悪なのは**認証後ページのキャッシュ**
- 専用線は**BGP必須**、開通に1〜2ヶ月。急ぐなら接続事業者経由
- **VPCピアリングは推移不可**。5個を超えたらTransit Gateway
- **Kubernetesはとにかく IP を食う**。サブネットは `/20` 以上
- 通信できないときは **VPCフローログ**が最短の答え
