# ④ ルーティング

> **この章のゴール**：ルータが「どの経路を選ぶか」の判断ロジックを理解し、経路表（ルーティングテーブル）を読めるようになる。そして、規模に応じてスタティック／OSPF／BGPのどれを使うべきか判断できるようになる。

← [③ IPアドレスとサブネット](03-ip-subnet.md) ／ 次章 → [⑤ トランスポート層とアプリケーション層](05-transport-application.md)

---

## 0. まず全体像（30秒）

ルーティングとは **「宛先IPアドレスを見て、次にどこへ渡すかを決めること」** です。

ルータは巨大な「道案内表」を持っていて、パケットが来るたびにこう判断します。

```
1. 宛先IPを見る                          例: 10.20.30.40
2. 経路表の中から、最も詳しく一致する行を探す  ← ロンゲストマッチ
3. その行に書かれた「次の渡し先」へ転送する    ← ネクストホップ
4. 該当がなければデフォルトルート（0.0.0.0/0）へ
5. デフォルトもなければ破棄（+ ICMP到達不能を返す）
```

**この5行がルーティングのすべてです。** 以降はこれを支える仕組みの話になります。

## 1. 経路表（ルーティングテーブル）を読む

### 1-1. 実際の経路表

```
$ ip route          （Linux）

default via 192.168.1.1 dev eth0                   ← デフォルトルート
10.10.0.0/16 via 192.168.1.254 dev eth0            ← 静的経路
192.168.1.0/24 dev eth0 proto kernel scope link    ← 直接接続
```

```
Router# show ip route          （Cisco）

Codes: C - connected, S - static, O - OSPF, B - BGP

C    192.168.1.0/24 is directly connected, GigabitEthernet0/0
S    10.10.0.0/16 [1/0] via 192.168.1.254
O    10.20.0.0/16 [110/20] via 192.168.1.253
S*   0.0.0.0/0 [1/0] via 192.168.1.1
                └┬┘ └┬┘
          アドミニストレイティブディスタンス / メトリック
```

| 列 | 意味 |
| --- | --- |
| **コード（C/S/O/B）** | どうやってこの経路を知ったか |
| **宛先ネットワーク** | どこ宛てのパケットか |
| **[110/20]** | [AD値 / メトリック] — 経路の「信頼度」と「距離」 |
| **via / ネクストホップ** | 次に渡す相手のIP |
| **インタフェース** | どのポートから出すか |

### 1-2. ロンゲストマッチ — 最も詳しい経路が勝つ

複数の経路が該当する場合、**プレフィックス長が最も長い（＝詳しい）ものが選ばれます**。

```
経路表:
  10.0.0.0/8      via A
  10.20.0.0/16    via B
  10.20.30.0/24   via C
  0.0.0.0/0       via D

宛先 10.20.30.40 のパケットは？
  → /8, /16, /24 すべてに該当するが、最も長い /24 が勝つ → C へ

宛先 10.20.99.5 のパケットは？
  → /8 と /16 に該当。長い /16 が勝つ → B へ

宛先 8.8.8.8 のパケットは？
  → どれにも該当しない → デフォルトルート D へ
```

> 💡 **これが「特定の通信だけ別経路に流す」設計の基礎**です。デフォルトはインターネット向け、`10.20.0.0/16` だけ拠点間VPN経由、といった制御ができます。

### 1-3. アドミニストレイティブディスタンス（AD）— どのプロトコルを信じるか

**同じ宛先を、複数のプロトコルが違う経路で教えてきた場合**、AD値が小さい方を採用します。「情報源の信頼度」です。

| 経路の種類 | AD値（Cisco） |
| --- | --- |
| 直接接続（Connected） | **0** |
| スタティック | 1 |
| eBGP | 20 |
| OSPF | 110 |
| RIP | 120 |
| iBGP | 200 |
| 到達不能 | 255 |

**メトリックとの違い**：
- **AD** = 「どのプロトコルを信じるか」（プロトコル間の比較）
- **メトリック** = 「同じプロトコル内で、どの経路が近いか」（経路間の比較）

### 1-4. 選択の優先順位（まとめ）

```
1. ロンゲストマッチ（プレフィックスが長い方）      ← 最優先
2. AD値が小さい方（信頼できるプロトコル）
3. メトリックが小さい方（近い経路）
4. 同じなら等コストマルチパス（ECMP）で負荷分散
```

## 2. スタティックルーティング — 手動で書く

### 2-1. 設定と特徴

```
Cisco:  ip route 10.20.0.0 255.255.0.0 192.168.1.254
Linux:  ip route add 10.20.0.0/16 via 192.168.1.254
```

| メリット | デメリット |
| --- | --- |
| 設定が単純・予測可能 | **経路が増えると管理不能** |
| CPU/メモリを消費しない | **障害時に自動で迂回しない** |
| 意図した経路を強制できる | 構成変更のたびに全機器を手作業で修正 |
| セキュア（経路情報を交換しない） | ヒューマンエラーが起きやすい |

### 2-2. いつ使うか

| 使うべき場面 | 理由 |
| --- | --- |
| **小規模（拠点数 〜3、ルータ 〜5台）** | 動的にするほどの規模がない |
| **スタブネットワーク**（出口が1つしかない） | 選択の余地がないので動的にする意味がない |
| **デフォルトルート** | どんな規模でも「最後の砦」として必要 |
| バックアップ経路（フローティングスタティック） | AD値を大きくして、主経路が落ちた時だけ有効化 |

#### フローティングスタティック（覚えておくと便利）

```
ip route 10.20.0.0 255.255.0.0 192.168.1.254        ← 主経路（AD=1）
ip route 10.20.0.0 255.255.0.0 192.168.2.254 200    ← 予備（AD=200）

通常は主経路を使い、主経路がダウンしたら自動的に予備に切り替わる
```

**小規模〜中規模のWAN冗長化で非常によく使う手法**です。動的ルーティングを導入せずに冗長化できます。

## 3. 動的ルーティング — 自動で learn する

### 3-1. 分類

| 分類 | 動作原理 | 代表プロトコル |
| --- | --- | --- |
| **ディスタンスベクタ型** | 「隣に聞いた距離」を伝播 | RIP、EIGRP※ |
| **リンクステート型** | **全体の地図**を各ルータが持ち、自分で最短経路を計算 | **OSPF**、IS-IS |
| **パスベクタ型** | 経由するAS（組織）の並びで判断 | **BGP** |

※ EIGRPは厳密には「拡張ディスタンスベクタ（ハイブリッド）」。

### 3-2. IGP と EGP

| 種別 | 意味 | 使う場所 | 代表 |
| --- | --- | --- | --- |
| **IGP**（内部） | 同じ組織（AS）の中 | 社内・データセンタ内 | **OSPF**、IS-IS、EIGRP、RIP |
| **EGP**（外部） | 組織と組織の間 | ISP間、インターネット | **BGP** 一択 |

## 4. OSPF — 企業内で最もよく使われる

### 4-1. 特徴

**Open Shortest Path First**。リンクステート型で、**各ルータがネットワーク全体の地図（LSDB）を持ち、ダイクストラ法で最短経路を計算**します。

| 項目 | 内容 |
| --- | --- |
| 標準規格 | ✅ オープン（ベンダー非依存） |
| 収束速度 | 速い（数秒） |
| メトリック | **コスト**＝帯域幅から算出（既定：10⁸ ÷ 帯域bps） |
| スケール | 数百ルータ規模まで（エリア分割で拡張） |
| 対応IPバージョン | OSPFv2（IPv4）／OSPFv3（IPv6） |

### 4-2. エリアという考え方

全ルータが全体の地図を持つと、規模が大きくなるほど負荷が上がります。そこで**エリアに分割**します。

```
        ┌─────────── Area 0（バックボーン）───────────┐
        │        すべてのエリアはArea 0に接続する      │
        └──┬──────────────┬──────────────┬─────────┘
           │              │              │
       [ABR]           [ABR]          [ABR]     ← エリア境界ルータ
           │              │              │
        Area 1         Area 2         Area 3
        （本社）        （大阪）        （名古屋）
```

**ルール**：すべてのエリアは **Area 0（バックボーンエリア）に隣接**していなければなりません。これが守れない場合は仮想リンク（Virtual Link）を使いますが、設計として避けるべきです。

**エリア分割の効果**：エリア内の詳細な経路情報が外に漏れず、境界で集約される → 経路表が小さくなり、障害の影響が局所化されます。

### 4-3. コスト計算の落とし穴

```
既定の計算式: コスト = 100,000,000 ÷ 帯域幅(bps)

  10Mbps  → コスト 10
  100Mbps → コスト 1
  1Gbps   → コスト 1  ← ！
  10Gbps  → コスト 1  ← ！！
```

> ⚠️ **既定のままだと、100Mbps・1Gbps・10Gbps がすべて「コスト1」で同じ扱い**になります。高速リンクがあるのに遅い経路が選ばれる原因になるので、**`auto-cost reference-bandwidth` を実際の最高速度に合わせて変更**してください（例：10Gなら `10000`）。**全ルータで同じ値にすること**が必須です。

### 4-4. 隣接関係（Neighbor）が確立しない原因

OSPFのトラブルの9割はここです。以下が**すべて一致**していないと隣接関係になりません。

| チェック項目 | 備考 |
| --- | --- |
| **エリアID** | 最頻出の設定ミス |
| **サブネットマスク** | 同一セグメントで一致必須 |
| **Hello / Dead インターバル** | 既定は10秒/40秒 |
| **認証設定** | 有効/無効とパスワード |
| **MTU** | **不一致だとExStartで止まる**（有名なハマりどころ） |
| Stubフラグ | エリアタイプの一致 |

```
確認: show ip ospf neighbor
  → 状態が FULL または 2WAY になっていればOK
  → ExStart / Exchange で止まっていたら MTU 不一致を疑う
```

## 5. BGP — インターネットを支えるプロトコル

### 5-1. 何をしているのか

**Border Gateway Protocol**。組織（AS）同士が「うちを経由すればこのネットワークに行けます」と経路を広告し合うプロトコルです。**インターネット全体が BGP で繋がっています**。

```
AS 65001 (自社)  ──  AS 2914 (ISP-A)  ──  AS 3356  ──  AS 15169 (Google)
                 ╲
                  ──  AS 4713 (ISP-B)  ──  ...

AS番号 = 組織に割り当てられる識別番号（16bit/32bit）
```

### 5-2. eBGP と iBGP

| 種別 | 対向 | AD値 | 特徴 |
| --- | --- | --- | --- |
| **eBGP** | 別のAS | 20 | ISP接続。TTL=1が既定 |
| **iBGP** | 同じAS内 | 200 | AS内で経路を配る。**フルメッシュ or ルートリフレクタ**が必要 |

### 5-3. 経路選択の優先順位（実務で使う上位）

BGPは「速い経路」ではなく「**ポリシーに沿った経路**」を選びます。

```
1. Weight        大きい方（Cisco独自・そのルータ内でのみ有効）
2. Local Pref    大きい方（AS内で共有。★出ていく経路の制御に使う）
3. 自分で生成した経路
4. AS Path       短い方（★最もよく使われる指標）
5. Origin        IGP < EGP < Incomplete
6. MED           小さい方（★入ってくる経路の制御に使う。隣接ASへの要望）
7. eBGP > iBGP
8. IGPメトリック  小さい方
```

**実務での使い分け**：
- **出ていくトラフィックを制御したい** → **Local Preference**（自分で決められる、確実）
- **入ってくるトラフィックを制御したい** → **AS Path プリペンド**または **MED**（相手次第、確実ではない）

### 5-4. 企業がBGPを使う場面

| 場面 | 説明 |
| --- | --- |
| **マルチホーム** | 複数のISPと契約し、片方が落ちても継続。**自社AS番号とIPアドレス（PI）が必要** |
| **クラウド専用線** | AWS Direct Connect・Azure ExpressRoute は **BGP必須** |
| **大規模データセンタ** | Spine-Leaf構成でBGPをIGP代わりに使う（BGP in the Data Center） |
| SD-WAN | オーバーレイの経路制御に内部利用 |

> 💡 **中小企業が最初にBGPに触れるのは、ほぼ「クラウド専用線を引くとき」**です。AWS/Azure と接続するには BGP セッションを張る必要があり、ここで初めてAS番号（プライベートASでも可）を意識することになります。

## 6. ルーティングプロトコルの選び方

| 規模・状況 | 推奨 | 理由 |
| --- | --- | --- |
| 拠点1〜3、ルータ数台 | **スタティック＋フローティングスタティック** | 動的にする管理コストの方が高い |
| 拠点3〜20、社内が複雑 | **OSPF（シングルエリア）** | 自動迂回。設定も難しくない |
| 拠点20以上・大規模社内 | **OSPF（マルチエリア）** or IS-IS | エリア分割で負荷と影響範囲を局所化 |
| ISPマルチホーム | **BGP** | 他に選択肢がない |
| クラウド専用線 | **BGP** | サービス側の要件 |
| データセンタファブリック | **BGP（eBGP）** or OSPF | Spine-Leafでは BGP が主流に |

> **迷ったら**：拠点数が片手で数えられて、経路が固定的なら**スタティック**。それを超えるか、冗長経路の自動切り替えが要るなら **OSPF**。外の世界と対等に話す必要があるなら **BGP**。

## 7. VRF — 1台のルータを複数に分ける

**VRF（Virtual Routing and Forwarding）** は、1台のルータ/L3スイッチの中に**独立した経路表を複数持たせる**技術です。L2におけるVLANの、L3版と考えてください。

```
   ┌──────── 物理ルータ 1台 ────────┐
   │  VRF: CORP   （社内業務系）      │  経路表A  ← 互いに完全分離
   │  VRF: GUEST  （ゲストWi-Fi）     │  経路表B
   │  VRF: OT     （工場・制御系）    │  経路表C
   └────────────────────────────────┘
```

| 用途 | 説明 |
| --- | --- |
| **マルチテナント** | データセンタで顧客ごとに分離 |
| **セキュリティ境界** | 業務系と制御系（OT）を物理的に分けずに完全分離 |
| **IPアドレス重複の共存** | M&A後に同じ `192.168.1.0/24` を使う組織を統合するとき |
| **キャリアのVPNサービス** | 広域イーサ・IP-VPN の裏側は MPLS+VRF |

> 💡 **M&Aや事業統合でIPが被った**——という状況で、VRFは実質的な救済策になります。片方をVRFに閉じ込め、NATで変換して連携させます。

## 8. ポリシーベースルーティング（PBR）

通常のルーティングは**宛先IPだけ**で判断しますが、PBRを使うと**送信元IP・プロトコル・ポート番号**でも経路を変えられます。

```
例: 
  ・営業部（10.10.10.0/24）のインターネット通信 → ISP-A 経由
  ・開発部（10.10.20.0/24）のインターネット通信 → ISP-B 経由
  ・全社の 10.20.0.0/16 宛て               → VPN 経由
```

**使う場面**：回線の使い分け、特定サービスだけプロキシ迂回、コスト最適化。
**注意**：通常の経路表より優先されるため、**トラブル時に「なぜこの経路を通るのか分からない」の原因になりがち**。設定したら必ずドキュメント化してください。

## 9. 経路の冗長化（VRRP / HSRP）

端末のデフォルトゲートウェイが1台のルータだと、そのルータが落ちると全滅します。そこで**2台で1つの仮想IPを共有**します。

```
         端末のデフォルトGW = 10.10.10.1（仮想IP）
                    │
        ┌───────────┴───────────┐
   ルータA（実IP .252）      ルータB（実IP .253）
   優先度110 → Master        優先度100 → Backup
   
   Masterが落ちるとBackupが仮想IPを引き継ぎ、GARPで周知（数秒で切替）
```

| プロトコル | 標準/独自 | 備考 |
| --- | --- | --- |
| **VRRP** | 標準（RFC） | **ベンダー混在環境ではこれ** |
| HSRP | Cisco独自 | Cisco環境で一般的 |
| GLBP | Cisco独自 | 負荷分散も行う |

> ⚠️ **よくある設計ミス**：VRRPで機器は冗長化したのに、**上流のスイッチへのケーブルが1本しかない**。あるいは**両方のルータが同じ電源系統から給電されている**。冗長化は「機器」ではなく「経路と電源を含めた全体」で考えてください（→ [⑪ 冗長化とBCP](11-operations.md)）。

## 10. トラブルシューティング（L3）

| 症状 | 疑う原因 | 確認 |
| --- | --- | --- |
| 特定の宛先だけ届かない | 経路が無い／間違っている | `show ip route <宛先>` で該当行を確認 |
| 通信が片方向だけ成立 | **戻りの経路が無い** | **両側**の経路表を確認 |
| 経路がバタバタ変わる | フラッピング（リンク不安定） | インタフェースのup/downログ |
| pingは通るがアプリが動かない | L4以上の問題（FW・ポート） | [⑤](05-transport-application.md)・[⑥](06-security.md)へ |
| traceroute が途中で `* * *` | ICMP応答を返さない機器がある | 異常とは限らない。最終到達を確認 |
| ルーティングループ | 経路の相互参照 | TTL exceeded が多発。経路表を突き合わせ |

### 「片方向だけ通信できる」は最頻出

```
A拠点 → B拠点 のping：通る
B拠点 → A拠点 のping：通らない

原因：B側のルータに「A拠点宛て」の経路が無い
    （行きは通るが、帰りのパケットが迷子になっている）

教訓：ルーティングは必ず「往復」で設計・確認する
```

## 11. よくある疑問（FAQ）

**Q. デフォルトゲートウェイとデフォルトルートは同じ？**
A. ほぼ同じ意味です。端末視点で「外に出るときの出口」を指すのがデフォルトゲートウェイ、ルータの経路表上の `0.0.0.0/0` の行がデフォルトルートです。

**Q. L3スイッチとルータ、どちらを使うべき？**
A. **社内のVLAN間ルーティングはL3スイッチ**（ハードウェア処理で高速・安価・ポート数が多い）、**WAN・インターネットとの境界はルータ／UTM**（NAT・VPN・詳細なフィルタ・PPPoEなどWAN側の機能が必要）。役割分担が定石です。

**Q. ECMP（等コストマルチパス）で帯域は2倍になる？**
A. 合計としては増えますが、[② のLAG](02-physical-datalink.md) と同じく**1フローは1経路に固定**されます。単一の大容量転送は速くなりません。

**Q. OSPFとBGPを同時に使うことはある？**
A. あります。**社内はOSPF、インターネット/クラウド接続はBGP**という構成は中〜大規模で一般的です。両者の間で経路を再配布（redistribute）する際は、**ループを作らないようフィルタを必ず入れて**ください。

## まとめ

- ルーティングの判断は **ロンゲストマッチ → AD値 → メトリック** の順
- **AD = プロトコルの信頼度**、**メトリック = 経路の近さ**
- 小規模は**スタティック**、冗長化は**フローティングスタティック**で足りることが多い
- 中規模以上の社内は **OSPF**。エリア分割で負荷と影響範囲を局所化
- **OSPFの参照帯域は必ず変更する**（既定だと1G以上が全部コスト1）
- 隣接が張れないときは **エリアID・マスク・タイマー・MTU** を確認
- ISPマルチホームとクラウド専用線は **BGP必須**
- **VRFは「L3版のVLAN」**。IP重複の救済にも使える
- 冗長化は **VRRP/HSRP**。ただし経路と電源も含めて冗長にすること
- **ルーティングは必ず往復で設計する**
