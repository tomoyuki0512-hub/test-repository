# ⑥ ネットワークセキュリティ

> **この章のゴール**：ファイアウォールの種類と限界を理解し、VPNの方式を選べるようになる。そして「境界防御」から「ゼロトラスト」へという時代の転換を、製品名ではなく思想として掴む。

← [⑤ トランスポート層とアプリケーション層](05-transport-application.md) ／ 次章 → [⑦ 無線LANとWAN](07-wireless-wan.md)

---

## 0. まず全体像（30秒）

ネットワークセキュリティの歴史は、**「守る場所」がどこかの変遷**として理解できます。

```
【〜2015年ごろ】境界防御モデル
   社内 = 安全  |  外 = 危険
   出入口（ゲートウェイ）にファイアウォールを置けば守れる
        ↓
   前提が崩れた理由：
     ・クラウド利用 → 守るべきデータが社内にない
     ・リモートワーク → 守るべき人が社内にいない
     ・内部犯行・端末の持ち込み → 社内も安全ではない
        ↓
【現在】ゼロトラストモデル
   「社内だから信頼する」をやめる
   すべてのアクセスを、その都度「誰が・どの端末で・何に」で検証する
```

**重要な認識**：ゼロトラストは製品名ではなく**設計思想**です。「ゼロトラスト製品を買えば実現する」というものではありません。

## 1. ファイアウォール — 種類と限界

### 1-1. 世代の違い

| 世代 | 判断材料 | できること／できないこと |
| --- | --- | --- |
| **パケットフィルタ型** | IP・ポート・プロトコル | 単純。**戻りの通信も明示的に許可が必要** |
| **ステートフルインスペクション型** | ＋通信の状態（セッション） | **現在の基本**。行きを許可すれば戻りは自動 |
| **UTM** | ＋アンチウイルス・IPS・URLフィルタ等を1台に統合 | **中小企業の定番**。安価だが性能はほどほど |
| **NGFW（次世代FW）** | ＋**アプリケーション識別**・ユーザー識別・SSL復号 | 「ポート443の中身がFacebookかSalesforceか」を見分ける |
| **WAF** | HTTPの中身（L7） | **Webアプリ専用**。SQLi・XSSを防ぐ。FWの代わりにはならない |

### 1-2. ステートフルであることの意味

```
【ステートレス（パケットフィルタ）】
  内→外 の許可ルール：src 10.0.0.0/8 → dst any:443 permit
  外→内 の許可ルール：src any:443 → dst 10.0.0.0/8 permit  ← これも必要！
  → 外から443番を送りつけられると通ってしまう（危険）

【ステートフル】
  内→外 の許可ルール：src 10.0.0.0/8 → dst any:443 permit
  → 戻りは「自分が出した通信の応答」だと分かるので自動的に許可
  → 身に覚えのない外→内は通らない（安全）
```

**現代のファイアウォールは基本的にステートフル**です。ただし、**クラウドのネットワークACL（AWSのNACLなど）はステートレス**なので、設計時に混同しないよう注意してください（→ [⑧](08-cloud-network.md)）。

### 1-3. NGFWのアプリケーション識別

現代の通信はほぼすべてが **TCP/UDP 443番** に集約されています。ポート番号による制御は、もはや意味をなしません。

```
すべて 443番ポート:
  ・Microsoft 365（許可したい）
  ・Salesforce（許可したい）
  ・個人のGoogle Drive（禁止したい）
  ・ファイル共有サイト（禁止したい）
  ・匿名プロキシ（絶対禁止）

→ ポート番号では区別不可能
→ NGFWのアプリケーション識別が必要
```

さらに現代的な要件として、**「同じMicrosoft 365でも、会社のテナントは許可・個人アカウントは禁止」**（テナント制限）といった制御も求められます。

### 1-4. ファイアウォールで防げないもの

| 防げない | 理由 | 対策 |
| --- | --- | --- |
| **正規の通信に紛れた攻撃** | 443番の正常な通信に見える | NGFW＋EDR＋ログ分析 |
| **フィッシングでの認証情報窃取** | ユーザー自身が入力してしまう | **MFA**・教育・パスキー |
| **内部からの持ち出し** | 内→外は許可されている | DLP・CASB |
| **持ち込み端末・USB** | ネットワークを経由しない | 資産管理・端末制御 |
| **暗号化された悪意ある通信** | 中身が見えない | SSL復号（ただし副作用あり） |

> 💡 **「ファイアウォールを入れたから安全」は最も危険な誤解**です。ファイアウォールは「入口の門番」であって、家の中の警備員ではありません。

## 2. ネットワークの区分け（セグメンテーション）

### 2-1. DMZ — 公開サーバーを隔離する

外部に公開するサーバーは、**社内LANとは別の区画**に置きます。

```
    インターネット
         │
    ┌────┴────┐
    │  FW     │
    └─┬────┬──┘
      │    │
   ┌──┴─┐  └────┐
   │DMZ │       │
   │Web │    社内LAN
   │Mail│    （サーバー・クライアント）
   └────┘
   
【許可する通信】
  インターネット → DMZ:443    ✅
  DMZ → 社内DB:3306          ✅（必要最小限のポートのみ）
  インターネット → 社内LAN     ❌ 遮断
  DMZ → 社内LAN（上記以外）    ❌ 遮断  ← ここが最重要
```

**DMZの本質は「公開サーバーが乗っ取られても、社内に波及させない」こと**です。DMZから社内への通信を絞っていなければ、DMZを作る意味がありません。

### 2-2. マイクロセグメンテーション

従来のVLAN単位の分離をさらに細かくし、**サーバー個体・ワークロード単位**で通信を制御します。

```
従来: 「サーバーVLAN内は自由に通信できる」
      → 1台侵入されると、同じVLANの全サーバーに横展開（ラテラルムーブメント）される

マイクロセグメンテーション:
      → Webサーバー → DBサーバーの3306 のみ許可
      → Webサーバー同士の通信は禁止
      → 1台侵入されても広がらない
```

**ランサムウェア対策として最も効果的な施策の一つ**です。実装手段はクラウドのセキュリティグループ、ホスト型ファイアウォール、専用製品（Illumio等）など。

### 2-3. 分けるべき区画（チェックリスト）

| 区画 | 分離する理由 |
| --- | --- |
| **ゲストWi-Fi** | 素性の分からない端末。**インターネットのみ許可** |
| **サーバー** | クライアントからの不要なアクセスを遮断 |
| **IoT・監視カメラ・複合機** | **脆弱でパッチが当たらない機器の巣窟**。インターネットから隔離 |
| **OT・制御系（工場）** | **止まると事故になる**。IT系から完全分離 |
| **機器管理（スイッチ・APの管理IP）** | 管理端末からのみ到達可能に |
| **開発・検証環境** | 本番への誤操作を防ぐ |
| **業務委託・派遣** | 必要な範囲だけに限定 |

> ⚠️ **複合機（コピー機）は見落とされがちな侵入口**です。古いファームウェア、初期パスワード、スキャンデータの保管——**インターネットから到達可能な状態で放置**されている例が実際にあります。必ずセグメントを分けてください。

## 3. VPN — 拠点と人をつなぐ

### 3-1. 方式の分類

| 方式 | 用途 | 特徴 |
| --- | --- | --- |
| **IPsec サイト間VPN** | **拠点 ⇔ 拠点** | 常時接続。インターネット経由で安価に拠点間を結ぶ |
| **IPsec リモートアクセスVPN** | 人 ⇔ 社内 | 専用クライアントが必要 |
| **SSL-VPN** | 人 ⇔ 社内 | **ブラウザだけで使える**方式もある。導入が容易 |
| **L2TP/IPsec** | 人 ⇔ 社内 | OS標準機能で接続可。設定が容易だが機能は限定的 |
| **WireGuard** | 両方 | **軽量・高速・設定がシンプル**。近年急速に普及 |
| 広域イーサ / IP-VPN | 拠点 ⇔ 拠点 | **キャリアの閉域網**。VPNというよりWAN回線（→ [⑦](07-wireless-wan.md)） |

### 3-2. IPsecの構成要素（最低限）

```
【フェーズ1（IKE）】お互いの身元確認と、安全な通信路の確立
   認証方式: 事前共有鍵（PSK）or 証明書
   暗号化  : AES-256
   ハッシュ : SHA-256
   DHグループ: 14以上

【フェーズ2（IPsec SA）】実際のデータを流すトンネル
   暗号化  : AES-256-GCM
   対象通信 : 10.10.0.0/16 ⇔ 10.20.0.0/16
```

> ⚠️ **サイト間VPNが繋がらないときの定番原因**：
> 1. **フェーズ1/2 のパラメータが両端で不一致**（1つでも違うと張れない）
> 2. **NAT配下にある**（→ **NAT-T / UDP 4500** を有効化）
> 3. **暗号化対象のネットワーク定義が左右で逆・不一致**
> 4. **MTU**（→ 1400前後に調整、または MSS クランプを設定）
> 5. **IPアドレス帯が重複している**（→ [③](03-ip-subnet.md) の設計の話に戻る）

### 3-3. スプリットトンネルの判断

リモートVPN接続時、**すべての通信をVPN経由にするか、社内宛てだけをVPN経由にするか**という設計判断があります。

| 方式 | 通信の流れ | メリット | デメリット |
| --- | --- | --- | --- |
| **フルトンネル** | すべてVPN経由 | 全通信を監視・フィルタできる | **VPN装置と回線が逼迫**。Web会議が重い |
| **スプリットトンネル** | 社内宛てのみVPN、他は直接 | 快適・装置の負荷が小さい | 端末の通信を統制できない |

**実務での現実解**：
- Microsoft 365・Web会議などの**大容量かつ信頼できるサービスは除外**（スプリット）
- その他はVPN経由（フル）
- 端末側に **EDR** を入れて、直接通信部分の安全性を担保

> 💡 これは2020年のリモートワーク急拡大時に、多くの企業が学んだ教訓です。フルトンネルのままだと**VPN装置がボトルネックになり、全社の生産性が落ちます**。

### 3-4. VPN装置そのものが狙われている

近年、**VPN機器の脆弱性を突いた侵入がランサムウェア被害の最大の経路**になっています。

| 対策 | 内容 |
| --- | --- |
| **パッチ適用を最優先** | VPN機器の脆弱性は公開後、数日で悪用される |
| **MFAを必須にする** | ID/パスワードだけの認証は、漏洩したら終わり |
| **EOL製品を使い続けない** | サポート終了機器は**修正パッチが出ない** |
| **アカウント棚卸し** | 退職者・元委託先のアカウントが生きている事例が多い |
| **ログの監視** | 深夜・海外IPからのログイン成功を検知 |

> ⚠️ **これは「いつか起きるかもしれない」話ではなく、実際に多発している被害**です。VPN機器のパッチ適用は、他のどの作業よりも優先度が高いと考えてください。

## 4. ゼロトラスト — 思想の転換

### 4-1. 基本原則

```
1. すべてのアクセスを検証する（社内だから信頼、をやめる）
2. 最小権限（必要な範囲だけ、必要な時間だけ）
3. 侵害を前提にする（防げない前提で、被害を局所化する）
```

### 4-2. 検証する要素

アクセスのたびに、以下を組み合わせて判断します。

| 要素 | 確認内容 |
| --- | --- |
| **アイデンティティ** | 誰か（ID・**MFA**・パスキー） |
| **デバイス** | 会社管理端末か・OSは最新か・EDRは動いているか |
| **場所・時刻** | 通常と異なる国からのアクセスではないか |
| **振る舞い** | いつもと違う大量ダウンロードをしていないか |
| **対象データの機密度** | 機密度が高いほど厳しく |

### 4-3. 現実的な導入ステップ

一気に全部は無理です。**効果の大きい順**に手を付けます。

| 順 | 施策 | 効果 | 難易度 |
| --- | --- | --- | --- |
| 1 | **全アカウントにMFA** | ★★★ 最大 | 低 |
| 2 | **IDを統合（SSO）** | ★★★ | 中 |
| 3 | 端末管理（MDM）＋EDR導入 | ★★★ | 中 |
| 4 | 条件付きアクセス（デバイス状態で制御） | ★★ | 中 |
| 5 | ネットワーク分離（マイクロセグメンテーション） | ★★ | 高 |
| 6 | VPN廃止 → ZTNA へ移行 | ★★ | 高 |
| 7 | ログ統合・SIEM/SOC | ★★ | 高 |

> 💡 **費用対効果が圧倒的に高いのは「MFAの全面適用」**です。認証情報の窃取による侵入は、MFAだけで大半を防げます。ゼロトラストの議論をする前に、まずここを終わらせてください。
>
> 📖 IDとSSOの詳細 → [SSO（シングルサインオン）完全ガイド](../sso/README.md)

## 5. SASE / SSE — クラウド時代のセキュリティ基盤

### 5-1. 何が問題だったのか

```
【従来】拠点 → 本社のFW → インターネット・クラウド
        （ヘアピン構成／バックホール）

問題：クラウドを使うのに、わざわざ本社を経由する
     → 本社の回線とFWがボトルネック
     → 遅い・高い・拡張できない
     → リモートワーカーはそもそも本社を経由できない
```

### 5-2. SASEの考え方

**セキュリティ機能をクラウド側に置き、利用者は最寄りの拠点（PoP）に接続する。**

```
【SASE】
  本社     ─┐
  支社     ─┤
  在宅     ─┼→ 最寄りのクラウドPoP（検査・制御）→ インターネット / SaaS / 自社データセンタ
  出張先   ─┤
  工場     ─┘

  → どこにいても同じポリシーが適用される
  → 本社を経由しないので速い
  → 拠点が増えても機器を買わなくていい
```

### 5-3. 構成要素

| 略語 | 正式名称 | 役割 |
| --- | --- | --- |
| **SWG** | Secure Web Gateway | Webフィルタ・マルウェア検査（プロキシのクラウド版） |
| **CASB** | Cloud Access Security Broker | SaaSの利用状況の可視化・シャドーIT対策 |
| **ZTNA** | Zero Trust Network Access | **VPNの置き換え**。アプリ単位でアクセス許可 |
| **FWaaS** | Firewall as a Service | クラウド型ファイアウォール |
| **DLP** | Data Loss Prevention | 情報漏洩防止 |
| **SD-WAN** | — | 回線の最適化（→ [⑦](07-wireless-wan.md)） |

**SSE** = 上記のうちネットワーク機能（SD-WAN）を除いたセキュリティ部分。
**SASE** = SSE ＋ SD-WAN。

### 5-4. ZTNA が VPN と決定的に違う点

```
【VPN】接続すると「社内ネットワークの一員」になる
       → その後は基本的に社内を自由に動ける
       → 端末がマルウェアに感染していたら、社内全体が危険

【ZTNA】ネットワークに参加しない。アプリケーション単位で接続を仲介
       → 「山田さんは経費システムとファイルサーバーAにのみアクセス可」
       → 他のサーバーは存在すら見えない（見えないものは攻撃できない）
```

### 5-5. SASE導入時の注意点

| 論点 | 注意 |
| --- | --- |
| **PoPの場所** | 国内にPoPがあるか。海外PoP経由だと遅延が増える |
| **既存機器の扱い** | 一気に置き換えられない。**併存期間の設計**が必要 |
| **通信の可視性** | SSL復号の範囲とプライバシーの線引き |
| **障害時の影響** | **SASEが落ちると全拠点・全社員が止まる**。フォールバック設計は必須 |
| **コスト** | ユーザー課金が基本。人数が多いと機器購入より高くなる場合がある |

## 6. 認証 — ネットワークへの入口

### 6-1. 802.1X（有線・無線共通の認証）

**ネットワークに接続する時点で認証する**仕組みです。

```
  端末（サプリカント）
      │  ①接続を試みる
      ↓
  スイッチ / AP（オーセンティケータ）
      │  ②認証情報を転送（RADIUS）
      ↓
  RADIUSサーバー（認証サーバー）← Active Directory等と連携
      │  ③認証結果 ＋ 割り当てるVLANを返す
      ↓
  認証成功 → 適切なVLANに配置
  認証失敗 → 隔離VLAN or 遮断
```

| 認証方式 | 使うもの | 強度 |
| --- | --- | --- |
| **EAP-TLS** | **クライアント証明書** | ★★★ 最強。パスワード漏洩の影響を受けない |
| PEAP-MSCHAPv2 | ID/パスワード | ★★ 導入が容易。AD連携しやすい |
| EAP-TTLS | ID/パスワード等 | ★★ |
| MACアドレス認証（MAB） | MACアドレス | ★ **偽装可能**。プリンタ等の補助用途のみ |

**動的VLAN割り当て**が強力です。同じポートに繋いでも、「営業部の田中さん → VLAN10」「来客 → ゲストVLAN」と自動で振り分けられます。

### 6-2. アカウント管理の実務

| やること | 理由 |
| --- | --- |
| **退職者アカウントの即時停止** | **侵入経路No.1**。人事システムと連動させるのが理想 |
| **特権アカウントの分離** | 日常業務用と管理用を分ける |
| **共有アカウントの廃止** | 誰がやったか追跡できない |
| **定期的な棚卸し** | 半年に1回は全アカウントをレビュー |
| **委託先アカウントに期限を設定** | 契約終了後に自動失効させる |

## 7. 監視・検知

| 仕組み | 役割 |
| --- | --- |
| **IDS** | 侵入を**検知**する（通知のみ） |
| **IPS** | 侵入を**遮断**する（インラインで動作） |
| **EDR** | **端末側**で不審な挙動を検知・対処 |
| **NDR** | **ネットワークの通信**から異常を検知 |
| **SIEM** | 各種ログを**集約・相関分析** |
| **SOC** | それらを**人が24時間監視**する体制 |

### 検知したい典型的な異常

```
・普段アクセスしない国からのログイン成功
・深夜の大量データダウンロード
・内部から外部への大量アップロード（情報持ち出し）
・同一アカウントで短時間に複数拠点からログイン（不可能な移動）
・C2サーバーへの定期的なビーコン通信
・管理者権限の突然の付与
・大量のログイン失敗（ブルートフォース）
```

> 💡 **ログは「取っているだけ」では意味がありません**。少なくとも「誰も見ていないログ」は、インシデント後の事後調査にしか役立たない、と認識しておくべきです。

## 8. 規模別のセキュリティ構成（実務の目安）

| 規模 | 最低限やること | 現実的な構成 |
| --- | --- | --- |
| **小規模（〜50人）** | UTM 1台・ゲストWi-Fi分離・**全員MFA**・EDR | UTM（FortiGate 40F/60F クラス等）＋クラウド型EDR＋Microsoft 365のMFA |
| **中規模（50〜500人）** | ＋NGFW冗長・VLAN分離・802.1X・ログ集約 | NGFW HA構成＋RADIUS＋SIEM（クラウド型）＋MDM |
| **大規模（500人〜）** | ＋SASE/ZTNA・マイクロセグメンテーション・SOC | SASE基盤＋EDR/NDR＋24時間SOC（自社 or アウトソース） |

**予算配分の目安**：小規模なら「UTM に投資するより、**MFA + EDR + バックアップ**」の方が費用対効果が高い、というのが近年の実感です。境界防御の限界を踏まえた判断です。

## 9. よくある疑問（FAQ）

**Q. UTMを入れれば中小企業のセキュリティは十分？**
A. 不十分です。UTMは「入口」だけを守ります。**メール経由のフィッシング・認証情報の窃取・端末の感染**は防げません。**MFA・EDR・バックアップ（3-2-1ルール）**の3点セットを同時に整えてください。

**Q. VPNとZTNA、どちらを選ぶべき？**
A. 既存のVPN装置が現役でユーザー数が少ないなら、当面はVPN＋MFAで問題ありません。ただし**装置の更改タイミングでZTNAを検討**するのが自然です。VPN装置の脆弱性リスクとライセンス費用を比較してください。

**Q. SSL復号は必ずやるべき？**
A. 「やった方が検知率は上がるが、副作用も大きい」というトレードオフです。**まずはカテゴリ除外を前提とした部分的な復号から**始め、法務・人事と合意を取ってください。

**Q. ゼロトラストにすればファイアウォールは不要？**
A. 不要にはなりません。境界防御は「不要」ではなく「**それだけでは足りない**」のです。多層防御の1層として引き続き機能します。

## まとめ

- 現代のFWは**ステートフル**が前提。ただし**クラウドのNACLはステートレス**なので混同しない
- ポート番号では制御できない時代（全部443）。**アプリケーション識別が必要**
- **DMZの本質は「DMZ→社内」を絞ること**
- **マイクロセグメンテーションはランサムウェアの横展開を止める最有効手段**
- サイト間VPNのトラブルは **パラメータ不一致・NAT-T・MTU・IP重複**
- **VPN機器の脆弱性は現在の最大の侵入経路**。パッチとMFAを最優先で
- リモートVPNは**スプリットトンネルで大容量SaaSを逃がす**のが現実解
- ゼロトラストは製品ではなく思想。**まずMFAの全面適用**が最も効く
- SASE/ZTNAは「本社経由をやめる」ための基盤。ただし**SASE障害時の影響範囲**は必ず設計に織り込む
- 小規模なら **MFA + EDR + バックアップ** が最も費用対効果が高い
