# ⑤ トランスポート層とアプリケーション層

> **この章のゴール**：TCPとUDPの違いを「なぜそう設計されているか」から理解する。そして、ポート番号・DNS・HTTP・TLSという、アプリ開発者もインフラ担当も毎日触る技術の中身を押さえる。

← [④ ルーティング](04-routing.md) ／ 次章 → [⑥ ネットワークセキュリティ](06-security.md)

---

## 0. まず全体像（30秒）

L3（IP）までで「相手のマシンには届く」ようになりました。しかし2つ足りません。

| 足りないもの | 解決するのは |
| --- | --- |
| **同じマシンの中の、どのアプリ宛てか** | **ポート番号**（L4） |
| **本当に届いたか、順番は正しいか** | **TCP**（L4） |

```
   IPアドレス = マンションの住所
   ポート番号 = 部屋番号
   
   192.168.1.10 : 443
   └──────────┘  └─┘
      どのマシン   どのアプリ
```

そして L7 では、**DNS（名前解決）→ TLS（暗号化）→ HTTP（中身のやりとり）** という3つが、Web通信のほぼすべてを占めています。

## 1. ポート番号

### 1-1. 3つの区分

| 範囲 | 名称 | 用途 |
| --- | --- | --- |
| 0 〜 1023 | **ウェルノウンポート** | 標準サービス。**待ち受けにはroot/管理者権限が必要** |
| 1024 〜 49151 | 登録済みポート | アプリケーションが登録 |
| 49152 〜 65535 | **エフェメラルポート** | **クライアントが接続時に自動で使う一時ポート** |

> 💡 **クライアント側のポートは毎回変わります**。`192.168.1.10:51234 → 93.184.216.34:443` のように、送信元は自動割当。サーバー側だけが固定です。ファイアウォールのルールを書くときは、**宛先ポートだけを指定する**のが基本です。

### 1-2. 覚えるべきポート番号

| ポート | プロトコル | サービス | 備考 |
| --- | --- | --- | --- |
| 20/21 | TCP | FTP | データ/制御。**平文。今はSFTPを使うべき** |
| **22** | TCP | **SSH / SFTP** | リモート管理の標準 |
| 25 | TCP | SMTP | メール送信（サーバー間） |
| **53** | **UDP/TCP** | **DNS** | **UDPが基本、大きい応答とゾーン転送はTCP** |
| 67/68 | UDP | DHCP | サーバー/クライアント |
| **80** | TCP | **HTTP** | 平文Web |
| 123 | UDP | NTP | 時刻同期 |
| 161/162 | UDP | SNMP | 監視/トラップ |
| 389 / 636 | TCP | LDAP / LDAPS | ディレクトリ（AD認証） |
| **443** | **TCP/UDP** | **HTTPS / QUIC** | **UDP 443 = HTTP/3**。忘れがち |
| 445 | TCP | SMB | Windowsファイル共有。**インターネットに絶対公開しない** |
| 587 | TCP | SMTP Submission | メール送信（クライアント→サーバー） |
| 993 / 995 | TCP | IMAPS / POP3S | メール受信 |
| 1194 | UDP | OpenVPN | |
| 3306 / 5432 | TCP | MySQL / PostgreSQL | **DBは絶対に公開しない** |
| **3389** | TCP | **RDP** | **公開すると即座に攻撃される。VPN経由必須** |
| 500 / 4500 | UDP | IKE / IPsec NAT-T | サイト間VPN |
| 51820 | UDP | WireGuard | 新しいVPN |

> ⚠️ **「公開してはいけない三銃士」＝ 445（SMB）・3389（RDP）・データベースポート**。インターネットに直接公開すると、数分〜数時間で攻撃を受けます。ランサムウェア被害の主要な侵入経路がまさにここです。

## 2. TCP — 確実に届ける

### 2-1. TCPが保証すること

| 機能 | 内容 |
| --- | --- |
| **コネクション型** | 事前に接続を確立してから通信 |
| **順序保証** | シーケンス番号で順番を復元 |
| **再送制御** | ACKが返らなければ再送 |
| **フロー制御** | 受信側のバッファ量（ウィンドウサイズ）に合わせる |
| **輻輳制御** | ネットワークが混んできたら送信速度を落とす |

### 2-2. 3ウェイハンドシェイク（接続確立）

```
クライアント                        サーバー
     │                                │
     │ ──── SYN (seq=x) ──────────→  │  「話しかけていい？」
     │                                │
     │ ←─── SYN+ACK (seq=y, ack=x+1) │  「いいよ。そっちも聞こえる？」
     │                                │
     │ ──── ACK (ack=y+1) ────────→  │  「聞こえてる。始めよう」
     │                                │
     │ ═════ データ転送 ═══════════  │
```

**なぜ3回必要か**：双方向の通信路が生きていることを、**お互いが確認**する必要があるからです。2回だと、サーバーは「自分の返事が届いたか」を知りません。

### 2-3. 4ウェイハンドシェイク（切断）

```
     │ ──── FIN ─────────→  │   「もう送るものはない」
     │ ←─── ACK ──────────  │   「了解」
     │ ←─── FIN ──────────  │   「こちらも送り終わった」
     │ ──── ACK ─────────→  │   「了解」
     │
     └─ TIME_WAIT（約2分待機）  ← 遅れて届くパケットのため
```

> 💡 **`TIME_WAIT` が大量にあるのは正常です**。高負荷サーバーで枯渇する場合はカーネルパラメータの調整対象になりますが、通常は放置して構いません。

### 2-4. TCPの状態遷移（トラブル時に見る）

```
$ ss -tan     または     netstat -an

LISTEN       待ち受け中（サーバーが正常に起動している）
SYN_SENT     SYNを送ったが応答なし → 【FWでブロック or 相手が落ちている】
ESTABLISHED  接続確立・通信中（正常）
CLOSE_WAIT   相手からFINが来たが自分が閉じていない → 【アプリのバグの疑い】
TIME_WAIT    正常な終了処理中
```

| 状態 | 大量にあるときの意味 |
| --- | --- |
| **SYN_SENT が滞留** | **ファイアウォールで落とされている**可能性が高い |
| **SYN_RECV が大量** | SYN Flood 攻撃の可能性 |
| **CLOSE_WAIT が大量** | **アプリケーションがソケットを閉じていない**（リソースリーク） |
| TIME_WAIT が大量 | 通常は正常。極端なら短命接続が多すぎる |

### 2-5. ウィンドウサイズと帯域遅延積 — 「遠いと遅い」の正体

TCPは「ACKを待たずに送れる量（ウィンドウサイズ）」に上限があります。そのため、**遅延が大きいと帯域を使い切れません**。

```
最大スループット ≒ ウィンドウサイズ ÷ RTT（往復遅延）

例: ウィンドウ 64KB、東京〜米国西海岸 RTT 100ms の場合
   64KB ÷ 0.1秒 = 640KB/s ≒ 5Mbps
   
   → 回線が1Gbpsでも、1本のTCP接続では5Mbpsしか出ない！
```

**対策**：
- **ウィンドウスケーリング**（RFC 1323）を有効化 → 現代のOSは既定で有効
- 並列転送（複数コネクション）
- 遅延の小さい場所にサーバーを置く／CDNを使う

> 💡 **「回線を10Gbpsにしたのに、海外拠点とのファイル転送が速くならない」**——これは帯域ではなく**遅延（RTT）とウィンドウサイズ**の問題です。回線増強では解決しません。この見極めができると、無駄な投資を防げます。

## 3. UDP — 速さ優先

### 3-1. 特徴

| TCP | UDP |
| --- | --- |
| 接続を確立する | **いきなり送る** |
| 再送・順序保証あり | **なし（届かなくても知らない）** |
| ヘッダ 20バイト | **ヘッダ 8バイト** |
| 遅いが確実 | **速いが不確実** |

### 3-2. UDPが選ばれる理由

| 用途 | なぜUDPか |
| --- | --- |
| **DNS** | 1往復で終わる。再送はアプリ側で十分 |
| **音声・ビデオ通話** | **再送されても手遅れ**。多少欠けても通話は続く方が良い |
| **動画のライブ配信** | 同上 |
| **NTP** | 軽量・1往復 |
| **SNMP** | 監視対象に負荷をかけたくない |
| **QUIC（HTTP/3）** | UDP上に**独自の信頼性制御を実装**した（後述） |

> 💡 **「UDPは信頼性がないから業務では使わない」は誤解**です。**信頼性の制御をアプリ側でやりたいから、あえてUDPを使う**——これが現代的な考え方です。QUICはその極致で、TCPの制約を回避するためにUDPの上に全部作り直しています。

## 4. DNS — 名前をIPに変える

### 4-1. 名前解決の流れ

```
1. ブラウザ・OSのキャッシュを見る          （hostsファイルもここ）
2. なければ DNSキャッシュサーバー（フルリゾルバ）に聞く
3. フルリゾルバが、ルートDNS → .com → example.com と階層をたどる（再帰問い合わせ）
4. 結果を返し、TTLの間キャッシュする
```

### 4-2. 主要レコード（最低限）

| レコード | 意味 |
| --- | --- |
| **A** | ホスト名 → IPv4アドレス |
| **AAAA** | ホスト名 → IPv6アドレス |
| **CNAME** | 別名。**ゾーン頂点（example.com自体）には使えない** |
| **MX** | メールの宛先サーバー |
| **TXT** | SPF・DKIM・DMARC・所有権証明 |
| **NS** | このゾーンを管理するDNSサーバー |
| **PTR** | IP → ホスト名（逆引き） |

> 📖 **DNSの詳細は専用ガイドがあります** → [DNS・ドメイン完全ガイド](../dns-guide.md)（レコードの詳細、ドメイン取得、HTTPS証明書の仕組みまで）

### 4-3. ネットワーク担当として押さえるべきポイント

| 論点 | 実務上の注意 |
| --- | --- |
| **TTLの設計** | 切り替え前に**TTLを短く（300秒等）しておく**。当日に短くしても手遅れ |
| **内部DNSと外部DNS** | 社内向けと公開向けで別の答えを返す構成（**スプリットDNS**）が一般的 |
| **DNSは単一障害点** | **必ず冗長化**。DNSが落ちると「全部落ちた」ように見える |
| **DoH / DoT** | DNS over HTTPS/TLS。**ブラウザが独自にDoHを使うと社内のDNSフィルタを迂回**してしまう |
| **キャッシュポイズニング** | DNSSEC・ソースポートランダム化で対策 |

> ⚠️ **「なんか全部繋がらない」の原因No.1はDNS**です。`ping 8.8.8.8` は通るのに `ping google.com` が通らないなら、確定でDNSの問題。切り分けの第一歩として必ず両方試してください。

## 5. HTTP — Webの言葉

### 5-1. バージョンの進化

| バージョン | 年 | トランスポート | 主な改善 |
| --- | --- | --- | --- |
| HTTP/1.0 | 1996 | TCP | 1リクエスト1接続 |
| **HTTP/1.1** | 1997 | TCP | Keep-Alive。**まだ広く現役** |
| **HTTP/2** | 2015 | TCP + TLS | **多重化**（1接続で並列）・ヘッダ圧縮・サーバープッシュ |
| **HTTP/3** | 2022 | **QUIC（UDP）+ TLS1.3** | **HoLブロッキング解消**・接続の高速確立・経路変更に強い |

### 5-2. HTTP/2 の「多重化」とその限界

HTTP/1.1では1接続あたり1リクエストずつしか処理できず、ブラウザは6本程度の接続を張って誤魔化していました。HTTP/2はこれを**1接続で並列化**しました。

しかし問題が残りました：**TCPレベルのHead-of-Lineブロッキング**です。

```
HTTP/2 over TCP:
  1本のTCP接続で10個のファイルを並列ダウンロード中
  → パケットが1つロスすると、TCPは「順序保証」のため全体を止めて再送を待つ
  → 無関係な9個のファイルまで止まる
```

### 5-3. HTTP/3（QUIC）が解決したこと

QUICは**UDPの上に、ストリームごとに独立した信頼性制御を実装**しました。

| 改善 | 内容 |
| --- | --- |
| **HoLブロッキング解消** | ストリームごとに独立。1つのロスが他を止めない |
| **接続確立が速い** | TCPハンドシェイク＋TLSハンドシェイクを統合（**0-RTT/1-RTT**） |
| **コネクションマイグレーション** | **Wi-Fi → モバイル回線に切り替わっても接続が切れない**（Connection IDで識別） |
| 暗号化が前提 | TLS 1.3 が組み込み。平文QUICは存在しない |

> ⚠️ **ネットワーク管理者への影響**：
> - HTTP/3 は **UDP 443番** を使います。**UDP 443 をブロックしていると、ブラウザはTCPにフォールバックします**（動くが遅い）
> - 従来のプロキシ・IPS は TCP 前提のものが多く、**QUICを解析できない**ことがある
> - 企業によっては「可視性が失われる」として**あえてUDP 443をブロック**する運用もある。是非はともかく、**意図的な設計判断として行うべき**です

## 6. TLS — 暗号化と身元確認

### 6-1. TLSが提供する3つ

| 機能 | 内容 |
| --- | --- |
| **暗号化** | 盗聴されても中身が読めない |
| **完全性** | 改ざんを検知できる |
| **認証** | **相手が本物であることを証明書で確認** |

「暗号化」だけが注目されがちですが、**認証（なりすまし防止）が同じくらい重要**です。

### 6-2. バージョン

| バージョン | 状態 |
| --- | --- |
| SSL 2.0/3.0 | **危殆化。使用禁止** |
| TLS 1.0/1.1 | **非推奨。主要ブラウザでサポート終了** |
| **TLS 1.2** | 現役。まだ広く使われる |
| **TLS 1.3** | **推奨**。ハンドシェイクが1往復に短縮、脆弱な暗号方式を排除 |

**設定の指針**：サーバー側は **TLS 1.2 と 1.3 のみ有効化**。1.1以下は無効にしてください。

### 6-3. ハンドシェイクの流れ（TLS 1.3）

```
クライアント → サーバー : ClientHello（対応する暗号方式＋鍵交換の材料）
クライアント ← サーバー : ServerHello + 証明書 + 鍵交換の材料 + Finished
クライアント → サーバー : Finished
                     ↓
             以降は共通鍵で暗号化通信
```

TLS 1.2 では2往復必要だったものが、**1往復**になっています。遅延の大きい経路ほど効果が大きい改善です。

### 6-4. 証明書の検証で見ているもの

```
1. 有効期限内か
2. ドメイン名が一致するか（CN / SAN）
3. 信頼された認証局（CA）の署名があるか
4. 失効していないか（CRL / OCSP）
5. 中間証明書が正しく連なっているか（チェーン）
```

> ⚠️ **最頻出のトラブル：中間証明書の設定漏れ**。「PCのブラウザでは見えるのに、スマホや古い端末だとエラーになる」——これはサーバーに中間証明書を入れ忘れているサインです。PCは中間証明書をキャッシュ／自動取得することがあるため、気づきにくいのです。**SSL Labs等の外部チェックツールで確認**してください。

### 6-5. SSLインスペクション（可視化）の是非

企業のNGFW/プロキシは、**TLS通信を一度復号して中身を検査**することがあります。

| メリット | デメリット・リスク |
| --- | --- |
| マルウェア・情報漏洩を検知できる | **プライバシーの問題**（銀行・医療サイトは除外が必要） |
| URLフィルタが正確に効く | 機器の負荷が非常に大きい |
| — | **証明書ピンニングしているアプリが動かなくなる** |
| — | 復号点が新たな攻撃対象になる |

**実務での定石**：全部を復号するのではなく、**カテゴリ（金融・医療・個人）を除外リストに入れ、それ以外を検査**する。そして**就業規則・プライバシーポリシーで従業員に周知**しておくこと。

## 7. QoS — 通信に優先順位をつける

帯域が足りないとき、**「何を優先するか」**を決めるのがQoSです。

### 7-1. 優先すべきトラフィックの順序

| 優先度 | トラフィック | 要求される品質 |
| --- | --- | --- |
| **最高** | 音声（VoIP） | **遅延 < 150ms、ジッタ < 30ms、ロス < 1%** |
| 高 | ビデオ会議 | 遅延 < 200ms、帯域が必要 |
| 中 | 業務アプリ・ERP | 応答性 |
| 低 | Web閲覧・メール | 多少遅くても支障なし |
| 最低 | バックアップ・OSアップデート | いつ終わってもよい |

### 7-2. 仕組み

| 要素 | 内容 |
| --- | --- |
| **分類（Classification）** | どのトラフィックか識別する（ポート・DSCP値・アプリ識別） |
| **マーキング** | IPヘッダの **DSCP** フィールドに印を付ける（音声はEF=46が定番） |
| **キューイング** | 優先度別のキューに入れる（LLQ/CBWFQ） |
| **シェーピング／ポリシング** | 帯域の上限を設ける（超過分を遅延させる／破棄する） |

> 💡 **QoSは「帯域が足りている場所では意味がない」**。輻輳する場所（＝WAN回線の出口）にだけ設定するのが正解です。LAN内は帯域が潤沢なので、通常は不要です。
>
> ⚠️ **DSCP値はインターネットを越えると保証されません**。ISPが書き換える／無視することがあります。QoSが確実に効くのは**自社で制御できる範囲（LAN内・SD-WAN・IP-VPN契約内）**だけです。

## 8. トラブルシューティング（L4/L7）

| 症状 | 原因の候補 | 確認方法 |
| --- | --- | --- |
| pingは通るがアプリが繋がらない | **ポートが閉じている（FW）** | `nc -zv host 443` / `Test-NetConnection` |
| 名前だけ解決できない | DNS | `ping 8.8.8.8` と `nslookup` を比較 |
| 接続が確立せずタイムアウト | FWで**破棄（drop）** されている | `SYN_SENT` で滞留 |
| 即座に「接続拒否」 | **サービスが起動していない**（RSTが返る） | `ss -tlnp` で LISTEN 確認 |
| 遅い・転送が伸びない | **RTT × ウィンドウサイズ** | `ping` でRTT測定、帯域遅延積を計算 |
| HTTPSだけエラー | 証明書（期限・チェーン・ドメイン不一致） | ブラウザの証明書詳細 / SSL Labs |
| 大きいデータだけ失敗 | **MTU / PMTUD** | `ping -M do -s 1472`（Linux）でサイズを詰める |
| 一部端末だけ繋がらない | プロキシ設定・DoH・ローカルFW | 端末のプロキシ設定を確認 |

### タイムアウトと接続拒否の違いは決定的

```
タイムアウト（応答なし）  → ファイアウォールが「破棄（drop）」している
                         または経路が無い
接続拒否（即座にRST）    → 通信は到達している。相手のサービスが起動していない
```

**この違いだけで、ネットワークの問題かサーバーの問題かが切り分けられます。**

## 9. よくある疑問（FAQ）

**Q. なぜHTTPSなのにDNSは暗号化されていないの？**
A. 従来のDNSは平文なので、「どのサイトを見たか」は通信経路上から分かります。これを解決するのが **DoH / DoT** です。ただし企業では、DoHによって社内のフィルタリングが迂回される問題があるため、**ブラウザのDoHを無効化するポリシーを配布する**運用が一般的です。

**Q. ポートスキャンされるのは危険？**
A. スキャン自体は日常的に発生しています（インターネットに公開していれば常時）。問題は**開いているポートに脆弱なサービスがある**こと。**不要なポートは閉じる**、**必要なものはVPN経由に限定する**のが対策です。

**Q. HTTP/3にすると速くなる？**
A. **モバイル環境・遅延が大きい環境・パケットロスがある環境では明確に速くなります**。安定した有線LANでは差は小さいです。CDNを使っていれば自動的に有効になっていることが多いので、まずは現状を確認してください。

**Q. 「TCPが遅い」と言われたらまず何を見る？**
A. **RTT（遅延）とパケットロス率**です。帯域（Mbps）ではありません。`ping` の結果と `traceroute` のどこで遅延が跳ねているかを見れば、大半は特定できます。

## まとめ

- **IP = マシン、ポート = アプリ**。この2つで通信相手が一意に決まる
- **445 / 3389 / DBポートは絶対に公開しない**
- TCPは **3ウェイハンドシェイク**で接続。状態（`SYN_SENT` / `CLOSE_WAIT`）が切り分けの手がかり
- **遠距離が遅いのは帯域ではなくRTT × ウィンドウサイズ**の問題。回線増強では解決しない
- UDPは「信頼性がない」のではなく「**信頼性を自分で作りたい**」ために選ばれる（QUICが好例）
- **`ping 8.8.8.8` は通るが名前解決できない → DNSの問題**
- HTTP/3は **UDP 443**。ブロックするなら意図的な判断として行う
- TLSは **1.2 と 1.3 のみ**有効化。中間証明書の入れ忘れに注意
- QoSは**輻輳する場所（WAN出口）にだけ**設定する
- **タイムアウト = FWで破棄／接続拒否 = サービス未起動**
