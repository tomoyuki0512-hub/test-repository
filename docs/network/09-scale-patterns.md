# ⑨ 規模別ネットワーク構成パターン（小規模・中規模・大規模）

> **この章のゴール**：自社の規模に合った構成を、構成図・機器リスト・コスト目安つきで選べるようになる。そして「いつ次の規模へ移行すべきか」の判断基準を持つ。

← [⑧ クラウドネットワーク](08-cloud-network.md) ／ 次章 → [⑩ オンプレ・クラウド・ハイブリッド構成](10-onprem-cloud-hybrid.md)

---

## 0. まず全体像（30秒）

規模が変わると、**何が変わるのか**。実は変わるのは3つだけです。

| 変わるもの | 小規模 | 中規模 | 大規模 |
| --- | --- | --- | --- |
| **階層の数** | 1階層（ルータ＋スイッチ） | 2階層（コア＋アクセス） | **3階層**（コア＋ディストリ＋アクセス）／Spine-Leaf |
| **冗長化の範囲** | ほぼ無し（＋モバイル予備） | 主要機器を冗長化 | **全経路・全電源を冗長化** |
| **運用の担い手** | 兼任担当者・外部委託 | 専任1〜2名 | **専任チーム＋SOC** |

そして最も重要な原則がこれです。

> ⚠️ **規模の判断基準は「人数」ではなく「止まったときの損害額」です。**
> 20人の会社でも、止まると1時間で数百万円の損失が出るなら、中規模相当の冗長構成が必要です。逆に500人でも、半日止まっても業務が回る（紙で代替できる）なら過剰投資は不要です。
> **人数は目安、判断はビジネス影響で。**

---

## 1. 規模の定義（本章での区分）

| 規模 | 人数 | 拠点数 | 端末台数の目安 | 想定される組織 |
| --- | --- | --- | --- | --- |
| **小規模** | 〜50人 | 1拠点 | 50〜150台 | スタートアップ、士業事務所、小売店舗、クリニック |
| **中規模** | 50〜500人 | 2〜10拠点 | 150〜1,500台 | 中堅企業、複数店舗展開、地方の製造業 |
| **大規模** | 500人〜 | 10拠点〜／DC保有 | 1,500台〜 | 大企業、全国展開、金融・製造の基幹系 |

**端末台数は「人数 × 2〜3」**で見積もります。PC・スマホ・IP電話・プリンタ・カメラ・IoT機器が加わるためです。**この見積もりを人数だけで行うと、必ずIPアドレスとAP容量が足りなくなります。**

## 2. 小規模構成（〜50人・1拠点）

### 2-1. 構成図

```
                  インターネット
                （光回線 1Gbps ベストエフォート）
                        │
                  ┌─────┴─────┐
                  │   ONU     │
                  └─────┬─────┘
                        │
                  ┌─────┴──────────────┐
                  │  UTM / ルータ       │  ← ルータ + FW + NAT + VPN + DHCP
                  │  （FortiGate 60F 等）│     を1台に集約
                  └─────┬──────────────┘
                        │
                  ┌─────┴─────────────┐
                  │  L2スイッチ（PoE+）  │  24〜48ポート
                  └──┬────┬────┬───────┘
                     │    │    │
              ┌──────┘    │    └──────┐
              │           │           │
         ┌────┴───┐  ┌────┴───┐  ┌────┴────┐
         │Wi-Fi AP│  │  PC群   │  │ NAS /   │
         │ ×2〜4  │  │ 有線    │  │ プリンタ │
         └────────┘  └────────┘  └─────────┘

  ＋ バックアップ回線：モバイルルータ（5G/LTE）を UTM の WAN2 へ
```

### 2-2. 機器構成と費用目安

| 役割 | 機器 | 台数 | 初期費用の目安 |
| --- | --- | --- | --- |
| UTM / ルータ | FortiGate 60F、YAMAHA RTX、UniFi Gateway 等 | 1 | 10〜40万円（＋年間ライセンス 5〜15万円） |
| L2スイッチ（PoE+） | 24〜48ポート・**管理型** | 1〜2 | 5〜20万円 |
| Wi-Fi AP | Wi-Fi 6/6E 対応 | 2〜4 | 3〜8万円/台 |
| NAS | RAID構成 | 1 | 10〜30万円 |
| UPS | 無停電電源装置 | 1 | 3〜10万円 |
| **初期合計** | | | **50〜150万円** |

| 月額 | 費用 |
| --- | --- |
| 光回線（法人） | 5,000〜20,000円 |
| モバイルバックアップ | 3,000〜10,000円 |
| クラウド（Microsoft 365 等） | 1,500〜3,000円/人 |
| **月額合計（30人想定）** | **6〜12万円** |

### 2-3. 設計のポイント

| 項目 | 推奨 |
| --- | --- |
| **セグメント** | 最低限 **業務／ゲスト／機器管理** の3分割。1セグメントで済ませない |
| IPアドレス | `10.1.0.0/16` 内で `/24` を切る。**`192.168.1.0/24` は避ける**（在宅VPNで衝突） |
| ルーティング | **スタティックのみ**。動的ルーティングは不要 |
| 冗長化 | 機器の冗長化はコスト的に困難。**モバイル回線でWANだけ冗長化**するのが費用対効果◎ |
| Wi-Fi | AP 2〜4台。**チャネルを手動で固定**（自動でも可） |
| 監視 | UTMの標準機能＋クラウド管理（メール通知）で十分 |
| **バックアップ** | **3-2-1ルール**（3コピー・2種類の媒体・1つはオフサイト）。ランサム対策として最重要 |

### 2-4. 小規模で「やってはいけない」こと

| ✗ やりがちな失敗 | なぜダメか | 代わりに |
| --- | --- | --- |
| **アンマネージドスイッチを買う** | VLANが切れず、後から必ず買い替えになる | **管理型（マネージド）を選ぶ**。差額は数万円 |
| ゲストWi-Fiを社内と同じネットワークに | 来客端末から社内NASが見える | 専用VLAN＋クライアント分離 |
| **UTMだけでセキュリティ対策完了とする** | メール経由・認証窃取は防げない | **MFA＋EDR＋バックアップ**を同時に |
| ルータのファーム更新をしない | 脆弱性が放置され、侵入経路になる | 保守契約を結び、更新を運用に組み込む |
| 構成図を残さない | 担当者が辞めると誰も分からなくなる | **1枚でいいので図とIP一覧を残す** |

### 2-5. 「クラウド寄せ」という選択肢

小規模では、**サーバーを持たない**構成が最も合理的です。

```
【従来】社内にファイルサーバー・メールサーバー・業務システム
        → 機器費・電気代・保守・バックアップ・故障対応がすべて自社負担

【推奨】Microsoft 365 / Google Workspace + SaaS
        → 社内に置くのは「ネットワーク機器」と「NAS（ローカルバックアップ用）」だけ
        → ネットワーク担当の仕事が激減する
```

**小規模企業にとって、最大のネットワーク設計判断は「何を社内に置かないか」**です。詳しくは [⑩](10-onprem-cloud-hybrid.md) を参照してください。

## 3. 中規模構成（50〜500人・2〜10拠点）

### 3-1. 構成図（本社）

```
        インターネット回線A          インターネット回線B
       （メイン・帯域確保型）        （バックアップ・別キャリア）
              │                          │
        ┌─────┴──────────────────────────┴─────┐
        │      NGFW（HA構成：Active/Standby）    │
        │      FortiGate 200F / PA-Series 等     │
        └─────┬──────────────────────────┬─────┘
              │                          │
        ┌─────┴──────────┐    ┌──────────┴─────┐
        │  コアL3スイッチ A │════│ コアL3スイッチ B │  ← スタック/VRRP
        │  （VLAN間ルーティング）  （冗長）           │
        └──┬──────┬───────┘    └───┬─────┬──────┘
           ║      ║                  ║     ║
        （LAG）  （LAG）           （LAG） （LAG）
           ║      ╚══════════╦═══════╝     ║
     ┌─────╨─────┐    ┌──────╨──────┐  ┌───╨────────┐
     │アクセスSW  │    │アクセスSW    │  │サーバーSW   │
     │ 1F（PoE+） │    │ 2F（PoE+）   │  │（DMZ/内部）  │
     └──┬────┬───┘    └───┬────┬────┘  └─────┬──────┘
        │    │            │    │              │
      PC群  AP群         PC群  AP群      サーバー / 仮想基盤

  ＋ 拠点接続：IP-VPN or 広域イーサ（＋インターネットVPNでバックアップ）
  ＋ クラウド接続：専用線（Direct Connect / ExpressRoute）
  ＋ 無線：APコントローラ（オンプレ or クラウド管理）
```

### 3-2. 拠点接続の構成

```
                    ┌──────────┐
                    │   本社   │ ← センター拠点
                    └────┬─────┘
                         │  IP-VPN / 広域イーサネット（閉域網）
        ┌────────────┬───┴────┬────────────┐
        │            │        │            │
   ┌────┴───┐  ┌────┴───┐ ┌──┴─────┐ ┌────┴───┐
   │ 大阪支社 │  │名古屋支社│ │ 福岡営業所│ │ 工場   │
   └────────┘  └────────┘ └────────┘ └────────┘
   
   ＋ 各拠点にインターネット回線を別途引き、
     SaaS通信はローカルブレイクアウト（本社経由にしない）
```

### 3-3. 機器構成と費用目安

| 役割 | 機器 | 台数 | 費用目安 |
| --- | --- | --- | --- |
| NGFW（本社・HA） | FortiGate 200F クラス | 2 | 200〜500万円（＋ライセンス年50〜150万円） |
| コアL3スイッチ | 冗長構成・10G/25Gアップリンク | 2 | 150〜400万円 |
| アクセススイッチ | 48ポート PoE+ | 10〜30 | 15〜40万円/台 |
| Wi-Fi AP | Wi-Fi 6E・コントローラ管理 | 20〜60 | 5〜10万円/台 |
| APコントローラ | オンプレ or クラウド | 1式 | 50〜200万円 or 年額 |
| 拠点ルータ | 支社用 | 拠点数分 | 20〜60万円/台 |
| サーバー基盤 | 仮想化ホスト＋ストレージ | 1式 | 500〜2,000万円 |
| **初期合計** | | | **1,500万〜5,000万円** |

| 月額 | 費用 |
| --- | --- |
| 本社回線（帯域確保型 ×2） | 15〜40万円 |
| 拠点間 IP-VPN | 10〜30万円/拠点 |
| クラウド専用線 | 5〜20万円 |
| 保守契約（機器） | 年額で機器費の10〜15% |
| **月額合計（5拠点想定）** | **80〜200万円** |

### 3-4. 設計のポイント

| 項目 | 推奨 |
| --- | --- |
| **階層** | **コア＋アクセスの2階層**。コアでVLAN間ルーティングを集約 |
| **冗長化** | コアスイッチ・NGFW・WAN回線を冗長化。スタック技術（VSS/vPC/MLAG）でLAGを組む |
| **VLAN設計** | 用途別に7〜10個（→ [②](02-physical-datalink.md) の設計例） |
| **IPアドレス** | 拠点ごとに `/16`、VLANごとに `/24`（→ [③](03-ip-subnet.md)） |
| **ルーティング** | **OSPF（シングルエリア）** または スタティック＋フローティング |
| **認証** | **802.1X（有線・無線）＋ RADIUS**。動的VLAN割り当て |
| **監視** | **SNMP＋Syslog＋NetFlow を集約**。Zabbix / PRTG / クラウド監視 |
| **Wi-Fi** | コントローラ管理必須。手動設定は破綻する |
| **ドキュメント** | 構成図・IP管理表・機器台帳・**変更履歴** を必ず維持 |

### 3-5. 中規模で最初に整えるべき優先順位

予算は有限です。**効果の大きい順**に投資してください。

```
1. WAN回線の冗長化（別キャリア）        ← 止まると全社が止まる
2. コアスイッチの冗長化                 ← 単一障害点の解消
3. 監視の仕組み（SNMP + アラート通知）   ← 「気づけない」が最大のリスク
4. 802.1X 認証                         ← 不正接続の防止
5. VLAN分離の徹底（IoT・ゲスト・管理）   ← 侵害の横展開防止
6. ログ集約（SIEM）                     ← 事後調査と検知
```

> 💡 **「3. 監視」を後回しにする組織が非常に多い**のですが、これは間違いです。**冗長化しても、切り替わったことに気づかなければ意味がありません。**片系で運用し続けて、もう片方も落ちて初めて障害になる——という事故は実際によくあります。

### 3-6. 中規模の落とし穴

| 落とし穴 | 症状 | 対策 |
| --- | --- | --- |
| **小規模構成のまま人数だけ増えた** | 1セグメントに300台。ブロードキャストで不安定 | 早期にVLAN分割 |
| **拠点ごとに設計がバラバラ** | 拠点によってIP体系・機器・設定が違い、運用不能 | **標準構成（テンプレート）を決める** |
| **本社集約（ヘアピン）でクラウドが遅い** | Web会議が途切れる、SaaSが重い | ローカルブレイクアウト／SD-WAN |
| **属人化** | 「〇〇さんしか分からない」 | 構成図・手順書・パスワード管理の整備 |
| **機器のEOL放置** | 保守切れ機器で障害。部品が無い | **機器台帳にEOL日を記載し、5年で計画更改** |

## 4. 大規模構成（500人〜・多拠点／データセンタ保有）

### 4-1. 3階層アーキテクチャ（キャンパスネットワーク）

```
              ┌────────────────────────────────┐
              │      インターネット / WAN        │
              └───────────┬────────────────────┘
                          │
        ┌─────────────────┴─────────────────┐
        │      境界（NGFW / SASE 接続点）      │  冗長・複数拠点
        └─────────────────┬─────────────────┘
                          │
    ═══════════════════════════════════════════════
        ┌────────────┐        ┌────────────┐
        │  コア SW A  │════════│  コア SW B  │      ← 高速転送に専念
        └──┬──────┬──┘        └──┬──────┬──┘         L3・100G
           ║      ╚═══════╗  ╔════╝      ║
    ═══════════════════════════════════════════════
        ┌──╨─────────┐  ┌──╨─────────┐            ← 集約・ポリシー適用
        │ディストリA/B │  │ディストリC/D │              L3境界・ACL
        │  （棟1）     │  │  （棟2）     │              VLAN間ルーティング
        └──┬────┬────┘  └──┬────┬─────┘
           ║    ║           ║    ║
    ═══════════════════════════════════════════════
      ┌────╨┐ ┌╨────┐   ┌────╨┐ ┌╨────┐          ← 端末収容
      │アクセス│ │アクセス│  │アクセス│ │アクセス│            PoE++・1G/2.5G
      └──┬──┘ └──┬──┘   └──┬──┘ └──┬──┘
        PC/AP    PC/AP     PC/AP    PC/AP
```

| 階層 | 役割 | 設計方針 |
| --- | --- | --- |
| **コア** | ひたすら高速に転送する | **余計な機能を持たせない**。ACLやNATを置かない |
| **ディストリビューション** | 集約点・**L3境界**・ポリシー適用 | VLAN間ルーティング・ACL・QoSはここ |
| **アクセス** | 端末を収容 | PoE給電・802.1X・ポートセキュリティ |

**なぜ3階層か**：コアに機能を持たせると、コアの障害が全社に波及します。**役割を分けることで、影響範囲を階層内に閉じ込められます。**

### 4-2. データセンタ：Spine-Leaf（クロスファブリック）

サーバー間通信（East-West トラフィック）が支配的なデータセンタでは、3階層ではなく **Spine-Leaf** を使います。

```
        ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐
        │Spine 1 │  │Spine 2 │  │Spine 3 │  │Spine 4 │
        └─┬─┬─┬─┬┘  └─┬─┬─┬─┬┘  └─┬─┬─┬─┬┘  └─┬─┬─┬─┬┘
          │ │ │ └──────┼─┼─┼─┼──────┼─┼─┼─┼──────┘ │ │ │
          │ │ └────────┼─┼─┼─┼──────┼─┼─┼─┼────────┘ │ │
          （全 Leaf が全 Spine に接続 ＝ フルメッシュ）
          │ │ │        │ │ │ │      │ │ │ │          │ │ │
        ┌─┴─┴─┴──┐  ┌──┴─┴─┴─┴┐  ┌─┴─┴─┴─┴┐  ┌──────┴─┴─┴┐
        │ Leaf 1 │  │  Leaf 2  │  │ Leaf 3 │  │  Leaf 4   │
        └───┬────┘  └────┬─────┘  └───┬────┘  └─────┬─────┘
          サーバー      サーバー      サーバー      サーバー
```

| 特徴 | 内容 |
| --- | --- |
| **どのサーバー間も必ず2ホップ** | 遅延が均一で予測可能 |
| **ECMPで全経路を使う** | STPでブロックする経路が無い（帯域が無駄にならない） |
| **拡張が容易** | Leafを足せばサーバーが増える、Spineを足せば帯域が増える |
| **VXLAN + EVPN** | L2をL3上にオーバーレイ。**VLANの4094個制限を突破**（1600万） |
| **ルーティング** | **eBGP** が主流（Leaf/Spine ごとにAS番号） |

### 4-3. 機器構成と費用目安

| 役割 | 機器 | 費用目安 |
| --- | --- | --- |
| コアスイッチ | シャーシ型・100G/400G | 1,000〜5,000万円/台 |
| ディストリスイッチ | 25G/100G アップリンク | 200〜800万円/台 |
| アクセススイッチ | 48ポート PoE++ | 30〜80万円/台 × 数百台 |
| NGFW | 高性能・クラスタ構成 | 1,000〜5,000万円 |
| SD-WAN / SASE | 全拠点分ライセンス | 年額 数千円〜/ユーザー |
| ロードバランサ | 冗長構成 | 500〜3,000万円 |
| DC（Spine-Leaf） | 1ラック分〜 | 数千万〜数億円 |
| **初期合計** | | **1億円〜数十億円** |

### 4-4. 設計のポイント

| 項目 | 推奨 |
| --- | --- |
| **アーキテクチャ** | キャンパスは3階層、DCはSpine-Leaf |
| **冗長化** | **N+1 以上。経路・電源・空調・回線・引込経路すべて** |
| **ルーティング** | 社内 OSPF（マルチエリア）or IS-IS、DC/外部接続 BGP |
| **オーバーレイ** | VXLAN + EVPN（マルチテナント・VLAN上限の突破） |
| **自動化** | **Ansible / Terraform / IaC**。手作業は事故の元 |
| **監視** | SNMP＋NetFlow/sFlow＋ストリーミングテレメトリ＋APM |
| **セキュリティ** | SASE/ZTNA・マイクロセグメンテーション・SOC 24/365 |
| **変更管理** | **CAB（変更諮問委員会）・作業手順書・切り戻し手順の事前承認** |
| **BCP/DR** | 地理的に離れたDC。RTO/RPOを定義（→ [⑪](11-operations.md)） |

### 4-5. 大規模では「技術」より「プロセス」が問題になる

```
大規模障害の原因の内訳（一般的な傾向）
  ・設定変更の誤り        ← 最多
  ・機器故障
  ・キャパシティ超過
  ・外部要因（キャリア障害・電源・災害）

→ 技術で防げるのは一部。「変更管理プロセス」の整備が最も効果的
```

| 必要なプロセス | 内容 |
| --- | --- |
| **変更管理** | 申請 → レビュー → 承認 → 実施 → 検証 → 記録 |
| **構成管理（CMDB）** | 何がどこにあり、何に依存しているかの台帳 |
| **インシデント管理** | 検知 → 一次対応 → エスカレーション → 恒久対策 |
| **キャパシティ管理** | 帯域・ポート・IP・ライセンスの使用率を定期レビュー |
| **ライフサイクル管理** | EOL/EOSの5年計画。**予算化を先に済ませる** |

## 5. 規模別 総合比較表

| 項目 | 小規模（〜50人） | 中規模（50〜500人） | 大規模（500人〜） |
| --- | --- | --- | --- |
| **階層** | 1階層 | 2階層（コア＋アクセス） | 3階層／Spine-Leaf |
| **FW** | UTM 1台 | NGFW HA構成 | NGFWクラスタ＋SASE |

## 6. 移行のトリガー — いつ次の段階へ進むか

### 6-1. 小規模 → 中規模

以下のうち**2つ以上**当てはまったら、構成を見直す時期です。

```
□ 端末が150台を超えた（1セグメントの限界）
□ 拠点が2つ以上になった
□ ネットワーク停止で1時間あたり数十万円以上の損失が出る
□ Wi-Fiが「会議室で使えない」と苦情が出始めた
□ 「誰が何に繋いでいるか」を把握できなくなった
□ 情報システム担当が専任になった／なる予定
□ 監査・取引先から情報セキュリティ要件を求められた
```

### 6-2. 中規模 → 大規模

```
□ 拠点が10を超えた／海外拠点ができた
□ 自社データセンタ or 大規模なプライベートクラウドを持つ
□ 24時間365日の稼働が求められる
□ 情報システム部門が5名以上になった
□ 手作業での設定変更が追いつかない（自動化が必要）
□ 監査・法規制でログの長期保管と分析が必須になった
□ M&Aで異なるネットワークの統合が発生した
```

### 6-3. 「段階を飛ばす」のは可能か

**可能です。むしろ推奨される場合があります。**

```
【従来型の階段】小規模 → 中規模 → 大規模（機器を買い足していく）

【現代的な選択】小規模 → クラウド＋SASE中心の構成
              → 拠点が増えても「機器を増やさず」対応できる

  例：50人 → 300人 に成長したが、
      ・サーバーは全部クラウド
      ・セキュリティはSASE（ユーザー課金）
      ・各拠点はインターネット回線＋小型ルータのみ
      → 中規模の重厚な機器投資をスキップできる
```

この判断については、次章 [⑩ オンプレ・クラウド・ハイブリッド](10-onprem-cloud-hybrid.md) で詳しく扱います。

## 7. 業種別の構成の勘所

規模だけでなく、**業種特有の要件**が構成を左右します。

| 業種 | 特有の要件 | 構成への影響 |
| --- | --- | --- |
| **製造業（工場）** | 制御系（OT）の可用性が最優先。止まると生産停止 | **OT/IT を完全分離**。OT側はレガシー機器が多く更新困難 |
| **小売・飲食（多店舗）** | 店舗数が多く、各店に技術者がいない | **ゼロタッチ導入・SD-WAN**。POS の可用性 |
| **医療** | 電子カルテ・医療機器。**個人情報が最高機密** | 厳格なセグメント分離・3省2ガイドライン対応 |
| **金融** | 規制・監査・低遅延 | 専用線・厳格な変更管理・ログ長期保管 |
| **教育** | 端末密度が極端に高い（1教室40台同時） | **高密度Wi-Fi設計が最重要**。予算制約が強い |
| **建設** | 現場が移動する・仮設 | **モバイル回線中心**。ローカル5G の検討 |
| **IT/SaaS** | 社内システムが少なく、クラウド中心 | **オフィスはインターネット回線とWi-Fiだけで足りる** |

## 8. よくある疑問（FAQ）

**Q. 予算が限られている。何から手を付けるべき？**
A. 優先順位は **①バックアップ（3-2-1）→ ②MFA → ③ネットワークの冗長化 → ④監視 → ⑤機器の高機能化** です。**高価なUTMを買うより、バックアップとMFAを整える方が、被害を防ぐ効果は圧倒的に大きい**です。

**Q. 機器はどのくらいで更改すべき？**
A. **5年**が目安です。理由は、①メーカー保守（EOS）が5〜7年で切れる、②減価償却が5年、③5年で性能要件が1世代変わる、の3つ。**EOL日を機器台帳に記載し、3年目から予算化**を始めてください。

**Q. 自社で運用すべきか、外部委託すべきか？**
A. 判断軸は**「障害時に何分で復旧できる体制か」**です。小規模で専任がいないなら、**保守契約＋リモート監視サービス**の方が結果的に安く速いことが多いです。中規模以上は、設計は外部・運用は自社、というハイブリッドが一般的です。

**Q. 「クラウド管理型」の機器（Meraki、UniFi等）はどうか？**
A. **小〜中規模では非常に有効**です。設定がGUIで完結し、拠点にログインせず一括管理でき、担当者のスキル要件も下がります。注意点は、**①年額ライセンスが必須（切れると機能停止する製品もある）**、**②クラウド管理基盤の障害時の影響**、**③細かい制御が効かない場合がある**こと。

**Q. 人数が増える予定だが、今はまだ小さい。どう設計すべき？**
A. **物理配線とIPアドレス設計だけは、将来の規模で作ってください。** この2つは後からの変更コストが桁違いです。機器は必要になってから買い足せます。具体的には、**配線は多めに敷設（空配管も）**、**IPは `/16` で予約**しておく、が鉄則です。

## まとめ

- 規模の判断は**人数ではなく「止まったときの損害」**で行う
- 端末台数は **人数 × 2〜3** で見積もる
- **小規模**：1階層・UTM 1台・**モバイル回線でWANだけ冗長化**が費用対効果◎。**管理型スイッチを選ぶこと**
- **中規模**：2階層・コアとNGFWを冗長化・**802.1X**・標準構成の統一。**監視を後回しにしない**
- **大規模**：3階層／Spine-Leaf・全経路冗長・自動化。**技術よりプロセス（変更管理）が要**
- 移行トリガーは **端末150台／拠点2つ／拠点10／損害額** が目安
- **配線とIPアドレス設計だけは将来の規模で作る**（後から変えられない）
- 現代は**中規模の重厚な機器投資をスキップして、クラウド＋SASEに寄せる選択肢**がある
- 機器は**5年で更改**。EOLを台帳に書き、3年目から予算化
